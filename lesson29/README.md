# 第29章 ソフトウェアの脆弱性と対策（OWASP）【D8】

D8 の中核、ソフトウェアの脆弱性を学ぶ章です。攻撃の仕組みを「名前と特徴で見分け、最も効果的な対策を選べる」ことがゴールで、SQL インジェクションやバッファオーバーフロー、集計と推論など CISSP 超頻出の論点を扱います。開発経験がある方こそ「コードの書き方」ではなく「管理者としてどの対策を優先するか」という視点の切り替えを意識してください。

## 1. Webアプリケーションの脆弱性

### OWASP Top 10 — 攻撃の「定番」を知る

Web アプリの脆弱性は **OWASP Top 10** に代表的なものがまとまっています。近年の版では**アクセス制御の不備 (Broken Access Control)** が第1位で、「インジェクションだけが怖いのではない」という傾向の変化も試験で問われます。

### 代表的な攻撃と対策の対応表

| 攻撃 | 仕組み | 最も効果的な対策 |
|---|---|---|
| SQLインジェクション (SQL injection) | 入力欄に SQL の断片を混ぜて実行させる | **パラメータ化クエリ (prepared statement)** + 入力検証 |
| XSS (cross-site scripting) | ページに悪意のスクリプトを埋め込み、閲覧者のブラウザで実行 | **出力時のエスケープ** + CSP |
| CSRF (cross-site request forgery) | ログイン済みユーザーに意図しないリクエストを送らせる | **CSRF トークン**(リクエストの正当性確認) |
| SSRF (server-side request forgery) | サーバーに内部ネットワークへのリクエストを代行させる | 宛先の許可リスト |
| ディレクトリトラバーサル | `../` でパスを遡り非公開ファイルへ到達 | 入力検証・正規化 |

XSS には、投稿として保存されて何度も実行される**格納型 (stored)**、URL に仕込んで踏ませる**反射型 (reflected)**、ブラウザ内の処理だけで起きる **DOM 型**があります。

### セッション管理と入力検証の鉄則

セッション ID の推測・固定化 (session fixation) を防ぐには、**ログイン成功時に ID を再発行**し、Cookie に Secure / HttpOnly 属性を付けます。

> 💡 コツ: 試験のひっかけ No.1 は「クライアント側 (JavaScript) の入力検証」です。利便性には役立ちますが、攻撃者はブラウザを介さずリクエストを送れるため、**検証は必ずサーバー側でも行う**が正解です。

マネジメント視点では、個別のバグ修正より「セキュアコーディング標準の整備と開発者教育」が根本対策 (BEST) になりやすい点も覚えておきましょう。

### 確認問題

**問1.** Web アプリの検索欄への入力を使って SQL 文が組み立てられており、攻撃者が「' OR 1=1 --」のような文字列でデータベース全件を取得できることが判明しました。最も効果的 (MOST effective) な対策はどれですか？

1. 詳細なエラーメッセージを画面に表示しないようにする
2. パラメータ化クエリ(プリペアドステートメント)で SQL を組み立てる
3. クライアント側の JavaScript で特殊文字を除去する
4. データベースのテーブルを暗号化する

<details><summary>答えと解説</summary>

正解: **2**

SQL インジェクションの根本対策は、入力データを SQL の構文と分離する**パラメータ化クエリ**です。エラーメッセージの抑制は攻撃のヒントを減らすだけで侵入自体は防げません。クライアント側検証は攻撃者がブラウザを介さずリクエストを送れば素通りします(試験の定番ひっかけ)。テーブル暗号化は漏えい時の被害軽減策で、正規のアプリ経由で実行されるインジェクションには無力です。「最も効果的」と問われたら、緩和策ではなく根本原因を断つ選択肢を選びましょう。

</details>

**問2.** 掲示板サイトに書き込まれた投稿を他のユーザーが閲覧すると、ブラウザ上で不正なスクリプトが実行され、セッション Cookie が攻撃者に送信されていました。この攻撃の分類として正しいものはどれですか？

1. 反射型 XSS
2. CSRF
3. SQL インジェクション
4. 格納型 XSS

<details><summary>答えと解説</summary>

正解: **4**

悪意のスクリプトが**サーバーに保存され、閲覧者全員の環境で繰り返し実行される**のは格納型(stored/persistent) XSS です。反射型はリンクに仕込んだスクリプトがその場で返ってくるもので保存されません。CSRF はスクリプト実行ではなく「ログイン済みユーザーに意図しないリクエストを送らせる」攻撃、SQL インジェクションはデータベースへの攻撃で、ブラウザ上でのスクリプト実行とは別物です。XSS の 3 類型(格納型・反射型・DOM 型)は「どこに仕込まれるか」で見分けます。

</details>

**問3.** 銀行サイトにログイン中のユーザーが攻撃者のページを開いたところ、ユーザーが気づかないうちに送金リクエストが銀行サイトへ送信されました。この攻撃への対策として最も適切 (BEST) なものはどれですか？

1. 正当な画面から発行された CSRF トークンをリクエストごとに検証する
2. 通信を TLS で暗号化する
3. パスワードの複雑さ要件を強化する
4. WAF でSQL構文を含むリクエストを遮断する

<details><summary>答えと解説</summary>

正解: **1**

これは CSRF(クロスサイトリクエストフォージェリ)で、「ログイン済みの正規ユーザーの権限」が悪用されます。対策は、正当なフォームから発行された**トークン**をリクエストに含めて検証し、外部サイト発のリクエストを拒否することです。TLS は盗聴対策であり、正規ユーザーのブラウザから送られる CSRF リクエストも正しく暗号化されて届いてしまいます。パスワード強化も無関係(すでにログイン済みの状態が悪用されるため)。WAF の SQL 遮断は別の攻撃向けです。「ログイン済み」「気づかないうちにリクエスト」のキーワードから CSRF を見抜きましょう。

</details>

**問4.** 開発チームが「入力チェックはブラウザの JavaScript で実装済みなので安全です」と報告してきました。セキュリティ専門家として最も適切 (MOST appropriate) な指摘はどれですか？

1. JavaScript は性能が低いので別の言語で書き直すべきである
2. 入力チェックよりも WAF の導入を優先すべきである
3. 攻撃者はクライアントを経由せずリクエストを送れるため、サーバー側でも検証が必要である
4. JavaScript のコードを難読化すれば安全性は確保できる

<details><summary>答えと解説</summary>

正解: **3**

クライアント側の検証はユーザビリティ向上には有効ですが、攻撃者は curl や中間プロキシで**ブラウザを介さずに任意のリクエストを送信**できるため、セキュリティ境界にはなりません。検証は必ず**サーバー側で**行います(超頻出)。性能の話は論点のすり替え、WAF は多層防御の一枚にはなりますがアプリ自身の検証の代替ではありません。難読化は解析の手間を増やすだけで、リクエスト改ざんは防げません。「クライアント側だけで検証」と見たら即座に誤りと判断できるようにしましょう。

</details>

**問5.** 近年の OWASP Top 10 で第1位に位置づけられ、「一般ユーザーが URL を書き換えるだけで他人のデータや管理者機能にアクセスできてしまう」タイプの脆弱性はどれですか？

1. 暗号化の失敗
2. アクセス制御の不備 (Broken Access Control)
3. インジェクション
4. セキュリティの設定ミス

<details><summary>答えと解説</summary>

正解: **2**

近年の OWASP Top 10 では**アクセス制御の不備**が第1位です。URL のパラメータ書き換えで他人の情報が見える(IDOR など)、権限チェックの漏れで管理機能に到達できる、といった認可の欠陥が該当します。インジェクションはかつての第1位で今も重大ですが順位が下がりました。暗号化の失敗は保護すべきデータの平文保存など、設定ミスはデフォルト設定の放置などで、問題文の「URL を書き換えるだけで他人のデータに到達」は認可チェックの欠如そのものです。順位より「どの説明がどの脆弱性か」を見分けられることが大切です。

</details>

## 2. メモリと実行環境の脆弱性

### バッファオーバーフロー — 古典にして超頻出

**バッファオーバーフロー (buffer overflow)** は、確保したメモリ領域を超えるデータを書き込ませ、隣接領域を上書きして任意コードを実行させる攻撃です。

| 対策 | 位置づけ |
|---|---|
| **境界チェック・入力長の検証** | 根本対策(開発時に作り込む) |
| ASLR(アドレス配置のランダム化)・DEP(データ領域の実行禁止) | **緩和策**(攻撃を難しくするだけ) |
| メモリ安全な言語(Java、Go、Rust など)の採用 | 設計レベルの対策 |

「最も効果的な対策は?」と問われたら、ASLR ではなく**入力の境界チェック**(または メモリ安全な言語)が正解になりやすい点に注意してください。

### 競合状態と TOCTOU

**競合状態 (race condition)** は処理の順序やタイミングのすき間を突く脆弱性で、代表例が **TOCTOU (time-of-check to time-of-use)** です。「権限を確認した時点」と「実際に使う時点」の間にファイルを差し替えるなど、**チェックと使用の間隙**が攻撃されます。対策は操作のアトミック化(不可分化)やロックです。

### その他の実行環境の論点

- **メンテナンスフック/バックドア**: 開発者がデバッグ用に仕込んだ秘密の入口。**出荷・本番移行前に必ず除去**します
- **特権昇格 (privilege escalation)**: 一般権限から管理者権限を奪取。最小権限とパッチ適用で緩和
- **エラー処理**: 詳細なスタックトレースやDBエラーは攻撃者へのヒントです。**ユーザーには一般的なメッセージ、詳細は内部ログへ**が鉄則
- **整数オーバーフロー**: 桁あふれで検証をすり抜ける。型と範囲の検証が対策

> 💡 コツ: 「チェックした後に使う」という記述を見たら TOCTOU、「確保した領域を超える」ならバッファオーバーフロー、と**キーワードで即断**できるようにしておくと CAT 形式で時間を稼げます。

### 確認問題

**問1.** C 言語で書かれた入力処理関数に、確保したバッファ長を超えるデータを送り込むと任意のコードが実行できる欠陥が見つかりました。根本原因を断つ対策として最も効果的 (MOST effective) なものはどれですか？

1. ASLR を有効にしてメモリ配置をランダム化する
2. IDS を導入して攻撃を検知する
3. 入力データの長さを検証する境界チェックを実装する
4. 管理者権限でのプロセス実行をやめる

<details><summary>答えと解説</summary>

正解: **3**

バッファオーバーフローの根本原因は「入力長を確認せずにメモリへ書き込むコード」なので、**境界チェック(入力長の検証)の実装**が根本対策です。ASLR は攻撃の成功率を下げる**緩和策**にすぎず、欠陥自体は残ります(定番のひっかけ)。IDS は検知のみで防止になりません。最小権限での実行は被害を小さくする良い習慣ですが、こちらも緩和策です。「根本原因を断つ」「最も効果的」と問われたら、コードの欠陥そのものを直す選択肢を選びます。

</details>

**問2.** あるプログラムは、ファイルへのアクセス権限を確認してから数ミリ秒後に実際の書き込みを行います。攻撃者はこのすき間にシンボリックリンクを差し替え、本来書き込めないシステムファイルを上書きしました。この脆弱性の名称はどれですか？

1. TOCTOU(check 時と use 時の競合状態)
2. バッファオーバーフロー
3. セッション固定化
4. 整数オーバーフロー

<details><summary>答えと解説</summary>

正解: **1**

「権限を確認した時点 (time-of-check)」と「実際に使用する時点 (time-of-use)」の間隙を突く攻撃は **TOCTOU**、競合状態 (race condition) の代表例です。対策はチェックと使用をアトミック(不可分)な操作にすること、ロックの利用です。バッファオーバーフローはメモリ領域の超過書き込み、セッション固定化は Web のセッション ID を事前に固定する攻撃、整数オーバーフローは数値の桁あふれで、いずれも「チェックと使用の時間差」という本問のキーワードに合いません。

</details>

**問3.** 本番リリース直前のコードレビューで、開発者が認証を迂回してシステムに入れるデバッグ用の隠し機能が見つかりました。最も適切 (BEST) な対応はどれですか？

1. リリース後に修正パッチで対応する
2. 隠し機能のパスワードを複雑なものに変更する
3. 文書化して運用チームに引き継ぐ
4. リリース前に該当コードを完全に除去する

<details><summary>答えと解説</summary>

正解: **4**

これは**メンテナンスフック(バックドア)**です。認証を迂回する入口は攻撃者に発見されれば全統制が無効になるため、**本番移行前に完全除去**が原則です。パスワード変更や文書化は「バックドアの存在を容認する」選択肢であり誤り。リリース後のパッチ対応は、除去できると分かっているリスクを一時的に受容する合理性がなく、デューケアを欠きます。試験では「デバッグ用の隠し入口」と見たら「出荷前に除去」が反射的に選べるようにしましょう。

</details>

**問4.** Web アプリでエラーが発生した際、ユーザーの画面にデータベース名・テーブル構造・スタックトレースが表示されています。これの最大の問題点はどれですか？

1. ユーザー体験が悪化し、サポートコストが増える
2. 攻撃者に内部構造のヒントを与え、攻撃の精度を高めさせる
3. 画面表示が増えることでサーバーの性能が低下する
4. ログファイルの容量が増加する

<details><summary>答えと解説</summary>

正解: **2**

詳細なエラー情報は攻撃者にとって**偵察情報の宝庫**です。テーブル構造が分かれば SQL インジェクションの精度が上がり、スタックトレースからフレームワークのバージョンや脆弱性を特定できます。正しい設計は「ユーザーには一般的なメッセージ、詳細は内部ログにのみ記録」です。ユーザー体験やサポートコストは実害として小さくないものの、セキュリティ試験で問われる「最大の問題」は情報漏えいです。性能やログ容量は本質と無関係な選択肢です。

</details>

**問5.** 新規開発プロジェクトで、バッファオーバーフローなどメモリ系脆弱性の混入を設計段階から減らしたいと考えています。最も効果的 (MOST effective) なアプローチはどれですか？

1. リリース後に侵入テストを毎年実施する
2. 全開発者にセキュリティ誓約書への署名を義務づける
3. メモリ管理を言語ランタイムが行う、メモリ安全な言語を採用する
4. DEP と ASLR を本番サーバーで有効化する

<details><summary>答えと解説</summary>

正解: **3**

設計段階の判断として、Java・Go・Rust のような**メモリ安全な言語**を採用すれば、境界チェックやメモリ解放をランタイムが担い、バッファオーバーフロー系の脆弱性をクラスごと排除できます。これは「シフトレフト(早い工程での対策)」の典型です。侵入テストは出来上がった後の発見手段で、混入自体は減らせません。誓約書は管理的統制ですが技術的な作り込みミスは防げません。DEP/ASLR は運用段階の緩和策で「設計段階から減らす」という問いに合いません。問題文の工程(設計・開発・運用)に合った対策を選ぶのがコツです。

</details>

## 3. データベースのセキュリティ — 集計・推論・暗号化

### 集計と推論 — 似て非なる超頻出ペア

データベース特有の脅威として、CISSP では**集計 (aggregation)** と**推論 (inference)** の区別が繰り返し問われます。

| 用語 | 仕組み | 例 |
|---|---|---|
| **集計 (aggregation)** | 個々には無害な低機密データを**大量に集める**と、全体として高機密になる | 各支店の売上を全部集めると会社全体の未公表業績が分かる |
| **推論 (inference)** | アクセスできる情報から、アクセスできない機密を**論理的に導き出す** | 部品の発注急増と求人情報から新製品の発売時期を見抜く |

対策には、**ポリインスタンス化 (polyinstantiation)**(同じ主キーで機密レベルごとに異なる内容の行を持たせ、下位クリアランスの利用者に偽装データを見せる)、ノイズや擾乱の挿入、コンテキスト依存アクセス制御(問い合わせの回数・組み合わせを制限)があります。ポリインスタンス化は「下位利用者の推論を防ぐための正当な嘘」という独特の仕組みで、超頻出です。

### アクセス制御と暗号化の層

- **ビュー (view)**: テーブルの特定の行・列だけを見せる仮想的な表。**コンテンツ依存アクセス制御**の代表例です
- **ストアドプロシージャ**: 決められた操作だけを許し、直接のテーブル操作を防ぎます
- **暗号化の層**: ストレージごと守る TDE (transparent data encryption)、特定の機微な列だけ守る**列レベル暗号化**、アプリ層での暗号化。守りたい脅威(媒体盗難か、DBA の覗き見か)で選びます
- **NoSQL インジェクション**: SQL でなくても、クエリを文字列連結で組み立てれば同種の注入が成立します

### データマイニングとプライバシー

データウェアハウスでの**ナレッジ発見 (KDD)** は有用ですが、個人データの組み合わせがプライバシー侵害や推論リスクを生みます。目的外利用の制限と匿名化の検討がマネジメントの責務です。

> 💡 コツ: 「集める」と書いてあれば集計、「導き出す・見抜く」なら推論。動詞に注目すると一瞬で見分けられます。

### 確認問題

**問1.** 機密区分のない出荷データベースにアクセスできる社員が、特定部品の発注量の急増・新しい梱包資材の調達・工場の求人増という複数の情報から、未発表の新製品の生産開始時期を言い当てました。この脅威はどれに分類されますか？

1. 集計 (aggregation)
2. 推論 (inference)
3. SQL インジェクション
4. ショルダーサーフィン

<details><summary>答えと解説</summary>

正解: **2**

アクセス可能な情報を手がかりに、直接はアクセスできない機密(新製品の生産時期)を**論理的に導き出して**いるので推論 (inference) です。集計は「同種の低機密データを大量に集めると全体が高機密になる」ことで、本問は異なる種類の情報からの導出なので推論が適切です。SQL インジェクションは不正なクエリ注入、ショルダーサーフィンは画面の覗き見で、どちらも正規のアクセス権の範囲内で起きている本問とは異なります。「集める=集計、導き出す=推論」と動詞で見分けましょう。

</details>

**問2.** 軍事システムのデータベースで、機密クリアランスのない利用者が「存在しないはずの艦船の行き先」を照会した際、空欄を返すと存在自体を推測されるため、同じ主キーに対して無害なダミーの行を返す設計にしました。この技法はどれですか？

1. トークン化
2. 正規化
3. シャドーイング
4. ポリインスタンス化

<details><summary>答えと解説</summary>

正解: **4**

**ポリインスタンス化 (polyinstantiation)** は、同一の主キーに機密レベルごとに異なる内容の行(インスタンス)を持たせ、下位クリアランスの利用者には偽装データを見せることで**推論攻撃を防ぐ**技法です。「空欄や拒否の応答そのものがヒントになる」問題への対策である点が独特です。トークン化は機微データを無意味な代替値に置き換える保護、正規化はデータベース設計の冗長排除でセキュリティ技法ではありません。シャドーイングという標準用語はこの文脈にはありません。軍事DBの文脈+ダミー行とくればポリインスタンス化と即断できます。

</details>

**問3.** 人事データベースで、一般の管理職には自部門の社員の氏名と内線番号だけを見せ、給与列や他部門の行は見せないようにしたいと考えています。最も適切 (BEST) な実装はどれですか？

1. 必要な行と列だけを含むビューを定義し、ビューにのみ権限を付与する
2. テーブル全体を TDE で暗号化する
3. 管理職全員にテーブルへの SELECT 権限を付与し、閲覧ルールを周知する
4. 給与データを別サーバーに移設する

<details><summary>答えと解説</summary>

正解: **1**

特定の**行と列だけを見せる**ならビュー (view) が定石で、コンテンツ依存アクセス制御の代表例です。TDE はストレージ・媒体レベルの暗号化で、正規に接続した利用者には透過的に復号されるため閲覧制限になりません(頻出ひっかけ)。SELECT 権限+周知は技術的統制を欠き、「信頼するが検証しない」状態です。別サーバー移設は過剰かつ管理コスト増で、行・列単位の制御という要件も満たしません。「見せる範囲を絞る」要件にはビュー、と覚えてください。

</details>

**問4.** データベース暗号化の方式を選定しています。「ディスクやバックアップ媒体の盗難には備えたいが、アプリケーションの改修はできない」という制約がある場合、最も適切 (MOST appropriate) な選択はどれですか？

1. アプリケーション層での項目単位暗号化
2. クライアント側暗号化
3. TDE(透過的データ暗号化)
4. ハッシュ化して保存する

<details><summary>答えと解説</summary>

正解: **3**

**TDE (transparent data encryption)** はデータベースがストレージへの書き込み時に自動で暗号化する方式で、**アプリの改修なし**に媒体盗難・バックアップ流出に備えられます。「透過的」の名のとおりアプリからは暗号化を意識しません。アプリ層・クライアント側の暗号化はより強い保護(DBA からも隠せる)ですが、アプリ改修が必要で本問の制約に反します。ハッシュ化は不可逆で元データを読み出せなくなるため、通常業務データには使えません。暗号化方式は「どの脅威に備えるか+制約」で選ぶのが試験の定石です。

</details>

**問5.** マーケティング部門がデータウェアハウスで顧客の購買履歴・位置情報・問い合わせ履歴を結合し、個人の行動プロファイルを自動生成する分析プロジェクトを開始しようとしています。セキュリティ管理者として最初に (FIRST) 行うべきことはどれですか？

1. 分析サーバーのスペックを増強する
2. 分析結果を全社に公開する手順を整備する
3. 結合後データの機密区分を下げて利用しやすくする
4. 利用目的がプライバシーポリシーと法規制に適合するか評価する

<details><summary>答えと解説</summary>

正解: **4**

複数データの結合(集計)は**単体では見えなかった機微な人物像**を作り出すため、まず**目的の正当性とプライバシー法規制への適合性を評価**するのがマネジメントの第一歩です。収集時の同意目的を超える利用は GDPR 等に抵触し得ます。サーバー増強や公開手順は適法性確認の後の話。結合後のデータは機微性が**上がる**ので機密区分を下げるのは逆方向の誤りです(集計の教訓)。FIRST 問題では「評価・確認」が「構築・実行」より先に来る、という CISSP の鉄則を思い出してください。

</details>
