# 第28章 セキュアなソフトウェア開発ライフサイクル【D8】

D8（ソフトウェア開発セキュリティ）の入り口として、開発ライフサイクル全体にセキュリティを組み込む考え方を学びます。CISSP では「どの段階で何をするのが最も効果的か」「開発プロセスをどう統制するか」というマネジメント視点が問われます。開発経験がある人ほど「技術的に正しい選択肢」を選びがちなので、プロセスと統制を優先する CISSP 的思考に切り替えましょう。

## 1. SDLCへのセキュリティ組み込みとシフトレフト

### セキュリティは「後付け」できない

ソフトウェア開発ライフサイクル (SDLC: Software Development Life Cycle) とは、要件定義から廃棄までの一連の流れです。CISSP の鉄則は **「セキュリティは SDLC の最初から、すべての段階に組み込む」** です。完成後に付け足すセキュリティは高コストで不完全になります。

| 段階 | 主なセキュリティ活動 |
|---|---|
| 要件定義 (requirements) | セキュリティ要件・プライバシー要件の定義、データ分類 |
| 設計 (design) | **脅威モデリング (threat modeling)**、設計レビュー、アーキテクチャ分析 |
| 実装 (implementation) | セキュアコーディング標準、**コードレビュー**、静的解析 |
| テスト (testing) | セキュリティテスト、脆弱性診断、受入テスト |
| 展開 (deployment) | 運用の認可 (authorization)、セキュアな構成 |
| 運用・保守 (operations) | パッチ、監視、変更管理 |
| 廃棄 (disposal) | データのサニタイズ、安全な移行 |

### シフトレフト (shift left)

工程を左（早い段階）に寄せるほど、欠陥の修正コストは安くなります。**要件・設計段階で見つけた欠陥の修正コストは、本番稼働後に見つけた場合の数十分の一**と言われます。脅威モデリングが「設計段階で行うのが最良」とされるのはこのためです。

### 展開前の「認可」

システムを本番に載せる前には、残留リスクを理解した**権限ある管理者がリスクを受容して運用を認可 (authorization to operate)** します。技術者のテスト合格だけでは不十分で、経営側の受容判断が必要という点が CISSP 的です。

💡 コツ: 「いつセキュリティを組み込むべきか」と問われたら、選択肢の中で**最も早い段階**を選ぶのが原則です。「テスト段階で初めてセキュリティチームが関与」は典型的な誤りの選択肢です。

### 確認問題

**問1.** 新規アプリケーション開発プロジェクトで、セキュリティ要件への対応コストを最小にしたいと考えています。セキュリティチームが関与を開始するタイミングとして最も適切 (BEST) なのはどれでしょうか？

1. 受入テストで脆弱性診断を行うとき
2. 本番展開の認可を判断するとき
3. 要件定義でセキュリティ要件を定義するとき
4. 実装段階でコードレビューを行うとき

<details><summary>答えと解説</summary>

正解: **3**

シフトレフト (shift left) の原則どおり、最も早い「要件定義」段階から関与するのが最も低コストで効果的です。テスト・展開・実装の各段階での活動はいずれも必要ですが、そこで「初めて」関与すると手戻りコストが大きくなります。CISSP では「いつ組み込むか」と問われたら最も早い段階を選ぶのが鉄則です。選択肢に『設計』と『要件定義』が並んだ場合も、より早い方を選びましょう。

</details>

**問2.** 脅威モデリング (threat modeling) を実施する時期として最も効果的 (MOST effective) なのはどれでしょうか？

1. 設計段階
2. 実装が完了した直後
3. ペネトレーションテストの直前
4. 本番稼働後の最初のレビュー時

<details><summary>答えと解説</summary>

正解: **1**

脅威モデリングはアーキテクチャが固まる設計段階で行うのが最も効果的です。この時点なら設計変更で脅威を根本から排除でき、コストも最小で済みます。実装後・テスト直前・稼働後では、発見した問題の修正に大きな手戻りが発生します。『稼働後にもレビューはするから正しいのでは』と迷わせるひっかけに注意してください。問われているのは「最も効果的な時期」です。

</details>

**問3.** 開発チームがテストをすべて完了し、システムを本番環境へ展開しようとしています。展開の前に必要な手続きとして最も適切なのはどれでしょうか？

1. 開発リーダーがテスト結果を確認して展開を実行する
2. ペネトレーションテスト業者が合格証明書を発行する
3. ユーザー部門が操作マニュアルを承認する
4. 権限ある管理者が残留リスクを受容し運用を認可する

<details><summary>答えと解説</summary>

正解: **4**

本番展開の前には、残留リスクを理解した権限ある管理者（認可責任者）がリスクを受容して運用を認可 (authorization) する必要があります。これは技術判断ではなく経営側の受容判断です。開発リーダーの確認は職務分掌の観点でも不適切（開発者が自分の成果物を承認して展開することになる）、外部業者の証明やマニュアル承認はリスク受容の代わりにはなりません。「技術テスト合格＝展開してよい」としない点が CISSP 的な考え方です。

</details>

**問4.** ソフトウェアの欠陥修正コストについて、CISSP 的に正しい説明はどれでしょうか？

1. 修正コストは発見時期によらずほぼ一定である
2. 発見が遅い段階になるほど修正コストは高くなる
3. テスト段階で発見するのが最も安く修正できる
4. 本番稼働後はパッチ配布で修正できるため最も安い

<details><summary>答えと解説</summary>

正解: **2**

欠陥は発見が遅れるほど、影響範囲の拡大・手戻り・インシデント対応などで修正コストが跳ね上がります。これがシフトレフトの根拠です。「一定」は明確な誤り、「テスト段階が最安」は要件・設計段階より遅いので誤り、「稼働後が最安」は実際には最も高くつくため誤りです。数十倍の差になるという定性的な理解を問う問題は頻出です。

</details>

**問5.** 古いシステムを廃棄 (disposal) してクラウド上の新システムへ移行します。廃棄段階のセキュリティ活動として最も重要 (MOST important) なのはどれでしょうか？

1. 旧システムのソースコードをアーカイブする
2. 旧システムの利用者アンケートを実施する
3. 記憶媒体のデータをサニタイズし、必要なデータを安全に移行する
4. 旧システムのライセンス費用を精算する

<details><summary>答えと解説</summary>

正解: **3**

廃棄段階の最重要事項は、データ残留 (data remanence) を防ぐための媒体サニタイズと、保持義務のあるデータの安全な移行です。これを怠ると廃棄した機器からの情報漏えいにつながります。ソースコードのアーカイブやライセンス精算は管理上は有用でもセキュリティ上の最重要事項ではなく、アンケートはセキュリティ活動ではありません。「廃棄＝データの終わりの始末」と覚えましょう。

</details>

## 2. 開発手法と成熟度モデル（ウォーターフォール・アジャイル・CMMI）

### 開発手法の対比（超頻出）

| 手法 | 特徴 | 向いているケース |
|---|---|---|
| ウォーターフォール (waterfall) | 工程を順番に進む。文書と承認が厳格。**後からの変更に弱い** | 要件が明確で変更が少ない大規模・規制産業の案件 |
| スパイラル (spiral) | 設計〜評価を繰り返すメタモデル。**各反復の先頭でリスク評価**を行う | リスクが高く段階的に固めたい大型案件 |
| アジャイル (agile) | 短い反復 (イテレーション) で動くソフトウェアを頻繁に届ける | 要件が流動的な案件 |

アジャイルソフトウェア開発宣言の「4つの価値」は、プロセスやツールよりも**個人と対話**を、包括的なドキュメントよりも**動くソフトウェア**を、契約交渉よりも**顧客との協調**を、計画に従うことよりも**変化への対応**を価値とする、という内容です。アジャイルでは各スプリントにセキュリティ要件（アビューザーストーリーやセキュリティの Definition of Done）を組み込みます。

### 成熟度モデル (maturity model)

組織の開発プロセスがどれだけ**一貫していて予測可能か**を測る物差しです。

| CMMI レベル | 名称 | 状態 |
|---|---|---|
| 1 | 初期 (Initial) | 場当たり的・属人的 |
| 2 | 管理された (Managed) | プロジェクト単位で管理 |
| 3 | 定義された (Defined) | 組織標準のプロセスが文書化 |
| 4 | 定量的に管理された (Quantitatively Managed) | 指標で定量管理 |
| 5 | 最適化している (Optimizing) | 継続的なプロセス改善 |

セキュリティに特化した成熟度モデルとしては **OWASP SAMM (Software Assurance Maturity Model)** があります。プロセス改善の進め方のモデルには IDEAL（開始→診断→確立→行動→学習）があります。

💡 コツ: 成熟度モデルは「個々の製品の品質」ではなく「**プロセスの成熟度・予測可能性**」の指標です。レベルの順番（特にレベル4＝定量的管理）は並べ替えで問われます。

### 確認問題

**問1.** 規制当局への提出文書が多く、要件が最初から明確に固まっており、途中変更がほとんど見込まれない基幹システムの開発を外部委託します。最も適した (MOST suitable) 開発手法はどれでしょうか？

1. スクラム
2. ウォーターフォール
3. エクストリームプログラミング
4. カンバン

<details><summary>答えと解説</summary>

正解: **2**

要件が明確・変更が少ない・文書と承認の厳格さが求められる案件には、工程順に進み各工程の成果物と承認が明確なウォーターフォールが適しています。スクラム・XP・カンバンはいずれもアジャイル系で、要件が流動的な場合に強みを発揮します。「アジャイルが新しい＝常に正しい」と思い込ませるひっかけに注意してください。CISSP は『状況に最適な手法』を問います。

</details>

**問2.** スパイラルモデルの最大の特徴として正しいものはどれでしょうか？

1. 各反復の繰り返しのたびにリスク評価を行う
2. すべての工程を一度だけ順番に実施する
3. ドキュメントを作成せず動くソフトウェアだけを重視する
4. 開発と運用を統合して自動デプロイを行う

<details><summary>答えと解説</summary>

正解: **1**

スパイラルモデルは計画→リスク分析→エンジニアリング→評価のサイクルを繰り返すメタモデルで、各反復の先頭でリスク評価を行うのが最大の特徴です。「一度だけ順番に」はウォーターフォール、「動くソフトウェア重視」はアジャイルの価値観、「開発と運用の統合」は DevOps の説明です。リスクという単語とスパイラルを結びつけて覚えましょう。

</details>

**問3.** アジャイルソフトウェア開発宣言の「4つの価値」に含まれるものはどれでしょうか？

1. 計画に従うことよりも契約交渉を重視する
2. 個人と対話よりもプロセスとツールを重視する
3. 包括的なドキュメントよりも動くソフトウェアを重視する
4. 変化への対応よりも網羅的なテストを重視する

<details><summary>答えと解説</summary>

正解: **3**

4つの価値は「個人と対話」「動くソフトウェア」「顧客との協調」「変化への対応」を、それぞれ「プロセスとツール」「包括的なドキュメント」「契約交渉」「計画に従うこと」よりも重視する、という内容です。他の選択肢はいずれも価値の左右を入れ替えた典型的なひっかけです。どちらを「より重視」するのかの向きまで正確に覚えてください。

</details>

**問4.** CMMI で、プロセスを指標にもとづいて定量的に管理している組織はどのレベルに該当するでしょうか？

1. レベル2（管理された）
2. レベル3（定義された）
3. レベル5（最適化している）
4. レベル4（定量的に管理された）

<details><summary>答えと解説</summary>

正解: **4**

レベル4は Quantitatively Managed（定量的に管理された）で、測定指標によるプロセス管理が定着した状態です。レベル2はプロジェクト単位の管理、レベル3は組織標準プロセスの文書化・定着、レベル5は継続的改善（最適化）の段階です。「定量」という言葉からレベル4を即答できるようにし、5段階の順序（初期→管理→定義→定量管理→最適化）も並べ替え問題に備えて覚えましょう。

</details>

**問5.** 経営陣が開発部門に CMMI 評価の導入を指示しました。成熟度モデルの導入によって組織が得られるものとして最も適切 (BEST) な説明はどれでしょうか？

1. すべての成果物から脆弱性が排除されることが保証される
2. 開発プロセスの一貫性と予測可能性が高まり、改善の道筋が得られる
3. 開発者個人のコーディング能力が自動的に向上する
4. 外部監査が不要になる

<details><summary>答えと解説</summary>

正解: **2**

成熟度モデルが測るのは「プロセス」の成熟度です。レベルが上がるほどプロセスが一貫し、結果が予測可能になり、次に改善すべき領域も明確になります。脆弱性ゼロの保証や個人スキルの自動向上は得られませんし、監査が不要になることもありません。『成熟度が高い＝製品が無欠陥』と飛躍させる選択肢が典型的なひっかけです。

</details>

## 3. 開発の統制と環境分離（職務分掌・エスクロー・リポジトリ保護）

### 環境の分離と職務分掌

開発の統制で最も問われるのが **環境分離** です。一般に「開発 (development) → テスト (test) → ステージング (staging) → 本番 (production)」と環境を分け、コードは変更管理プロセスを通じてのみ昇格させます。

- **開発者は本番環境に直接アクセスしない**のが原則です。自分の書いたコードを自分で本番に反映できる状態は、職務分掌 (separation of duties) 違反であり、不正や事故の温床になります
- **本番データをテストに使わない**のも原則です。使う必要がある場合はマスキング・擬名化、または合成データ (synthetic data) を使います

### コードリポジトリの保護

ソースコードは重要資産です。リポジトリにはアクセス制御と変更履歴（誰がいつ何を変えたか＝説明責任）が必要で、**API キーやパスワードなどのシークレットをコードにコミットしない**ことが鉄則です。万一コミットしてしまった場合は、履歴から消すことよりも**まず当該シークレットの無効化・ローテーション**が先です（履歴を消しても既に漏えいした可能性は消えないため）。

### ソフトウェアエスクロー (software escrow)

ベンダー製ソフトのソースコードを**中立な第三者に預託**し、ベンダーの倒産やサポート打ち切りの際に顧客がソースコードを入手できるようにする契約です。「ベンダーが倒産したら保守できない」というリスクへの対策として頻出です。

### セキュアコーディング標準

組織としてコーディング標準（入力検証、エラー処理、ログ、禁止 API など）を定め、**教育とコードレビュー・CI のゲートで定着**させます。文書を作って配るだけでは統制になりません。

💡 コツ: 「開発者が本番にアクセスできる」「本番データでテストしている」というシナリオが出たら、まず職務分掌・データ保護の違反を疑いましょう。利便性を理由にした例外は CISSP 的には誤答です。

### 確認問題

**問1.** 監査で「開発者が自分の書いたコードを自分の判断で本番環境へ直接デプロイできる」ことが指摘されました。この状態の最も本質的な問題はどれでしょうか？

1. デプロイの作業時間が長くなる
2. 職務分掌が確保されておらず、不正や誤りを第三者が検知できない
3. 開発者の負担が増えて離職率が上がる
4. 本番環境のライセンス数が不足する

<details><summary>答えと解説</summary>

正解: **2**

開発と本番反映を同一人物が完結できる状態は職務分掌 (separation of duties) の欠如です。悪意あるコードの混入や誤った変更を、承認・レビューという第三者のチェックで止められません。対策は環境分離と変更管理プロセス経由のデプロイです。作業時間・離職率・ライセンスはセキュリティ統制の論点ではありません。「便利だから」は CISSP では理由になりません。

</details>

**問2.** 品質保証チームが「本番と同じデータでないと十分なテストができない」と主張し、顧客の個人情報を含む本番データベースのコピーをテスト環境に取り込もうとしています。最も適切 (BEST) な対応はどれでしょうか？

1. マスキングした複製データまたは合成データを提供する
2. テスト環境にも本番と同じファイアウォールを設置して許可する
3. テスト期間中のみ本番データの使用を口頭で許可する
4. テスト担当者全員に NDA を署名させて許可する

<details><summary>答えと解説</summary>

正解: **1**

テスト環境は本番より統制が弱いのが普通で、個人情報をそのまま持ち込むと漏えいリスクと規制違反（目的外利用）につながります。マスキング・擬名化した複製や合成データなら、データの形を保ったままリスクを下げられます。ファイアウォール追加や NDA は補助にはなっても生データ持ち込みのリスクを解消せず、口頭許可は統制として成立しません。『技術対策を足せば生データでもよい』と思わせるひっかけです。

</details>

**問3.** 重要業務システムを小規模なベンダーのパッケージ製品で構築します。「ベンダーが倒産すると保守できなくなる」というリスクへの対策として最も適切なのはどれでしょうか？

1. ベンダーの財務情報を毎年確認する
2. 製品のバイナリを自社でバックアップする
3. ソフトウェアエスクロー契約を締結する
4. サイバー保険に加入する

<details><summary>答えと解説</summary>

正解: **3**

ソフトウェアエスクロー (software escrow) は、ソースコードを中立な第三者に預託し、倒産など所定の条件でユーザー企業が入手できるようにする契約で、このリスクへの直接の対策です。財務確認はリスクの早期発見にはなっても発生時の対策になりません。バイナリのバックアップではソースコードがないため保守・改修ができず、保険は金銭補償のみで保守継続は実現しません。

</details>

**問4.** 開発者が誤ってクラウドサービスの API キーを公開リポジトリにコミットしてしまいました。最初に (FIRST) 行うべき対応はどれでしょうか？

1. コミット履歴を書き換えてキーを削除する
2. 該当開発者にセキュア開発研修を受講させる
3. リポジトリを非公開に変更する
4. 該当する API キーを直ちに無効化・ローテーションする

<details><summary>答えと解説</summary>

正解: **4**

公開された時点でキーは漏えいした前提で考えます。履歴の削除やリポジトリの非公開化を先にしても、既にクローラーや第三者が取得した可能性は消えません。したがって最初にやるべきはキー自体の無効化・ローテーションで、漏えいした認証情報を使えなくすることです。履歴削除・非公開化・再発防止の研修はその後に行う対応です。「FIRST」問題では被害を直接止める行動を選びましょう。

**問5.** セキュアコーディング標準を策定しました。開発組織に定着させる方法として最も効果的 (MOST effective) なのはどれでしょうか？

1. 標準文書を社内ポータルに掲載して全員に周知メールを送る
2. 違反した開発者への罰則規定を就業規則に追加する
3. 開発者教育と、コードレビュー・CI の自動チェックに標準を組み込む
4. 年1回の内部監査で標準の存在を確認する

<details><summary>答えと解説</summary>

正解: **3**

統制は「書く」だけでなく「日々のプロセスに組み込んで実施される」ことで初めて機能します。教育で理解させ、コードレビューと CI の自動チェックをゲートにすれば、標準違反はマージ前に検出され、継続的に定着します。文書掲載や周知メールだけでは行動が変わらず、罰則は萎縮を招くだけで実装を支援しません。年1回の監査では日々の違反を防げません。

</details>
