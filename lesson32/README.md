# 第32章 シナリオドリル②（D5〜D8横断・BEST/MOST問題）

D5〜D8（IAM・評価とテスト・運用・ソフトウェア開発）を横断するシナリオドリルです。全問が「あなたは〜です」で始まる状況判断問題で、BEST/MOST/FIRST/LEAST を問います。知識の暗記ではなく「マネジメントとしてどの順序で・何を優先して動くか」を体に染み込ませましょう。

## 1. D5+D6ドリル: アイデンティティと評価の判断

### この回のテーマ

D5（IAM）と D6（セキュリティの評価とテスト）の論点を、本試験そっくりのシナリオ形式で演習します。全問が **BEST / MOST / FIRST** 形式です。

### 解き方のコツ

- **リスクの大きいところから着手** — MFA もアクセスレビューも、まず特権アカウント (privileged account) が最優先です
- **順序の鉄則を思い出す** — 退職処理は「削除より無効化が先」、ペネトレーションテストは「書面の許可が先」のように、CISSP には決まった順序があります
- **証拠と文書を重視** — 監査・評価の文脈では「文書化して経営陣の承認を得る」が正解になりやすい選択肢です

4つの選択肢はどれも「やってもよさそう」に見えます。**「最初に」「最も」と聞かれたら、人命→事業→資産の優先順位と、プロセスの正しい順序で1つに絞り込みましょう。**

💡 コツ: 「技術的に正しい」選択肢がひっかけです。マネジメントの帽子をかぶって選んでください。

### 確認問題

**問1.** あなたはセキュリティ管理者です。限られた予算で多要素認証 (MFA) を段階的に導入することになりました。最初に (FIRST) 適用すべき対象はどれですか？

1. 全従業員のメールアカウント
2. リモートアクセス VPN の利用者
3. ドメイン管理者などの特権アカウント
4. 経営層のアカウント

<details><summary>答えと解説</summary>

正解: **3**

段階導入では「侵害されたときの影響が最も大きいアカウント」から守るのが鉄則です。特権アカウント (privileged account) が奪われると環境全体が危険にさらされるため、最優先で MFA を適用します。VPN 利用者や経営層も重要ですが影響範囲は特権アカウントに及びません。全従業員への一斉展開は理想ですが「限られた予算で段階的に」という条件に合いません。ひっかけ: 「経営層=偉い人が先」と考えがちですが、試験では役職ではなくリスクの大きさで優先順位を決めます。

</details>

**問2.** あなたは IT 管理者です。ある従業員が不正行為により即日懲戒解雇されることになり、人事部門から連絡を受けました。その従業員のアカウントに対して最初に (FIRST) 行うべき処置はどれですか？

1. アカウントを直ちに無効化する
2. アカウントを直ちに削除する
3. 本人のデータを別媒体へ移してから削除する
4. 退職手続きの完了を待ってから処理する

<details><summary>答えと解説</summary>

正解: **1**

懲戒解雇では報復行為のリスクがあるため、アカウントは「直ちに無効化 (disable)」します。削除ではなく無効化なのは、ファイルの所有権・暗号鍵・調査に必要な証跡を保全するためです（削除は後から必要に応じて）。データ移行は無効化の後で安全に行えます。手続き完了を待つのは最悪で、その間に持ち出しや破壊が起こり得ます。ひっかけ: 「削除」は一見徹底して見えますが、証拠とデータを失うため CISSP では誤答の定番です。

</details>

**問3.** あなたはセキュリティマネージャーです。定期アクセスレビューで、10年間に複数の部署を異動してきた従業員が、過去の部署の権限をすべて保持したままであることが判明しました (privilege creep)。BEST な対応はどれですか？

1. 全権限を直ちに剥奪し、本人に再申請させる
2. 現在の職務に必要な権限だけを残すように見直す
3. 本人と上司に事情を確認するまで何もしない
4. 次回の定期レビューで再確認する旨を記録して終了する

<details><summary>答えと解説</summary>

正解: **2**

最小権限 (least privilege) の原則に従い、「現在の職務に必要な権限」へ是正するのが BEST です。全剥奪は業務を止めてしまい過剰反応です（本人に不正の兆候があるわけではありません）。確認まで放置や記録のみは、発見したリスクを放置することになりデューケア (due care) に反します。ひっかけ: 「直ちに全部剥奪」は強そうに見えますが、ビジネスへの影響を考えないセキュリティは CISSP では正解になりません。

</details>

**問4.** あなたはセキュリティアーキテクトです。自社の従業員が、社内の IdP で認証したうえで複数の外部 SaaS をブラウザから SSO で使えるようにしたいと考えています。この要件に BEST なのはどれですか？

1. OAuth 2.0 を単体で利用する
2. LDAP を外部公開して SaaS から直接認証させる
3. Kerberos チケットを SaaS と共有する
4. SAML によるフェデレーションを構成する

<details><summary>答えと解説</summary>

正解: **4**

企業 IdP と外部 SaaS のブラウザベース SSO は SAML フェデレーションの典型的なユースケースです。OAuth 2.0 は「認可」のフレームワークであり、単体では認証を提供しません（超頻出のひっかけ）。LDAP の外部公開は認証情報を危険にさらす悪手です。Kerberos は社内ネットワーク向きで、インターネット越しの SaaS 連携には適しません。ひっかけ: OAuth/OIDC/SAML の使い分けは頻出です。「認可は OAuth、ブラウザ SSO の認証連携は SAML（または OIDC）」と整理しましょう。

</details>

**問5.** あなたはセキュリティコンサルタントです。顧客企業から本番環境へのペネトレーションテストを依頼されました。テストを開始する前に最初に (FIRST) 行うべきことはどれですか？

1. スキャンツールと攻撃環境を準備する
2. テスト範囲と交戦規定を定めた書面の許可を経営陣から得る
3. 対象システムのバックアップを取得する
4. 検知を避けるため IDS/IPS の無効化を依頼する

<details><summary>答えと解説</summary>

正解: **2**

許可のないペネトレーションテストは不正アクセスそのものです。テスト範囲・時間帯・手法・緊急連絡先を定めた交戦規定 (rules of engagement) を含む書面の許可を得ることが、何よりも先に必要です。ツール準備やバックアップはその後の話です。IDS/IPS の無効化は「検知・対応能力も含めて評価する」というテストの目的を損ない、通常は行いません。ひっかけ: 技術的準備から入りたくなりますが、CISSP では「法的・契約的な保護が FIRST」です。

</details>

**問6.** あなたは脆弱性管理の責任者です。全社スキャンの結果、数千件の脆弱性が検出されました。修正の優先順位を決める基準として MOST 適切なのはどれですか？

1. CVSS の基本値が高い順に対応する
2. 修正が容易なものから対応する
3. 資産の重要度と悪用可能性を組み合わせて優先度を決める
4. 検出件数が多いシステムから対応する

<details><summary>答えと解説</summary>

正解: **3**

脆弱性のトリアージは「その資産がどれだけ重要か（ビジネス影響）」と「実際に悪用されやすいか（公開エクスプロイトの有無、外部露出）」を組み合わせたリスクベースで行うのが MOST 適切です。CVSS 基本値だけでは自社環境の文脈（資産価値・補償コントロール）が反映されません。容易なものから着手するのは達成感はあっても重大リスクを放置します。件数の多さはリスクの大きさと一致しません。ひっかけ: 「CVSS 順」は一見正しそうですが、環境評価を伴わない機械的対応は次点止まりです。

</details>

**問7.** あなたは調達担当のセキュリティ評価者です。重要データを預けるクラウドベンダーについて、セキュリティ統制が一定期間にわたり有効に運用されていた証拠を確認したいと考えています。要求すべき報告書として BEST なのはどれですか？

1. SOC 1 Type Ⅰ
2. SOC 2 Type Ⅰ
3. SOC 2 Type Ⅱ
4. SOC 3

<details><summary>答えと解説</summary>

正解: **3**

セキュリティ等の Trust サービス基準を対象とするのは SOC 2、そして「一定期間の運用有効性」を検証するのは Type Ⅱ です。SOC 1 は財務報告に係る統制が対象で目的が異なります。SOC 2 Type Ⅰ は「ある時点の設計」の評価にとどまり、運用の証拠になりません。SOC 3 は一般公開用の要約で、評価に必要な詳細を含みません。ひっかけ: 「Type Ⅰ=時点・設計、Type Ⅱ=期間・運用」の対比は超頻出です。迷ったら『期間にわたり』という言葉を探しましょう。

</details>

**問8.** あなたは CISO です。外部監査で重要な統制の不備を指摘されましたが、是正には多額の費用がかかる一方、分析の結果リスクは小さいと判断しました。BEST な対応はどれですか？

1. リスク受容を文書化し、経営陣の承認を得る
2. 監査人に指摘の撤回を求めて交渉する
3. 費用に関係なく直ちに是正する
4. 対応を文書化せず、次回監査まで様子を見る

<details><summary>答えと解説</summary>

正解: **1**

対策費用がリスク低減効果を上回る場合、リスク受容 (risk acceptance) は正当な選択肢です。ただし必ず文書化し、受容の決定は経営陣が行う必要があります（残留リスクのオーナーは経営陣）。監査人への撤回要求は独立性への不当な干渉です。費用対効果を無視した是正は経営資源の浪費で、CISSP 的には不正解です。文書化しない放置は受容ではなく「無視」であり、デューケア違反になります。ひっかけ: 「監査指摘=必ず是正」ではありません。リスクベースの判断と文書化・承認がセットなら受容も正解になります。

</details>

## 2. D7ドリル: 運用とインシデントの判断

### この回のテーマ

D7（セキュリティの運用）のシナリオ演習です。インシデント対応・フォレンジック・災害復旧 (DR)・変更管理を横断して、**初動の順序**と**優先順位の判断**を問います。

### 解き方のコツ

- **インシデントの初動は封じ込め** — 被害の拡大防止（隔離）が、駆除や報告よりも先です
- **証拠は壊れやすい順に集める** — 揮発性の順序 (order of volatility) を思い出しましょう。メモリはディスクより先です
- **復旧要件は BIA から逆算** — RPO が短いほど継続的なデータ転送が必要になります
- **人命は常に最優先** — 物理的な脅威や強要 (duress) のシナリオでは、資産よりも人の安全を選びます

💡 コツ: 「犯人探し」「懲戒」「とにかく全部止める」といった感情的・極端な選択肢は、ほぼ確実にひっかけです。プロセスに沿った冷静な一手を選びましょう。

### 確認問題

**問1.** あなたはセキュリティ運用の担当者です。SIEM のアラートから、ファイルサーバー1台がマルウェアに感染していることが確認できました。最初に (FIRST) 行うべき対応はどれですか？

1. 直ちにマルウェアを駆除して業務を再開する
2. 感染サーバーをネットワークから隔離する
3. 経営陣と規制当局へ報告する
4. 根本原因の調査を開始する

<details><summary>答えと解説</summary>

正解: **2**

インシデント対応の初動は「被害の拡大防止=封じ込め」です。感染サーバーを隔離して横展開 (lateral movement) を止めることが最優先です。駆除（根絶）を先にすると、隔離前に感染が広がるうえ、証拠も失われます。報告は重要ですが封じ込めの後、根本原因調査はさらに後の段階です。ひっかけ: CISSP の7段階（検知→対応→軽減→報告→復旧→修復→教訓）では、報告より先に封じ込め・軽減が来ることを覚えておきましょう。

</details>

**問2.** あなたはインシデント対応チームのリーダーです。ランサムウェアにより複数の端末でファイルの暗号化が進行中です。この状況で BEST な初動はどれですか？

1. 身代金の支払い手続きを準備する
2. すべてのサーバーの電源を直ちに落とす
3. 全従業員へ注意喚起メールを送る
4. 感染セグメントを隔離し、オフラインバックアップの無事を確認する

<details><summary>答えと解説</summary>

正解: **4**

進行中のランサムウェアでは「感染範囲の隔離（封じ込め）」と「復旧手段=バックアップの保全確認」を並行で行うのが BEST です。ランサムウェアはバックアップも狙うため、オフライン/イミュータブルバックアップの無事確認が復旧の生命線です。身代金の支払いは復号の保証がなく原則回避します。全サーバーの電源断は未感染システムまで止め、メモリ上の証拠も失う過剰対応です。注意喚起は有効ですが拡大防止の決め手にはなりません。ひっかけ: 「全部止める」は安全に見えて、事業影響と証拠喪失の面で誤りです。

</details>

**問3.** あなたは社内調査の担当者です。不正行為の疑いで従業員の PC を押収し、将来の訴訟で証拠として使う可能性があります。証拠能力を維持するために MOST 重要なのはどれですか？

1. チェーンオブカストディ（管理の連鎖）を途切れなく記録する
2. できるだけ早く PC を起動して内容を分析する
3. 本人から口頭で同意を得る
4. パスワードを解除して全ファイルを閲覧する

<details><summary>答えと解説</summary>

正解: **1**

法廷で証拠能力 (admissibility) を保つ鍵は、「誰が・いつ・どこで・何を扱ったか」を押収から提出まで途切れなく記録するチェーンオブカストディです。これが欠けると改ざんの疑いを排除できず証拠として使えません。押収した原本をそのまま起動・閲覧するのは証拠を改変する行為で厳禁です（ライトブロッカーでイメージを取得し、コピーを分析します）。口頭の同意は記録に残らず不十分です。ひっかけ: 「早く分析」はスピード感があって良さそうですが、保全より先に分析はあり得ません。

</details>

**問4.** あなたはフォレンジック調査員です。稼働中のサーバーから証拠を収集します。揮発性の順序 (order of volatility) に従うと、最初に (FIRST) 収集すべきものはどれですか？

1. ハードディスクのフルイメージ
2. アーカイブ済みのバックアップテープ
3. 実行中プロセスとメモリ (RAM) の内容
4. 監査ログの印刷物

<details><summary>答えと解説</summary>

正解: **3**

証拠は「失われやすいものから」収集します。順序は、CPU レジスタ/キャッシュ→メモリ・実行中プロセス・ネットワーク接続状態→一時ファイル→ディスク→バックアップ→印刷物です。選択肢の中で最も揮発性が高いのはメモリの内容で、電源断で消滅します。ディスクイメージやバックアップ、印刷物は電源を切っても残るため後回しにできます。ひっかけ: 「まずディスクイメージ」と覚えている人が多いですが、ライブフォレンジックではメモリが先です。

</details>

**問5.** あなたは DR 計画の責任者です。本番業務に影響を与えずに、代替サイトを実際に起動して復旧処理を検証したいと考えています。BEST なテスト方式はどれですか？

1. 構造化ウォークスルー（机上演習）
2. シミュレーションテスト
3. パラレルテスト
4. フルインタラプションテスト

<details><summary>答えと解説</summary>

正解: **3**

パラレルテストは、本番を動かしたまま代替サイトを並行稼働させて復旧手順を検証する方式で、「本番に影響なし+実際に起動して検証」という要件に合致します。机上演習やシミュレーションは実際にシステムを起動しないため検証が不十分です。フルインタラプションは本番を実際に切り替えるため最も確実ですが、業務停止のリスクがあり「影響を与えず」という条件に反します。ひっかけ: テストの5段階（読み合わせ→ウォークスルー→シミュレーション→パラレル→フルインタラプション）は強度順に並べて覚えましょう。

</details>

**問6.** あなたはバックアップ戦略の設計者です。基幹データベースの RPO（目標復旧時点）が 15 分と定められました。BEST な方式はどれですか？

1. リモートジャーナリングによる継続的なトランザクション転送
2. 日次フルバックアップ
3. 週次フル+日次増分バックアップ
4. 電子ボールティングによる日次のバッチ転送

<details><summary>答えと解説</summary>

正解: **1**

RPO 15分とは「失ってよいデータが最大15分ぶん」という意味です。日次や週次のバックアップでは最大24時間〜のデータを失うため要件を満たせません。リモートジャーナリングはトランザクションログをほぼリアルタイムで遠隔地へ転送し続けるため、15分以内のデータ損失に抑えられます。電子ボールティングはバッチ転送のため間隔が空きます。ひっかけ: RPO はバックアップの「頻度」を決め、RTO は復旧の「速さ」を決めます。どちらから逆算するかを取り違えないようにしましょう。

</details>

**問7.** あなたは運用マネージャーです。管理者の1人が変更管理プロセスを通さずに本番ファイアウォールの設定を変更し、大規模な通信障害が発生しました。サービス復旧後に MOST 適切な対応はどれですか？

1. その管理者を直ちに懲戒解雇する
2. 根本原因を分析し、変更管理プロセスの徹底と教育を行う
3. 全管理者からファイアウォールの変更権限を剥奪する
4. 再発していないことを確認し、記録せずに終了する

<details><summary>答えと解説</summary>

正解: **2**

インシデント後は個人攻撃ではなく「プロセスの改善」に焦点を当てるのがマネジメントの正解です。なぜ無断変更が可能だったのか（技術的統制の不足・教育不足・緊急変更手順の不備）を分析し、変更管理の徹底・教育・必要なら承認の技術的強制を行います。即時解雇は過剰で、組織として学ぶ機会を失います。全員からの権限剥奪は運用を止める過剰反応です。記録しない終了は教訓 (lessons learned) の放棄です。ひっかけ: 「犯人を罰する」選択肢は感情的には正しそうですが、CISSP では常にプロセス改善が優先です。

</details>

**問8.** あなたは物理セキュリティの設計者です。深夜勤務の警備員や運用担当者が、武器を持った侵入者に操作や解錠を強要されるリスクに備えたいと考えています。BEST な設計はどれですか？

1. 強要されても要求を拒否するよう訓練する
2. 入口を遠隔施錠して侵入者を閉じ込める
3. 警報を鳴らして直ちに対峙させる
4. 要求には従いながら、強要コード (duress code) で無言の通報を行えるようにする

<details><summary>答えと解説</summary>

正解: **4**

人命は常に最優先です。武器を持つ相手への抵抗・対峙・閉じ込めは従業員を危険にさらすため不適切です。BEST は、表向きは要求に従って身の安全を確保しつつ、通常と異なる PIN や合言葉（duress code）で警備会社や警察へ無言の通報が届く仕組みです。資産やシステムは後から取り戻せますが、人の命は取り戻せません。ひっかけ: 「セキュリティを守るために拒否」は勇ましく見えますが、CISSP では人命より優先されるものはありません。

</details>

## 3. D8ドリル: 開発セキュリティの判断

### この回のテーマ

D8（ソフトウェア開発セキュリティ）のシナリオ演習です。開発現場で起こりがちな「利便性 vs 統制」の対立を、マネジメント視点でさばく練習をします。

### 解き方のコツ

- **職務分掌と環境分離は譲らない** — 開発者の本番アクセスや本番データのテスト利用は、便利でも原則 NO。ただし「拒否して終わり」ではなく**代替手段を提供する**選択肢が BEST になります
- **漏れたシークレットは「まず無効化」** — 履歴の掃除や再発防止より先に、いま使える鍵を止めます
- **リリース判断はリスクベース** — 延期か続行かを技術者が独断せず、リスク評価をビジネスオーナー・経営陣に示して判断させるのが CISSP 流です

💡 コツ: 「直ちに禁止」「無条件に許可」のような両極端は大抵ひっかけです。統制を守りつつビジネスを前に進める中庸の選択肢を探しましょう。

### 確認問題

**問1.** あなたはセキュリティマネージャーです。開発チームから「テストの精度を上げるため、本番の顧客データをそのままテスト環境で使いたい」と要望がありました。BEST な対応はどれですか？

1. NDA への署名を条件に本番データの利用を許可する
2. 読み取り専用アカウントで本番データベースへの接続を許可する
3. マスキングした複製データまたは合成データを提供する
4. テスト要件を縮小してデータ利用自体を不要にする

<details><summary>答えと解説</summary>

正解: **3**

テスト環境は本番より統制が緩いため、生の顧客データを置くことは漏えいリスクとプライバシー規制違反につながります。BEST は、形式や分布を保ったままマスキング（または合成データ生成）したデータを提供し、テスト精度と保護を両立させることです。NDA は人の行動を縛るだけでデータ自体を守りません。読み取り専用でも本番データが開発者の目に触れる問題は残ります。テスト要件の縮小は品質を犠牲にする本末転倒です。ひっかけ: 「拒否」ではなく「安全な代替を提供する」選択肢が CISSP の正解パターンです。

</details>

**問2.** あなたは DevSecOps の推進担当です。コーディングの段階で、できるだけ早期に脆弱性を発見して開発者にフィードバックしたいと考えています。MOST 適切なのはどれですか？

1. ソースコードを静的に解析する SAST を CI パイプラインに組み込む
2. ステージング環境への DAST スキャンをリリース前に実施する
3. 四半期ごとにペネトレーションテストを実施する
4. 本番環境に RASP を導入する

<details><summary>答えと解説</summary>

正解: **1**

「コーディング段階で早期に」という条件に合うのは SAST（静的解析）です。ソースコードを実行せずに解析でき、コミットのたびに CI で自動実行して開発者へ即座にフィードバックできます（シフトレフトの実践）。DAST は動作するアプリが必要でテスト段階以降、ペネトレはさらに後かつ頻度が低く、RASP は本番の実行時保護であり「早期発見」ではありません。ひっかけ: SAST=ソース・早期、DAST=実行中・後期の対比は超頻出です。問題文の「どの段階か」を必ず確認しましょう。

</details>

**問3.** あなたはセキュリティエンジニアです。社内の Git リポジトリのコードに、クラウドサービスの API キーがハードコードされてコミットされているのを発見しました。最初に (FIRST) 行うべきことはどれですか？

1. コミット履歴からキーを完全に削除する
2. 開発者にセキュア開発研修を受けさせる
3. リポジトリを非公開に変更する
4. 流出したキーを直ちに無効化してローテーションする

<details><summary>答えと解説</summary>

正解: **4**

コミットされた時点でそのキーは「漏えいした」とみなします。履歴の削除やリポジトリの非公開化をしても、既にクローンやキャッシュで複製されている可能性を消せません。したがって FIRST はキーの無効化とローテーション（新しいキーへの差し替え）で、攻撃者が使える窓を閉じることです。履歴の掃除・シークレット管理の導入・研修はその後の是正・再発防止策です。ひっかけ: 「履歴から削除」は根本対応に見えますが、漏れた鍵自体は生きたままです。『鍵を止めるのが先』と覚えましょう。

</details>

**問4.** あなたは開発チームのセキュリティ担当です。SCA ツールが、製品で使用中の OSS ライブラリに悪用コードが公開された Critical の脆弱性を検出しました。BEST な対応はどれですか？

1. そのライブラリの使用を直ちに停止し、リリースを中止する
2. 修正版へのアップデートを検証環境でテストし、速やかに適用する
3. 内部システムからの利用のみなので対応不要と記録する
4. ライブラリのソースを自社で修正し、独自パッチとして保守する

<details><summary>答えと解説</summary>

正解: **2**

悪用コードが公開された Critical 脆弱性は放置できません。標準的な対応は、提供されている修正版へ検証環境でテストのうえ速やかに更新することです（パッチ管理と同じ「テスト→適用」の順序）。使用停止・リリース中止は依存の置き換えコストが大きく、修正版があるなら過剰です。「内部だから不要」は内部脅威と多層防御を無視しています。独自パッチは保守負債となり、以後の更新から取り残される悪手です。ひっかけ: 極端な停止でも放置でもなく、「テストして更新」という王道が正解です。

</details>

**問5.** あなたはセキュリティマネージャーです。開発者から「本番障害の調査を素早く行うため、本番環境への常時アクセス権がほしい」と要望されました。BEST な対応はどれですか？

1. 調査の迅速化はビジネス上有益なので常時アクセスを許可する
2. 職務分掌を保ちつつ、必要時のみ承認つきで一時的な特権を付与する (JIT アクセス)
3. 読み取り専用であれば常時アクセスを許可する
4. 上長の承認を条件に常時アクセスを許可する

<details><summary>答えと解説</summary>

正解: **2**

開発者の本番常時アクセスは職務分掌 (separation of duties) に反し、不正変更やデータ漏えいのリスクを生みます。一方で障害対応のニーズは正当なので、BEST は「必要なとき・必要な時間だけ・承認と記録つき」で付与するジャストインタイム (JIT) の特権管理です。読み取り専用でも顧客データ閲覧の問題が残り、常時である必要もありません。上長承認があっても「常時」の構造的リスクは消えません。ひっかけ: 「拒否」か「許可」の二択ではなく、統制された第三の道 (PAM/JIT) が用意されていたらそれが正解です。

</details>

**問6.** あなたはアプリケーションセキュリティの担当者です。Web アプリへの SQL インジェクション対策として BEST なのはどれですか？

1. WAF を導入して攻撃パターンを遮断する
2. 既知の攻撃文字列をブラックリストで入力検証する
3. 詳細なエラーメッセージを画面に表示しない
4. パラメータ化クエリ（プリペアドステートメント）を使用する

<details><summary>答えと解説</summary>

正解: **4**

SQL インジェクションの根本対策は、SQL 文とデータを分離するパラメータ化クエリです。入力がコードとして解釈されなくなるため、原因そのものを断てます。WAF は有効な多層防御ですが回避手法が存在する「緩和策」であり根本対策ではありません。ブラックリスト検証はすり抜けが起きやすく、ホワイトリスト方式に劣ります。エラーメッセージの抑制は情報漏えいを減らすだけで注入自体は防げません。ひっかけ: 「WAF 導入」はもっともらしい次点です。『根本対策か、緩和策か』を見分けるのが D8 の定番論点です。

</details>

**問7.** あなたはセキュリティ責任者です。重要製品のリリース2日前に、中程度の深刻度の脆弱性が新たに発見されました。修正にはリリース延期が必要です。BEST な進め方はどれですか？

1. セキュリティ最優先の原則に基づき、独断でリリースを延期する
2. リスク評価の結果と選択肢を示し、ビジネスオーナー・経営陣とともに判断する
3. 計画どおりリリースし、脆弱性のことは報告しない
4. 開発チームの判断に任せて修正を急がせる

<details><summary>答えと解説</summary>

正解: **2**

リリース延期はビジネス上の重大な意思決定であり、セキュリティ担当が独断すべきではありません。BEST は、脆弱性のリスク（悪用可能性・影響）、補償コントロールの選択肢（WAF での仮想パッチ、リリース直後の修正版計画など）を評価して提示し、リスクを負うビジネスオーナー・経営陣と一緒に判断することです。報告しないリリースは論外（デューケア違反）、開発チーム任せも説明責任の放棄です。ひっかけ: 「セキュリティ最優先で延期」は正義に見えますが、CISSP ではリスク情報を提供して経営に判断させるのがセキュリティ専門家の役割です。

</details>

**問8.** あなたは調達担当です。小規模なベンダーが開発した業務システムを長期利用する契約を結びますが、そのベンダーの倒産や事業撤退が心配です。この懸念への対策として BEST なのはどれですか？

1. ソースコードのエスクロー契約を締結する
2. SLA に高額の違約金条項を盛り込む
3. サイバー保険に加入する
4. 同じシステムを自社でも並行開発しておく

<details><summary>答えと解説</summary>

正解: **1**

ソフトウェアエスクローは、ソースコードを中立の第三者に預託し、ベンダーの倒産・保守放棄など所定の条件で顧客に開示される契約です。ベンダー消滅後も自社でシステムを保守し続けられるため、この懸念に対する定番の BEST 対策です。違約金は倒産した相手からは回収できません。保険は金銭補填のみでシステムの保守継続はできません。並行開発はコストが非現実的です。ひっかけ: エスクローは「ベンダー倒産が心配」というキーワードとセットで出る頻出論点です。

</details>
