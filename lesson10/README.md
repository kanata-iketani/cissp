# 第10章 セキュリティ評価基準とシステム・ハードウェアの保護【D3】

「この製品はどれくらい信頼できるのか」を客観的に測る評価基準と、OS やハードウェアが自分自身を守る仕組みを学ぶ章です。コモンクライテリアのような国際標準から、保護リング・TPM・仮想化・ICS/IoT まで、D3（セキュリティアーキテクチャとエンジニアリング）の土台となる「システムを守る設計」を一気に押さえます。

## 1. セキュリティ評価基準（TCSEC・ITSEC・コモンクライテリア）

### 「この製品は信頼できる？」を測るものさし

セキュリティ製品を調達するとき、ベンダーの宣伝文句だけでは信頼できません。そこで**第三者が共通の基準で評価する**仕組みが生まれました。歴史の流れで覚えましょう。

| 基準 | 特徴 |
|---|---|
| **TCSEC**（オレンジブック・米国） | 最初期の基準。**D〜A1** のランクで機密性を中心に評価。機能と保証を一体で評価 |
| **ITSEC**（欧州） | 機能（F）と**保証（E）を分離**して評価。機密性以外（完全性・可用性）も対象に |
| **コモンクライテリア / CC**（ISO/IEC 15408・国際標準） | TCSEC と ITSEC を統合した**現在の国際標準** |

ここで出てくる2つの言葉を区別しておきましょう。

- **機能 (functionality)**: 製品が何をできるか（例: ログイン認証、ログ記録、通信の暗号化）
- **保証 (assurance)**: その機能が主張どおり正しく動くと、どれだけ確信できるか（設計書の確認、テスト、ソースコードの調査などをどこまで深くやったか）

TCSEC のランクは、上ほど厳しくなる4つの区分です。

| 区分 | 名前 | 中身の目安 |
|---|---|---|
| D | 最小限の保護 | 評価に通らなかったもの |
| C1・C2 | 任意保護 | DAC（持ち主が権限を決める方式）。C2 では利用者ごとのログイン・監査ログが必要 |
| B1・B2・B3 | 強制保護 | MAC（L09 で見たラベルによる強制アクセス制御）。B2 以降で隠れチャネルの分析なども必要 |
| A1 | 検証済み設計 | B3 と同等の機能に、数学的な形式検証を加える |

### コモンクライテリアの登場人物（超頻出）

- **TOE (Target of Evaluation)**: 評価対象となる製品・システムそのもの
- **PP (Protection Profile)**: **利用者・顧客側**が「こういうセキュリティ機能がほしい」と書く要求仕様のテンプレート（「私がほしいもの」）
- **ST (Security Target)**: **ベンダー側**が「この製品はこういうセキュリティ機能を持つ」と主張する文書（「私が提供するもの」）
- **EAL (Evaluation Assurance Level) 1〜7**: 評価の厳密さ（保証レベル）。EAL1（機能テスト）〜 EAL7（形式検証）。**数字が大きいほど「機能が多い」のではなく「検証が厳密」**という点がひっかけの定番です

| EAL | 名前 |
|---|---|
| EAL1 | 機能テスト |
| EAL2 | 構造テスト |
| EAL3 | 方法論的テストとチェック |
| EAL4 | 方法論的設計・テスト・レビュー（市販の OS などでよく見られるレベル） |
| EAL5 | 準形式的設計とテスト |
| EAL6 | 準形式的検証済み設計とテスト |
| EAL7 | 形式的検証済み設計とテスト |

**形式検証**は、設計を数式で書き、ルールどおりに動くことを数学的に証明することです。「準形式的」は数式までは使わず、決まった書式で厳密に書く段階です。

**調達の流れで並べると**、登場人物の関係がつかめます。

1. 政府機関が「ファイアウォール用 PP」を用意する（ほしい機能の要求）
2. ベンダーが「製品 FW-X v3.2 の ST」を書き、PP に適合すると主張する
3. 評価機関が、ST に書かれた構成の FW-X v3.2（これが TOE）を EAL4 で評価する
4. 合格すると認証書が出て、調達側は「PP に適合し EAL4 で評価済み」の製品から選べる

### 認証と認定の違い（頻出）

- **認証 (certification)**: システムが基準を満たすかを**技術的に評価**する行為
- **認定 (accreditation)**: その評価結果を見て、**経営層が残留リスクを受容し、運用開始を正式承認**する行為（残留リスクは対策後も残るリスク。L04 で見たとおり）。現在の NIST のリスク管理の枠組みでは、この承認を**認可 (authorization)**、承認書を ATO (Authority to Operate) と呼びます

💡 コツ: 「certification = 技術者のハンコ、accreditation = 経営者のハンコ」と覚えましょう。CISSP では「最終的にリスクを受容するのは誰か → 経営層」という視点が繰り返し問われます。

そのほか、暗号モジュール専用の評価基準として **FIPS 140**（米国。暗号モジュールのセキュリティ要件をレベル1〜4で規定。現行は FIPS 140-3）も覚えておきましょう。暗号モジュールは、暗号化の計算や鍵の保管を受け持つ部品（ソフトウェアのライブラリや専用チップ）です。レベルが上がるほど物理的な守りが強くなり、たとえばレベル2ではこじ開けた跡が残る封印（改ざん痕跡）、レベル3ではこじ開けを検知して鍵を消す仕組みが求められます。

### 確認問題

**問1.** コモンクライテリア（ISO/IEC 15408）の EAL（評価保証レベル）について、最も適切な説明はどれでしょう？

1. EAL が高いほど、製品が持つセキュリティ機能の数が多いことを示す
2. EAL が高いほど、評価・検証が厳密に行われたこと（保証の高さ）を示す
3. EAL が高いほど、製品の処理性能が高いことを示す
4. EAL7 を取得した製品には脆弱性が存在しないことが保証される

<details><summary>答えと解説</summary>

正解: **2**

EAL は「どれだけ厳密に検証されたか」という保証（assurance）のレベルで、EAL1（機能テスト）から EAL7（形式的検証）まであります。機能の多さを示すものではない点が定番のひっかけです。性能は評価対象外で、EAL7 でも「脆弱性ゼロ」の保証にはなりません（評価時点・評価範囲での保証にすぎません）。

</details>

**問2.** コモンクライテリアにおいて、顧客・利用者側が「製品に求めるセキュリティ要件」を実装非依存で記述した文書はどれでしょう？

1. ST（Security Target）
2. TOE（Target of Evaluation）
3. PP（Protection Profile）
4. EAL（Evaluation Assurance Level）

<details><summary>答えと解説</summary>

正解: **3**

PP（保護プロファイル）は顧客側の「私がほしいもの」を書いた要求仕様テンプレートです。ST はベンダー側が「この製品が提供するもの」を主張する文書、TOE は評価対象の製品そのもの、EAL は評価の厳密さのレベルです。「PP=欲しい側、ST=売る側」の対応を入れ替えるひっかけが頻出です。

</details>

**問3.** 新システムの第三者評価が完了し、いくつかの残留リスクが報告されました。この後、システムの運用開始を正式に承認する行為と、それを行うべき主体の組み合わせとして最も適切なものはどれでしょう？

1. 認定（accreditation）― 経営層（上級管理者）
2. 認証（certification）― 評価を行った技術チーム
3. 認定（accreditation）― システムを構築したベンダー
4. 認証（certification）― 情報システム部門の運用担当者

<details><summary>答えと解説</summary>

正解: **1**

認定（accreditation）は、技術評価（certification）の結果を踏まえて経営層が残留リスクを受容し、運用開始を正式承認する行為です。技術チームが行うのは評価（認証）までで、運用開始の承認はできません。ベンダーや運用担当者にはリスク受容の権限がありません。「リスクを受容できるのは経営層だけ」は CISSP 全体を貫く鉄則です。

</details>

**問4.** FIPS 140-3 が評価の対象とするものとして、最も適切なものはどれでしょう？

1. ファイアウォールのアクセス制御機能
2. 組織の情報セキュリティマネジメントシステム（ISMS）
3. OS のアクセス制御モデル全般
4. 暗号モジュールのセキュリティ要件

<details><summary>答えと解説</summary>

正解: **4**

FIPS 140（現行は 140-3）は暗号モジュール（ハードウェア・ソフトウェア）のセキュリティ要件をレベル1〜4で定めた米国の基準です。ISMS の認証は ISO/IEC 27001、製品全般の評価はコモンクライテリア（ISO/IEC 15408）が担当します。「FIPS 140=暗号モジュール専用」と覚えると、基準名の入れ替えひっかけに対応できます。

</details>

**問5.** 政府機関が新しいファイアウォール製品を調達するにあたり、複数ベンダーの製品を共通の要求仕様で比較評価したいと考えています。調達側が最初に利用・作成すべきものとして最も適切なものはどれでしょう？

1. 各ベンダーの ST（Security Target）を取り寄せて、そのまま要求仕様とする
2. 対象製品分野の PP（Protection Profile）を利用して要求仕様を定める
3. 各製品に EAL7 の取得を義務付ける
4. 各ベンダーに FIPS 140-3 レベル4 の認証を義務付ける

<details><summary>答えと解説</summary>

正解: **2**

調達側（顧客側）の要求仕様を実装非依存で定義するのが PP の役割で、各ベンダーの ST が PP を満たすかで比較できます。ST はベンダー側の主張なので、そのまま要求仕様にすると比較の基準になりません。EAL7 は形式検証まで求める極めて高コストな保証レベルで、一般的なファイアウォール調達には過剰です。FIPS 140 は暗号モジュールの基準であり、製品全体の要求仕様にはなりません。

</details>

## 2. プロセッサとメモリの保護（保護リング・TCB・TPM）

### 基礎の基礎 — CPU・メモリ・OS・プロセス

この章は、コンピュータの中身を少しだけ知っている前提で進みます。最初に用語をそろえましょう。

| 用語 | 意味 |
|---|---|
| CPU | 命令を1つずつ実行する計算装置 |
| メモリ (RAM) | CPU が今使っているプログラムやデータを置く作業場所。電源を切ると消える |
| OS | CPU・メモリ・ディスクなどを管理し、アプリに使わせる基本ソフト（Windows、Linux など） |
| カーネル (kernel) | OS の中核部分。メモリの割り当てや、誰がどのファイルを開けるかの判定をする |
| プロセス (process) | 実行中のプログラム1つ分。Python でスクリプトを動かすと、python のプロセスが1つできる |
| デバイスドライバ | ディスクやネットワークカードなど、個々の機器を動かすための OS の部品 |
| ファームウェア | 機器に組み込まれた基本ソフト。PC では電源投入直後に動く UEFI（昔の BIOS） |

### OS は自分自身をどう守るか

CPU には**保護リング (protection rings)** という特権レベルの仕組みがあります。**Ring 0** が最も強い権限（**カーネルモード**。OS の中核やデバイスドライバが動く）、**Ring 3** が最も弱い権限（**ユーザーモード**。アプリが動く）です。（Ring 1・2 はドライバ用などに想定された中間の段ですが、Windows や Linux は通常 Ring 0 と Ring 3 の2段だけを使います。）

| リング | 名前 | 動くもの | できること |
|---|---|---|---|
| Ring 0 | カーネルモード | OS カーネル、デバイスドライバ | すべてのメモリ・機器を直接操作できる |
| Ring 3 | ユーザーモード | ブラウザ、Python スクリプトなどのアプリ | 自分のメモリだけ。ディスクや他プロセスには直接触れない |

アプリが OS の機能を使うときは、**システムコール**（アプリが OS に「これをして」と頼む決まった入口）を通じて一時的にカーネルモードへ切り替わります。

**ファイルを開くときの流れ**: Python で `open("memo.txt")` を実行すると、内部では次のことが起きます。Linux では `strace`（プロセスが呼んだシステムコールを表示するツール）で実物を見られます。

```
$ strace -e trace=openat python3 -c 'open("memo.txt")'
openat(AT_FDCWD, "memo.txt", O_RDONLY|O_CLOEXEC) = 3
```

- 1行目: python3 を strace の下で動かし、ファイルを開くシステムコール `openat` だけを表示させる（実際には Python 起動時のライブラリ読み込みの行も多数出ますが、ここでは memo.txt の行だけを抜き出しています。memo.txt は事前に作ってある前提です）
- 2行目: python3 が「今いるフォルダ (`AT_FDCWD`) の memo.txt を読み取り専用 (`O_RDONLY`) で開いて」と頼み、カーネルが成功の印として番号 `3` を返した（以後この番号でファイルを読む）

段階に分けると次のとおりです。

1. Ring 3: Python が `openat` を呼ぶ → CPU がカーネルモード（Ring 0）に切り替わる
2. Ring 0: カーネルが「このプロセスの利用者に memo.txt を読む権限があるか」を確認する
3. Ring 0: 許可ならディスクを操作して番号 `3` を用意する
4. Ring 3 に戻り、Python は番号 `3` を受け取る

権限がなければ、結果は `= -1 EACCES (Permission denied)`（拒否）になります。アプリは自分でディスクを直接読めないので、必ずこのカーネルの確認を通ることになります。これが「すべてのアクセスを仲介する」という、後で出てくるリファレンスモニタの考え方の実物です。

### メモリ保護 — プロセスは他人のメモリを見られない

各プロセスには独立したメモリ空間が割り当てられ（**プロセス分離 / process isolation**）、他プロセスのメモリを勝手に読めないようになっています。仕組みは**仮想メモリ**です。プロセスが使う番地（アドレス）は、CPU 内の MMU（メモリ管理装置）が実際のメモリの位置に変換します。

| プロセス | プロセスが使う番地 | 実際のメモリの位置 |
|---|---|---|
| ブラウザ | 0x7ffd1000 | 物理位置 0x1A2000 |
| 給与計算アプリ | 0x7ffd1000 | 物理位置 0x3F8000 |

同じ番地 `0x7ffd1000` を使っても、変換先が違うので互いのデータには届きません。変換表に載っていない番地を読もうとすると CPU が止め、OS がそのプロセスを強制終了します（Linux では `Segmentation fault` と表示されます）。この変換表を書き換えられるのは Ring 0 のカーネルだけです。

ほかにもメモリを守る仕組みとして、データ置き場のメモリを「実行禁止」にする **DEP / NX ビット**や、プログラムがメモリのどこに置かれるかを起動のたびに変える **ASLR** があります（攻撃との関係は L29 で扱います）。

### TCB とリファレンスモニタ（超頻出）

- **TCB (Trusted Computing Base)**: セキュリティポリシーの実施に関わるハードウェア・ソフトウェア・ファームウェアの総体。例: CPU のリング機構と MMU、OS カーネル、ログイン処理、UEFI ファームウェア。ブラウザや表計算ソフトは TCB の外です。TCB とそれ以外を分ける境界線を**セキュリティ境界 (security perimeter)** と呼びます
- **リファレンスモニタ (reference monitor)**: 「主体から客体へのすべてのアクセスを検査・仲介する」という**抽象的な概念（設計上のルール）**。主体・客体は L09 で見たとおり、アクセスする側（プロセス）とされる側（ファイルなど）です
- **セキュリティカーネル (security kernel)**: リファレンスモニタを実際に**実装したもの**（TCB 内のハードウェア・ソフトウェア・ファームウェア）

リファレンスモニタが満たすべき3要件は試験の定番です:

1. **すべてのアクセスを仲介する**（バイパス不可 / always invoked）
2. **改ざんから保護されている**（tamper-proof）
3. **検証可能なほど小さくシンプル**（verifiable）

### ハードウェアによる信頼の起点

ここでは2つの前提を使います（どちらも L11 で詳しく扱います）。

- **ハッシュ値**: データから計算する決まった長さの「指紋」。1ビットでも中身が変わると、まったく違う値になる
- **デジタル署名**: 作成者だけが持つ秘密鍵で付ける印。誰でも検証でき、改ざんされていれば検証に失敗する

PC の起動は、次の順にバトンを渡していきます。

1. UEFI ファームウェア（電源投入直後に動く）
2. ブートローダ（OS を読み込む小さなプログラム）
3. OS カーネル
4. デバイスドライバ・各種サービス

どこか1段でも改ざんされると、それより後の段はすべて信用できなくなります。そこで、各段が次の段を確かめてから渡すようにします。

| 仕組み | 役割 |
|---|---|
| **TPM (Trusted Platform Module)** | マザーボード上のセキュリティチップ。暗号鍵の安全な保管、起動時の完全性測定値の記録。BitLocker などのディスク暗号化の鍵保管に利用 |
| **HSM (Hardware Security Module)** | 外付け・ネットワーク接続型の鍵管理専用装置。CA の秘密鍵保管など**大規模・高性能**な鍵管理向け |
| **セキュアブート (secure boot)** | 起動時に各コンポーネントの**署名を検証**し、不正なら起動を**拒否** |
| **測定ブート (measured boot)** | 各起動段階の**ハッシュを TPM に記録**し、後から正常性を検証（リモート認証 / attestation。記録を外部のサーバに送り、正常な PC かを判定してもらうこと）できる。起動は止めない |

**測定ブートで TPM に残る記録の例**: TPM の中には PCR（測定値を記録する専用の場所）があり、各段のハッシュ値を「前の値とつなげて計算し直す」方法で積み上げます。

```
PCR[0] = SHA-256( 前の PCR[0] の値 ‖ UEFI ファームウェアのハッシュ値 )
```

`‖` は「2つの値をつなげる」という意味です。いったん記録した値は消したり好きな値に置き換えたりできず、足し込むことしかできません。そのため、途中の1段でも改ざんされていれば最終的な PCR の値が正常時と変わり、後から見抜けます。

BitLocker（Windows のディスク暗号化機能）は、PCR の値が正常時と同じときだけ TPM がディスクの鍵を出す設定にできます。起動部分が改ざんされた PC では鍵が出てこないので、ディスクは開けません。

💡 コツ: 「TPM = 板（マザーボード）に付いた個人用チップ、HSM = 組織の金庫」「セキュアブート = 門前払い、測定ブート = 記録して後で報告」と対で覚えましょう。

### 確認問題

**問1.** リファレンスモニタ（reference monitor）が満たすべき要件に「含まれない」ものはどれでしょう？

1. すべてのアクセスを例外なく仲介し、バイパスできないこと
2. 改ざんから保護されていること
3. 検証できるほど小さくシンプルであること
4. 高いスループットで並列処理ができること

<details><summary>答えと解説</summary>

正解: **4**

リファレンスモニタの3要件は「全アクセスの仲介（バイパス不可）」「改ざん防止（tamper-proof）」「検証可能性（小さくシンプル）」です。性能は要件に含まれません。むしろ「検証可能なほど小さく」という要件は、高機能・高性能化と相反する方向です。3要件はそのまま穴埋めで問われるので確実に覚えましょう。

</details>

**問2.** リファレンスモニタとセキュリティカーネルの関係として、最も適切な説明はどれでしょう？

1. リファレンスモニタは抽象的な概念であり、セキュリティカーネルはそれを実装したものである
2. セキュリティカーネルは抽象的な概念であり、リファレンスモニタはそれを実装したものである
3. 両者は同じものを指す完全な同義語である
4. リファレンスモニタはハードウェア、セキュリティカーネルはソフトウェアを指す

<details><summary>答えと解説</summary>

正解: **1**

リファレンスモニタは「全アクセスを仲介せよ」という設計上の抽象概念で、それを TCB 内のハードウェア・ソフトウェア・ファームウェアとして具現化したものがセキュリティカーネルです。概念と実装の関係を逆にした選択肢が定番のひっかけです。ハードウェア/ソフトウェアの区別で分ける説明も誤りで、セキュリティカーネルは両方を含みます。

</details>

**問3.** Ring 3（ユーザーモード）で動く Python スクリプトが、ディスク上のファイルを読もうとしています。このとき起きることとして最も適切なものはどれでしょう？

1. スクリプトがディスク装置を直接操作してファイルを読む
2. スクリプトはファイルを読めず、管理者に依頼するしかない
3. システムコールで OS カーネルに依頼し、カーネルがアクセス権を確認したうえで読み取る
4. スクリプトが一時的に Ring 0 の権限を持ち、自由にディスクを読む

<details><summary>答えと解説</summary>

正解: **3**

ユーザーモードのアプリはディスクなどの機器を直接操作できず、システムコールで OS カーネルに依頼します。CPU はカーネルモードに切り替わりますが、そこで動くのはアプリではなくカーネルのコードで、カーネルがアクセス権を確認してから読み取りを行います。アプリが Ring 0 の権限を得て自由に動けるわけではありません。権限があれば管理者に頼む必要もなく、システムコールで読めます。この「必ずカーネルの確認を通る」構造が、リファレンスモニタの考え方を実装したものです。

</details>

**問4.** ある社員のノート PC では、ディスク全体の暗号化鍵をマザーボード上のチップに保管し、起動時にファームウェアや OS が改ざんされていないかの測定値も同じチップに記録しています。このチップとして最も適切なものはどれでしょう？

1. HSM（Hardware Security Module）
2. TPM（Trusted Platform Module）
3. スマートカード
4. GPU（Graphics Processing Unit）

<details><summary>答えと解説</summary>

正解: **2**

マザーボード上に搭載され、暗号鍵の保管と起動時の完全性測定（プラットフォーム検証）を担うのは TPM です。HSM は CA の秘密鍵保管など組織規模の鍵管理に使う外付け・ネットワーク接続型の装置なので、個々の PC の内蔵チップという説明に合いません。スマートカードは携帯用の認証デバイスで、プラットフォームの測定値記録は行いません。「PC 内蔵=TPM、組織の金庫=HSM」で区別しましょう。

</details>

**問5.** セキュアブート（secure boot）と測定ブート（measured boot）の違いとして、最も適切な説明はどれでしょう？

1. セキュアブートは起動段階のハッシュを記録して後から検証し、測定ブートは署名が不正なら起動を拒否する
2. どちらも起動を拒否する仕組みだが、セキュアブートは BIOS 専用で測定ブートは UEFI 専用である
3. セキュアブートは署名が不正なコンポーネントの起動を拒否し、測定ブートは各段階のハッシュを TPM に記録して後から検証可能にする
4. セキュアブートはソフトウェアのみで実現され、測定ブートはハードウェアを使わない

<details><summary>答えと解説</summary>

正解: **3**

セキュアブートは起動時に署名を検証して不正なら「門前払い（起動拒否）」、測定ブートは各段階のハッシュを TPM に記録して後からリモート認証（attestation）などで検証できるようにする「記録して報告」の仕組みです。両者の役割を入れ替えた選択肢が典型的なひっかけです。測定ブートはむしろ TPM というハードウェアに依存します。

</details>

**問6.** カーネルモード（Ring 0）で動作するデバイスドライバの脆弱性が、ユーザーモードのアプリの脆弱性より深刻とされる理由として、最も適切なものはどれでしょう？

1. デバイスドライバはネットワークから直接アクセスできるため
2. カーネルモードのコードはシステム全体の資源に最高権限でアクセスでき、プロセス分離などの保護を受けないため
3. デバイスドライバはユーザーが自由に無効化できないため
4. カーネルモードのコードはメモリ使用量が大きいため

<details><summary>答えと解説</summary>

正解: **2**

Ring 0（カーネルモード）のコードはメモリ・ハードウェアを含むシステム全体に最高権限でアクセスできるため、ここを乗っ取られるとプロセス分離やアクセス制御といった保護機構そのものを無効化できます。だからこそ TCB は「小さく検証可能に」が原則です。ネットワークからの直接アクセス可否や無効化のしやすさ、メモリ使用量は特権レベルの深刻さの本質ではありません。

</details>

## 3. 仮想化とクラウドのセキュリティ

### 仮想化の基本とリスク

1台の物理マシン上で複数の仮想マシン (VM) を動かす土台が**ハイパーバイザ (hypervisor)** です。**仮想マシン**は、ソフトウェアで作った「コンピュータ1台分」で、中で独自の OS（**ゲスト OS**）が動きます。

たとえば CPU 32 コア・メモリ 256GB の物理サーバ1台を、次のように分けて使います。

| VM | ゲスト OS | 割り当て | 用途 |
|---|---|---|---|
| VM-A | Linux | 4 コア / 16GB | Web サーバ |
| VM-B | Linux | 8 コア / 64GB | データベース |
| VM-C | Windows | 4 コア / 32GB | 人事システム |

各 VM は自分専用のコンピュータを持っているように見えますが、実際の CPU やメモリの割り当てと、VM どうしの仕切りはハイパーバイザが受け持ちます。前章で見たカーネルがプロセスどうしを仕切るのと同じ役割を、1段下の層で VM どうしに対して行っているわけです。

- **Type 1（ベアメタル型）**: ハードウェア上で直接動く（データセンター向け。攻撃面が小さい。例: VMware ESXi、Microsoft Hyper-V）
- **Type 2（ホスト型）**: 通常の OS の上でアプリとして動く（開発・検証向け。ホスト OS の分だけ攻撃面が広い。例: VirtualBox を手元の PC にインストールして使う）

| 層（下から上へ） | Type 1 | Type 2 |
|---|---|---|
| 1 | ハードウェア | ハードウェア |
| 2 | ハイパーバイザ | ホスト OS（Windows など） |
| 3 | VM（ゲスト OS + アプリ） | ハイパーバイザ（アプリとして動く） |
| 4 | | VM（ゲスト OS + アプリ） |

最大の脅威は **VM エスケープ (VM escape)**: VM 内の攻撃者がハイパーバイザの脆弱性を突いて外へ脱出し、ホストや他の VM を侵害することです。対策はハイパーバイザへの迅速なパッチ適用と、機密度の異なる VM を同一ホストに同居させないことです。ほかに、無秩序に VM が増えて管理されなくなる **VM スプロール (VM sprawl)** も、パッチ漏れ・資産管理漏れの温床として頻出です。

**コンテナ (container)** は、アプリとその動作に必要なライブラリだけを箱詰めして、OS 上で他から仕切って動かす技術です（Docker が代表例）。VM のようにゲスト OS を丸ごと持たないため VM より軽量ですが、**ホスト OS のカーネルを全コンテナで共有**するため、カーネルの脆弱性が全コンテナに波及する点が VM との決定的な違いです。

カーネルを共有していることは、Linux のカーネルの版を表示する `uname -r` で確かめられます。

```
$ uname -r
6.8.0-45-generic
$ docker run --rm ubuntu uname -r
6.8.0-45-generic
```

- 1〜2行目: ホスト（コンテナを動かしている側のマシン）でカーネルの版を表示 → `6.8.0-45-generic`
- 3〜4行目: ubuntu のコンテナを起動して同じコマンドを実行し、終わったらコンテナを消す（`--rm`）→ 同じ `6.8.0-45-generic`

コンテナの中身が ubuntu でも、動いているカーネルはホストのものです。VM なら、ゲスト OS のカーネルの版が表示されます。**サーバーレス (serverless)**（利用者は関数のコードだけを置き、サーバの用意や台数の増減は事業者に任せる形態）では基盤の管理はクラウド事業者側ですが、コードと設定の安全性は利用者の責任です。

### クラウドのサービスモデルと責任共有（超頻出）

**責任共有モデル (shared responsibility model)** では、どこまでを事業者が守り、どこからを利用者が守るかがサービスモデルで変わります。

- **IaaS (Infrastructure as a Service)**: 仮想サーバやストレージを借りる。OS から上は利用者が入れて管理する（例: 仮想サーバを1台借りて Linux を自分で設定する）
- **PaaS (Platform as a Service)**: アプリの実行環境を借りる。利用者は自分のアプリのコードを置くだけ（例: マネージドなデータベースやアプリ実行基盤）
- **SaaS (Software as a Service)**: 完成したアプリを使う（例: Web メール、オンラインのオフィスソフト）

| 層 | IaaS | PaaS | SaaS |
|---|---|---|---|
| データ・アクセス管理 | 利用者 | 利用者 | **利用者** |
| アプリケーション | 利用者 | 利用者 | 事業者 |
| OS・ミドルウェア | 利用者 | 事業者 | 事業者 |
| 物理・仮想化基盤 | 事業者 | 事業者 | 事業者 |

💡 コツ: **「自分のデータとその分類・アクセス管理の責任だけは、どのモデルでも絶対に利用者に残る」**。これを問う問題が繰り返し出ます。

配置モデルは、**パブリック**（共用）・**プライベート**（1組織専用）・**コミュニティ**（共通の関心を持つ複数組織で共用）・**ハイブリッド**（組み合わせ）の4つ。パブリッククラウドでは複数顧客が同じ基盤に同居する**マルチテナンシー (multi-tenancy)** となり、テナント間分離の失敗が固有のリスクです。

### 確認問題

**問1.** SaaS を利用する場合でも、利用者（顧客）側に責任が残るものとして最も適切なものはどれでしょう？

1. アプリケーションの脆弱性修正
2. データの分類とユーザーのアクセス権管理
3. 仮想化基盤のパッチ適用
4. データセンターの物理セキュリティ

<details><summary>答えと解説</summary>

正解: **2**

責任共有モデルでは、サービスモデルが何であれ「自分のデータ（分類・保護要件の決定）と、誰にアクセスさせるか」の責任は常に利用者に残ります。SaaS ではアプリ・OS・基盤・物理設備はすべて事業者の責任範囲です。「SaaS なら全部お任せ」という誤解を突くのが定番のひっかけです。

</details>

**問2.** ハードウェア上で直接動作し、ホスト OS を介さないハイパーバイザの種類と、その一般的な利点の組み合わせとして最も適切なものはどれでしょう？

1. Type 2（ホスト型）― ホスト OS の保護機能を利用できる
2. Type 1（ベアメタル型）― ホスト OS がない分、攻撃面が小さい
3. Type 2（ホスト型）― 性能のオーバーヘッドが最も小さい
4. Type 1（ベアメタル型）― 一般ユーザーの PC での開発用途に最適である

<details><summary>答えと解説</summary>

正解: **2**

ハードウェア上で直接動くのは Type 1（ベアメタル型）で、間にホスト OS が存在しない分だけ攻撃面が小さく性能も高いため、データセンターや本番環境で使われます。Type 2 は OS 上のアプリとして動くホスト型で、手軽な反面ホスト OS の脆弱性の影響を受けます。Type 1 は開発者の普段使いの PC 向けではなく、用途を入れ替えた選択肢がひっかけです。

</details>

**問3.** ある VM 内で権限を得た攻撃者が、ハイパーバイザの脆弱性を悪用してホストや同居する他の VM へアクセスしました。この攻撃の名称と、最も効果的な予防策の組み合わせはどれでしょう？

1. VM スプロール ― VM の作成を承認制にする
2. VM エスケープ ― 各 VM に個別のウイルス対策ソフトを導入する
3. VM エスケープ ― ハイパーバイザへ迅速にパッチを適用し、機密度の異なる VM を同一ホストに同居させない
4. サイドチャネル攻撃 ― VM のメモリを増設する

<details><summary>答えと解説</summary>

正解: **3**

VM から脱出してホストや他 VM を侵害する攻撃は VM エスケープです。悪用されるのはハイパーバイザの脆弱性なので、ハイパーバイザのパッチ適用と、万一の際の影響を抑えるホスト分離（機密度の異なる VM を同居させない）が最も効果的です。VM 内のウイルス対策はゲスト内の防御であり、ハイパーバイザ層の脆弱性には無力です。VM スプロールは管理されない VM の乱立という別の問題です。

</details>

**問4.** コンテナ技術が仮想マシン (VM) と比べて持つ、セキュリティ上の固有のリスクとして最も適切なものはどれでしょう？

1. すべてのコンテナがホスト OS のカーネルを共有するため、カーネルの脆弱性の影響が全コンテナに及ぶ
2. コンテナは VM よりイメージのサイズが大きく、配布時の改ざん検知が難しい
3. コンテナはハイパーバイザを必ず二重に経由するため、攻撃面が広い
4. コンテナは物理サーバーを専有するため、マルチテナンシーが実現できない

<details><summary>答えと解説</summary>

正解: **1**

コンテナはゲスト OS を持たず、ホスト OS のカーネルを全コンテナで共有します。そのためカーネルに脆弱性があると全コンテナの分離が破られるおそれがあり、これが VM（ハイパーバイザでより強く分離される）との決定的な違いです。コンテナイメージはむしろ VM より軽量で、ハイパーバイザを使わないのが特徴です。軽量・高速という利点と分離の弱さという欠点をセットで覚えましょう。

</details>

**問5.** ある Linux サーバ上で 10 個のコンテナを動かしています。ホストの Linux カーネルに権限昇格の脆弱性が見つかりました。影響範囲として最も適切なものはどれでしょう？

1. コンテナはそれぞれ独自のカーネルを持つので、ホストだけが影響を受ける
2. コンテナはハイパーバイザで分離されているため、どのコンテナにも影響しない
3. 影響を受けるのは、脆弱性が見つかった時点で停止していたコンテナだけである
4. コンテナはホストのカーネルを共有しているため、10 個すべての分離が破られるおそれがある

<details><summary>答えと解説</summary>

正解: **4**

コンテナはゲスト OS を持たず、ホストのカーネルを全コンテナで共有しています。そのためカーネルの脆弱性を突かれると、1つのコンテナから他のコンテナやホストへ抜け出されるおそれがあり、10 個すべてが影響範囲に入ります。「コンテナごとに独自のカーネルを持つ」のは VM の特徴で、コンテナには当てはまりません。コンテナはハイパーバイザではなくホスト OS のカーネルの機能で仕切られています。停止中かどうかは脆弱性の影響範囲を決める要因ではありません。

</details>

**問6.** 社内で各部門が検証用の VM を自由に作成した結果、誰も管理していない VM が多数残り、パッチ未適用のまま放置されていることが判明しました。この状況への対応として最も適切なものはどれでしょう？

1. すべての VM を直ちに削除する
2. VM の作成・廃棄を申請承認制にし、資産台帳と連動したライフサイクル管理を導入する
3. ハイパーバイザを Type 1 から Type 2 に変更する
4. VM のスナップショットを毎日取得する

<details><summary>答えと解説</summary>

正解: **2**

この状況は VM スプロールで、根本原因は「管理プロセスなしに VM が作られること」です。作成・廃棄の承認プロセスと資産管理（インベントリ）を整備するのが管理者視点の BEST な対応です。全削除は業務影響を無視した乱暴な対応で、ハイパーバイザの種類変更やスナップショット取得はスプロールの原因に対処しません。CISSP では「技術で殴る前にプロセス・ガバナンスを整える」選択肢が正解になりやすいことを覚えておきましょう。

</details>

## 4. 組込みシステム・ICS・IoT のセキュリティ

### IT と「現場のシステム」は守り方が違う

工場やプラントを制御する **ICS (Industrial Control System / 産業用制御システム)** の仲間を押さえましょう。

| 用語 | 意味 |
|---|---|
| **SCADA** (Supervisory Control and Data Acquisition) | 広域に分散した設備（送電網・水道など）の監視制御とデータ収集 |
| **DCS** (Distributed Control System) | 1つのプラント内の分散制御システム |
| **PLC** (Programmable Logic Controller) | 機械を直接制御する小型コントローラ |
| **HMI** (Human Machine Interface) | 運転員が設備の状態を見て操作する画面 |

浄水場を例に、つながり方を下から並べます。

1. センサーとポンプ: 水位を測り、水を送る
2. PLC: 「水位が 2.0m を下回ったらポンプを止める」といった制御を一定間隔で繰り返し実行する
3. HMI: 運転員が水位の表示を見て、ポンプの手動停止などを指示する
4. SCADA サーバ: 市内各地の浄水場や配水所のデータを集めて監視する

**制御用の通信は守りが弱いことが多い**: 古くから使われる制御プロトコル（通信の取り決め）の Modbus/TCP には、送り手が誰かを確かめる仕組み（認証）がありません。

```
送信元 192.0.2.50:49152 → 宛先 198.51.100.20:502
Modbus 関数コード 06（1つのレジスタに書き込む） レジスタ 1 に値 0 を書け
```

- 1行目: 192.0.2.50 の機器から、PLC（198.51.100.20）の Modbus 用の番号 502 番へ送る
- 2行目: PLC の設定値の置き場所（レジスタ）1番に 0 を書き込む命令。たとえばこれが「ポンプ運転=1／停止=0」なら、ポンプが止まる

PLC はこの命令が運転員の HMI から来たのか攻撃者の PC から来たのかを区別できません。だからこそ、制御ネットワークに外から届かないようにする分離が最初の対策になります。

ICS の世界では、情報の機密性よりも**可用性と人命・設備の安全 (safety) が最優先**です。再起動が許されない、ベンダー保証が切れるためパッチを当てられない、OS が古いまま、といった制約が普通にあります。したがって対策の基本は**ネットワーク分離（セグメンテーション）**と、パッチの代わりになる**補償コントロール (compensating controls)**（L08 で見た「本来の対策ができないときの代わりの対策」。一方向ゲートウェイ、厳格なアクセス制御、監視強化など）です。**一方向ゲートウェイ**（データダイオードとも呼ぶ）は、物理的に片方向にしかデータが流れない装置で、制御ネットワークから IT ネットワークへ稼働データを送ることはできても、逆向きの通信は一切通しません。

### IoT・組込みシステム

IoT 機器は「小さなコンピュータ」ですが、**デフォルトパスワードのまま出荷される、アップデート手段がない・提供されない、計算能力が小さく暗号化が省かれる**といった弱点を抱えがちです。2016 年には、ID `admin`・パスワード `admin` のような初期設定のままのネットワークカメラなどが大量に乗っ取られ、Mirai というマルウェアによる大規模な DDoS 攻撃（大量の機器から一斉に通信を送りつけてサービスを止める攻撃）に使われました。対策の定番は、**デフォルト認証情報の変更、ファームウェア更新経路の確保、IoT 専用ネットワークセグメント（ネットワークを区切った区画）への分離**です。家庭用・業務用を問わず「IoT は信用せず隔離する」が基本姿勢です。

**組込みシステム**は、家電・車・医療機器などに組み込まれ、決まった仕事だけをする専用のコンピュータです。組込みシステムでは、応答時間が保証された **RTOS (Real-Time Operating System)**（例: 車のブレーキ制御で「信号から 10 ミリ秒以内に必ず応答する」ことを保証する OS）がよく使われます。リアルタイム性最優先の設計のため、セキュリティ機能は限定的なことが多い点を押さえましょう。

### エッジとフォグ

- **エッジコンピューティング (edge computing)**: データの発生源（センサーやデバイス）の近くで処理し、遅延と通信量を減らす
- **フォグコンピューティング (fog computing)**: エッジとクラウドの中間層（現場近くのゲートウェイ等）で処理する考え方

💡 コツ: この分野のシナリオ問題は「パッチを当てられない機器にどう対処するか」がお決まりのパターンです。答えはほぼ必ず**「分離 + 補償コントロール」**。「直ちにパッチ適用」「機器を即交換」のような現場の制約を無視した選択肢は、もっともらしくても誤りです。

### 確認問題

**問1.** 工場の製造ラインを制御する PLC に重大な脆弱性が見つかりましたが、ベンダーのサポート条件により OS のパッチ適用も機器の交換も当面できません。管理者として最も適切な対応はどれでしょう？

1. 業務を停止してでも直ちにパッチを適用する
2. リスクは低いと判断し、次回の設備更新まで何もしない
3. 制御ネットワークを IT ネットワークから分離し、アクセス制御や監視強化などの補償コントロールを導入する
4. PLC にウイルス対策ソフトをインストールする

<details><summary>答えと解説</summary>

正解: **3**

パッチを当てられない ICS 機器への定石は「ネットワーク分離 + 補償コントロール（compensating controls）」です。ICS は可用性と安全が最優先のため、業務を止めてのパッチ強行は不適切ですし、何もしないのはリスクの放置です。PLC のような組込みコントローラは汎用のウイルス対策ソフトを導入できないことがほとんどです。「パッチ不可→分離+補償」のパターンは頻出なので即答できるようにしましょう。

</details>

**問2.** 送電網や上下水道のように、広域に分散した設備の監視制御とデータ収集を行うシステムの名称として最も適切なものはどれでしょう？

1. SCADA
2. RTOS
3. CDN
4. SIEM

<details><summary>答えと解説</summary>

正解: **1**

SCADA (Supervisory Control and Data Acquisition) は広域に分散した設備の監視制御・データ収集システムで、電力・水道などの重要インフラで使われます。RTOS は応答時間が保証されたリアルタイム OS、CDN はコンテンツ配信網、SIEM はログの集中分析基盤で、いずれも制御システムそのものではありません。同じ ICS ファミリーでも「広域=SCADA、プラント内=DCS、機械直結=PLC」と範囲で区別しましょう。

</details>

**問3.** 一般的な IT システムと比較したとき、ICS（産業用制御システム）のセキュリティで最も優先されるものはどれでしょう？

1. 保存データの機密性
2. 可用性と人命・設備の安全（safety）
3. ユーザーの利便性
4. 通信の匿名性

<details><summary>答えと解説</summary>

正解: **2**

IT では一般に機密性 (C) が重視されますが、ICS では制御が止まったり誤動作したりすると人命や設備に直結するため、可用性と安全 (safety) が最優先です。この優先順位の違いが「ICS に IT 流のパッチ運用をそのまま持ち込めない」理由になります。CIA の優先順位は文脈で変わる、という視点そのものが CISSP で問われます。

</details>

**問4.** オフィスに多数の IoT 機器（ネットワークカメラ・スマートセンサー等）を導入するにあたり、最初に実施すべき対策の組み合わせとして最も適切なものはどれでしょう？

1. 機器の MAC アドレスを記録し、電源タップを統一する
2. すべての機器に EDR エージェントを導入し、フルディスク暗号化を有効にする
3. 機器を業務 LAN に直結し、通信を高速化する
4. デフォルト認証情報を変更し、ファームウェア更新手段を確認した上で、IoT 専用セグメントに分離する

<details><summary>答えと解説</summary>

正解: **4**

IoT 対策の基本3点セットは「デフォルトパスワードの変更」「更新経路の確保」「専用セグメントへの分離」です。IoT 機器は計算資源が乏しく、EDR エージェントやフルディスク暗号化のような PC 向け対策は導入できないことが多いのが実情です。業務 LAN への直結は、侵害された IoT 機器を踏み台にされるリスクを高める逆効果の選択肢です。

</details>

**問5.** 多数のセンサーが生成する大量データについて、クラウドに送る前にデータの発生源の近くで処理を行い、遅延と通信量を減らすアーキテクチャとして最も適切なものはどれでしょう？

1. メインフレームによる集中処理
2. グリッドコンピューティング
3. エッジコンピューティング
4. シンクライアント

<details><summary>答えと解説</summary>

正解: **3**

データ発生源（デバイスやセンサー）の近くで処理するのがエッジコンピューティングで、遅延低減と通信量削減が狙いです。エッジとクラウドの中間層（現場近くのゲートウェイ等）で処理する場合はフォグコンピューティングと呼びます。メインフレームやシンクライアントは集中処理の形態であり「発生源の近く」とは逆方向、グリッドは多数の計算機で大規模計算を分担する仕組みで文脈が異なります。

</details>
