# 第30章 DevSecOps・開発環境・ソフトウェア調達のセキュリティ【D8】

D8 の仕上げとして、開発パイプラインと「他人が書いたコード」を安全に使う統制を学びます。SAST/DAST/SCA などのテスト手法の使い分け、API・マイクロサービスの守り方、COTS・OSS・SaaS を調達するときの評価観点は、実務でも試験でも頻出です。開発経験がある人ほど「ツールの話」ではなく「どの段階で・誰が・何を統制するか」というマネジメント視点で整理し直しましょう。

## 1. DevSecOpsとCI/CDのセキュリティ

### 基礎の基礎 — CI/CD とパイプライン

開発者がコードを**コミット**(変更をリポジトリに記録すること)すると、自動で**ビルド**(ソースコードを実行できる形に変換すること)とテストが走る仕組みを **CI**(継続的インテグレーション)、合格したものを自動でテスト環境や本番へ届ける仕組みを **CD**(継続的デリバリー/デプロイ)と呼びます。この一連の自動処理の流れが**パイプライン**です。DevSecOps では、その各段階に次のような検査を挟みます。

| 段階 | 挟む検査の例 |
|---|---|
| コミット直後 | SAST、SCA、シークレット(パスワード等)の混入チェック |
| ビルド後 | 成果物へのコード署名、コンテナイメージのスキャン |
| テスト環境へデプロイ後 | DAST、IAST、ファジング |
| 本番デプロイ前 | 承認ゲート(人が確認して許可する関門) |
| 本番運用中 | RASP、監視 |

### セキュリティは「全員の責任」へ

DevOps は開発 (Development) と運用 (Operations) を一体化して高速リリースを実現する文化です。**DevSecOps** はそこにセキュリティを最初から組み込み、「セキュリティはセキュリティチームだけでなく全員の責任」にする考え方です。リリース直前にまとめて検査するのではなく、パイプラインの各段階に自動化されたチェックを埋め込みます(シフトレフト (shift left))。

### テスト手法の対比表(超頻出)

| 手法 | 見るもの | タイミング | 特徴 |
|---|---|---|---|
| **SAST** (静的解析) | ソースコード | 開発早期・ビルド時 | 実行せず解析。行単位で特定できるが擬陽性(問題ないのに問題ありと出る誤報)が多め |
| **DAST** (動的解析) | 動作中のアプリ | テスト環境・実行時 | 外部から攻撃を模擬。ソース不要、実行時の問題を発見 |
| **IAST** | 実行中の内部 | テスト実行中 | エージェント(アプリ内に組み込む監視用の小さなプログラム)を仕込み内側から観測。SAST と DAST の中間 |
| **RASP** | 本番の実行時 | 運用中 | アプリ内部から攻撃を検知・**ブロック**する防御機構 |

同じ「SQL を文字列連結で組み立てている」欠陥(第29章)を、SAST と DAST はそれぞれ次のように見つけます。

- **SAST の指摘例**: 「`db.py` の 12 行目: 入力値を文字列連結して SQL を作っています」。コードの場所まで分かります
- **DAST の検査例**: 検索欄に `'` を1文字送り、応答に DB のエラーが混ざるかを観察します。混ざれば「入力が SQL として解釈されている」と判断できますが、どの行が原因かまでは分かりません

さらに **SCA (Software Composition Analysis)** は、自分が書いたコードではなく**依存ライブラリ**(自分のコードが利用している他人の部品)**の既知脆弱性とライセンス**を洗い出します。既知脆弱性には CVE という通し番号が付いていて(例: ログ出力ライブラリ Log4j の重大な欠陥 CVE-2021-44228)、SCA は「使っている部品とバージョン」をこの一覧と突き合わせます。**ファジング (fuzzing)** は想定外の異常入力を自動で大量投入し、クラッシュや未処理例外(プログラムが想定していないエラー)を見つける手法です。年齢欄なら `-1`、`99999999999`、`A` を1万文字、絵文字、空文字などを次々に送ります。

### パイプライン自体も資産

CI/CD パイプラインが乗っ取られると、正規のリリース経路でマルウェアが配布されます(サプライチェーン攻撃)。対策は、パイプラインへの**最小権限アクセスと MFA**(第18章で見た多要素認証)、ビルド成果物への**コード署名**(第11章で見たデジタル署名を成果物に付け、改ざんを検知できるようにすること)、IaC(Terraform 等。サーバーやネットワークの構成をコードで書く方式)やコンテナイメージ(アプリと動作環境を1つにまとめた配布物)の**デプロイ前スキャン**、承認ゲートの設置です。

💡 コツ: 「ソースを見るのが SAST、動かして外から叩くのが DAST、本番で守るのが RASP、他人のコードを見るのが SCA」。試験は「この状況で最も適切なツールはどれか」と聞いてきます。

### 確認問題

**問1.** 開発チームは、コーディング段階のできるだけ早い時期に自社開発コードの脆弱性を発見したいと考えています。CI パイプラインに組み込むものとして最も適切 (BEST) なのはどれですか。

1. DAST を本番環境に対して毎晩実行する
2. SAST をコミットごとに自動実行する
3. RASP を本番アプリケーションに導入する
4. 年1回の外部ペネトレーションテストを契約する

<details><summary>答えと解説</summary>

正解: **2**

SAST (静的アプリケーションセキュリティテスト) はソースコードを実行せずに解析するため、コーディング段階の早期(シフトレフト)に組み込めます。DAST は動作するアプリケーションが必要なので「できるだけ早い時期」に合わず、本番相手に毎晩実行するのは適切でもありません。RASP は本番運用中の防御であり発見の時期が最も遅く、ペネトレーションテストも開発後期の手法です。ひっかけ: どれも脆弱性を見つける手段としては正しいので、「早期に」「自社開発コード」という条件で絞り込めるかが問われています。

</details>

**問2.** DAST (動的アプリケーションセキュリティテスト) の説明として最も適切なのはどれですか。

1. ソースコードを1行ずつ解析し、脆弱なコーディングパターンを特定する
2. 依存しているオープンソースライブラリの既知脆弱性を一覧化する
3. 開発者のコードレビューを AI が代行する
4. 動作中のアプリケーションに外部から疑似攻撃を行い、実行時の脆弱性を発見する

<details><summary>答えと解説</summary>

正解: **4**

DAST はブラックボックス的に、稼働中のアプリケーションへ外部からリクエストを送って脆弱性(認証の不備、インジェクションの応答など)を見つけます。ソースコードは不要で、設定ミスなど実行時にしか現れない問題を検出できるのが強みです。「ソースコードを1行ずつ解析し、脆弱な…」は SAST、「依存しているオープンソースライブラリ…」は SCA の説明です。「開発者のコードレビューを AI が代行する」のようなコードレビュー代行は DAST の定義ではありません。ひっかけ: 「静的=ソースを読む、動的=動かして試す」という対比を確実に覚えましょう。

</details>

**問3.** ある企業の Web アプリケーションが、広く使われているログ出力ライブラリの重大な脆弱性の影響を受けるか至急確認する必要があります。最も直接的に役立つ (MOST) のはどれですか。

1. SCA ツールによる依存関係スキャンの結果
2. 直近の DAST レポート
3. ソースコードの手動レビュー記録
4. ファジングテストの結果

<details><summary>答えと解説</summary>

正解: **1**

SCA (ソフトウェア構成分析) は依存ライブラリとそのバージョンを棚卸しし、既知の脆弱性 (CVE) と突き合わせるツールなので、「このライブラリを使っているか」に即答できます。DAST は外部からの挙動しか見ないため特定ライブラリの使用有無は分かりにくく、手動レビューは網羅性と速度に欠けます。ファジングは未知の不具合を見つける手法で、既知脆弱性の影響確認には向きません。ひっかけ: 「既知の脆弱性×依存ライブラリ」とくれば SCA(または SBOM)です。

</details>

**問4.** 本番環境で稼働中のアプリケーションの内部で動作し、攻撃をリアルタイムに検知して遮断する技術はどれですか。

1. IAST
2. SAST
3. RASP
4. SCA

<details><summary>答えと解説</summary>

正解: **3**

RASP (Runtime Application Self-Protection) はアプリケーションに組み込まれ、本番の実行時に内側から攻撃を検知し、処理の中断などで自らを防御します。IAST も内部で観測しますが、目的はテスト段階での脆弱性「発見」であり、本番での「防御」ではありません。SAST はソースコードの静的解析、SCA は依存関係の分析です。ひっかけ: IAST と RASP はどちらもエージェント型で混同しやすいですが、「テストで見つける IAST、本番で守る RASP」と区別します。

</details>

**問5.** CI/CD パイプラインそのものを保護する対策として最も適切 (BEST) な組み合わせはどれですか。

1. パイプラインの実行ログを全開発者に公開し、透明性を高める
2. パイプラインへの最小権限アクセスと MFA、ビルド成果物へのコード署名を実施する
3. リリース速度を優先し、セキュリティチェックは四半期ごとにまとめて行う
4. 本番デプロイ権限を全開発者に付与し、単一障害点をなくす

<details><summary>答えと解説</summary>

正解: **2**

パイプラインが侵害されると正規の配布経路でマルウェアが混入する(サプライチェーン攻撃)ため、アクセスの最小権限化と MFA、成果物への署名による改ざん検知が基本です。ログの全面公開は秘密情報(認証情報やトークン)の漏えいリスクがあり、チェックの後回しは DevSecOps の「組み込み」の思想に反します。全員へのデプロイ権限付与は職務分掌 (separation of duties) の放棄です。ひっかけ: 「開発の自由度を上げる」選択肢は、統制を問う問題ではほぼ誤答です。

</details>

## 2. APIとマイクロサービスのセキュリティ

### API は「もう1つの玄関」

現代のアプリケーションは API (Application Programming Interface) で連携します。API はプログラム同士が呼び出し合うための窓口で、人ではなくプログラムがリクエストを送り、データ(多くは JSON 形式)を受け取ります。

```text
GET /api/v1/orders/1001
Authorization: Bearer eyJhbGciOiJSUzI1NiJ9...
```

1行目は「注文番号 1001 の情報を取得(`GET`)したい」という要求、2行目は呼び出し元を証明するトークン(第20章で見た OAuth の通行証)です。応答は `{"id": 1001, "item": "本", "price": 1200}` のようなデータです。画面がない分、攻撃者にとってはスクリプトで自動化しやすい入口です。守りの基本は次のとおりです。

| 観点 | ポイント |
|---|---|
| 認証・認可 | **API キーだけでは弱い**(期限のない固定の文字列で、漏えいに気づきにくく失効管理も難しい)。OAuth 2.0 の短命トークン(数分〜1時間で失効)や、サービス間なら **mTLS**(相互 TLS)で双方を認証 |
| 流量制御 | **レート制限 (rate limiting)**(例: 1利用者あたり毎分100回まで。超えたら HTTP 429 Too Many Requests を返す)とスロットリング(超過分を遅らせて処理する)で、総当たりや資源枯渇(DoS)を抑える |
| 入力検証 | 必ず**サーバー側**で行う。クライアント側の検証は容易にバイパスされる |
| 集約 | **API ゲートウェイ**(すべての API の手前に置く共通の入口)に認証・レート制限・ログを集約し、統制点を1つにする |

**mTLS とは**: 通常の TLS(第12章)では、サーバーだけが証明書を見せて「本物のサーバーです」と証明し、クライアントは証明しません。mTLS ではクライアントも証明書を見せるので、「注文サービス」と「在庫サービス」が互いに相手を確認してから通信できます。Basic 認証(ID とパスワードを毎回リクエストに入れて送る方式)や API キーの共有は、この相互確認になりません。

### マイクロサービス特有の課題

マイクロサービスとは、1つのアプリを「注文」「在庫」「決済」のような小さなサービスに分け、API で連携させる作り方です。サービスが細かく分かれると、サービス間通信とシークレット(認証情報)の管理が爆発的に増えます。

- サービス間認証: mTLS や**サービスメッシュ**(通信の暗号化とポリシーを基盤側で一括管理)
- シークレット管理: コードやリポジトリに埋め込まず、**専用のシークレット管理基盤**(ボールト。例: HashiCorp Vault、AWS Secrets Manager)から実行時に取得し、定期ローテーション(定期的に新しい値へ取り替えること)
- **シャドー API** 対策: 管理台帳にない API が最大のリスク。**API インベントリ**を整備し、ゲートウェイ経由に集約して可視化

Webhook(外部からの呼び出しを受ける口)は送信元の検証(署名検証)を忘れがちです。送信側は事前に共有した秘密鍵で本文の MAC(第11章で見た改ざん検知の値)を計算してヘッダに付け、受信側は同じ計算をして一致すれば本物と判断します。GraphQL は1つのエンドポイント(API の呼び出し先 URL)で柔軟な問い合わせができる反面、過剰なデータ取得や深いネストによる DoS に注意が必要です。たとえば「利用者の友達の、友達の、友達の…」と入れ子を何十段も重ねた問い合わせ1件で、サーバーが膨大な検索をすることになります。問い合わせの深さや量に上限を設けて防ぎます。

💡 コツ: 試験では「クライアント側で検証しているから安全」「API キーがあるから認証は十分」が定番のひっかけです。検証はサーバー側、キーは単体では不十分、と反射で答えられるようにしましょう。

### 確認問題

**問1.** 公開 API に対して攻撃者がスクリプトで毎秒数千件のリクエストを送り、サービスの応答が劣化しています。この攻撃の影響を抑える対策として最も適切 (BEST) なのはどれですか。

1. API のドキュメントを非公開にする
2. クライアントアプリに利用規約への同意画面を追加する
3. API ゲートウェイでレート制限とスロットリングを適用する
4. API のエンドポイント URL を推測しにくい文字列に変更する

<details><summary>答えと解説</summary>

正解: **3**

大量リクエストによる資源枯渇には、呼び出し回数を制御するレート制限・スロットリングが直接効きます。API ゲートウェイで適用すれば全 API に一貫した統制をかけられます。ドキュメント非公開や URL の難読化は「隠蔽によるセキュリティ (security through obscurity)」で、自動スキャンにはほぼ無力です。同意画面は法的・UI 上の対策であり、スクリプトによる攻撃は止められません。ひっかけ: 「隠す」系の選択肢は、技術的統制を問う問題ではまず誤答です。

</details>

**問2.** 社内のマイクロサービス間の通信を保護する方法として、双方のサービスが互いを証明書で認証し合う仕組みはどれですか。

1. mTLS (相互 TLS)
2. API キーの共有
3. Basic 認証
4. IP アドレス制限

<details><summary>答えと解説</summary>

正解: **1**

mTLS (mutual TLS) は通常の TLS と異なり、サーバーだけでなくクライアント側も証明書を提示して相互に認証します。サービス間通信の暗号化となりすまし防止を同時に実現でき、サービスメッシュの基盤技術にもなっています。API キーの共有や Basic 認証は漏えい時の失効・ローテーションが難しく、「相互の」認証にはなりません。IP アドレス制限は境界統制としては補助になりますが、認証ではなくスプーフィングや内部侵害に弱い点が課題です。ひっかけ: 「双方が認証し合う」というキーワードが出たら mTLS です。

</details>

**問3.** Web フォームの入力チェックについて、セキュリティ上最も正しい考え方はどれですか。

1. JavaScript でクライアント側検証を行っていれば、サーバー側の検証は省略できる
2. 入力検証はユーザビリティの問題であり、セキュリティとは無関係である
3. クライアント側検証はサーバー側検証より堅牢なので優先すべきである
4. クライアント側検証は補助にすぎず、入力検証は必ずサーバー側で行う

<details><summary>答えと解説</summary>

正解: **4**

クライアント側の検証はブラウザの開発者ツールや API の直接呼び出しで簡単にバイパスできるため、セキュリティ統制としては信頼できません。サーバー側での検証(ホワイトリスト方式が望ましい)が必須で、クライアント側検証は入力ミスを早く知らせる利便性のための補助です。クライアント側検証を信頼してよいとする2つの選択肢はその逆を述べており、「入力検証はユーザビリティの問題であり…」は入力検証がインジェクション攻撃対策の中核であることを無視しています。ひっかけ: 「クライアントで検証済みだから安全」というシナリオが出たら、まずバイパス可能性を疑いましょう。

</details>

**問4.** マイクロサービス環境で、データベースの接続パスワードなどのシークレットを管理する方法として最も適切 (BEST) なのはどれですか。

1. 各サービスのソースコードに定数として埋め込み、リポジトリで一元管理する
2. 専用のシークレット管理基盤に保管し、実行時に取得して定期的にローテーションする
3. 全サービスで同じパスワードを使い、管理対象を1つに減らす
4. 設定ファイルに平文で記載し、ファイル名を推測されにくいものにする

<details><summary>答えと解説</summary>

正解: **2**

シークレットは専用の管理基盤(ボールト)に集約し、アクセス制御と監査ログのもとで実行時に取得、漏えいに備えて定期ローテーションするのが原則です。ソースコードやリポジトリへの埋め込みは、リポジトリにアクセスできる全員(および流出先)に漏れる典型的な事故原因です。パスワードの使い回しは1件の漏えいが全サービスの侵害につながり、平文の設定ファイルはファイル名を変えても隠蔽にすぎません。ひっかけ: 「管理が楽になる」方向の選択肢は、リスクを集中させていないか確認しましょう。

</details>

**問5.** セキュリティ監査で、どの部署が管理しているか不明な API エンドポイントが複数発見されました。再発を防ぐための対応として最初に行うべき (FIRST) ものはどれですか。

1. すべての API 通信を禁止するファイアウォールルールを適用する
2. 発見されたエンドポイントを直ちに削除する
3. GraphQL への移行プロジェクトを開始する
4. API インベントリを整備し、すべての API を API ゲートウェイ経由に集約する

<details><summary>答えと解説</summary>

正解: **4**

管理されていない「シャドー API」の根本原因は資産の可視性不足です。まずインベントリ(台帳)を整備して全 API を把握し、ゲートウェイ経由に集約すれば、認証・レート制限・ログという統制を漏れなくかけられます。全面禁止は業務を止める過剰反応で、エンドポイントの即時削除は依存する業務を壊すおそれがあり、調査が先です。GraphQL への移行は問題と無関係です。ひっかけ: CISSP では「守れないものは、まず見えるようにする」=資産管理が FIRST になる典型パターンです。

</details>

**問6.** API の認証に「期限のない固定の API キー」だけを使う方式が弱いとされる主な理由はどれですか？

1. 漏えいしても気づきにくく、期限がないため盗まれたキーが長く使われ続けるから
2. API キーは暗号化通信 (TLS) と同時に使えないから
3. API キーは文字数が短すぎて必ず総当たりで破られるから
4. API キーを使うと API ゲートウェイを設置できなくなるから

<details><summary>答えと解説</summary>

正解: **1**

API キーは固定の文字列で、コードやログに紛れて漏えいしても気づきにくく、期限もないため盗まれると失効させるまで使われ続けます。そのため OAuth 2.0 の短命トークン(数分〜1時間で失効)や、サービス間なら mTLS と組み合わせるのが望ましいとされます。API キーは TLS と一緒に使うのが普通で、長さは十分に取れるので総当たりが主な理由ではありません。API ゲートウェイで API キーを検証するのも一般的な構成です。

</details>

## 3. ソフトウェア調達とサードパーティコード

### 「買う・借りる・もらう」コードの統制

現代のシステムは自社開発コードよりも、市販品や OSS など**他人が書いたコード**の割合が圧倒的に大きいのが普通です。CISSP では「調達形態ごとに何を評価すべきか」が問われます。

表のライセンスはソフトの利用条件です。たとえば GPL という OSS ライセンスでは、改変したものを配布するならソースコードも公開する義務があり、知らずに製品に組み込むと契約違反になり得ます。SOC 2 Type II は第5章で見た SOC 報告書の一種で、独立監査人が一定期間の統制の運用を確かめたもの、責任分界は第10章で見た「クラウド事業者と自社の責任の境目」です。

| 形態 | 中身は見えるか | 評価の中心 |
|---|---|---|
| **COTS** (Commercial Off-The-Shelf。市販のパッケージソフト) | 見えない(ブラックボックス) | ベンダーの実績、**パッチ提供と脆弱性対応の体制**、サポート期間 |
| **OSS** (オープンソースソフトウェア。ソースが公開され誰でも使える) | 見える | コミュニティの活発さ、ライセンス、既知脆弱性、保守の継続性 |
| **カスタム開発(委託)** | 契約次第 | 開発プロセスの統制、コードの権利、受入テスト |
| **SaaS** (Web メールのようにネット越しに使うソフト) | 見えない(運用も相手) | 事業者の内部統制(**SOC 2 Type II** 報告書等)、責任分界、データの扱い |

### SBOM — ソフトウェアの「原材料表示」

**SBOM (Software Bill of Materials)** は、製品に含まれるコンポーネントとバージョンの一覧です。重大な脆弱性が公表されたとき、「うちはどの製品で使っているか」を即座に特定できます。

| コンポーネント | バージョン | ライセンス |
|---|---|---|
| log4j-core | 2.14.1 | Apache-2.0 |
| openssl | 3.0.13 | Apache-2.0 |
| jquery | 3.7.1 | MIT |

たとえば Log4j の重大な脆弱性(Log4Shell)が公表されたとき、全製品の SBOM から「log4j-core の影響を受けるバージョン(2.14.1 など)」を検索すれば、該当製品の一覧がすぐに出ます。SBOM の書式には SPDX や CycloneDX があります。OSS のリスク管理(既知脆弱性・ライセンス違反)でも中心的な道具です。

### 契約とサプライヤー管理

調達契約には、**脆弱性の通知義務、パッチ提供義務、サポート期間、監査権 (right to audit)** などのセキュリティ要件を盛り込みます。マネージドサービスやクラウドでは**責任分界**(どこまでが事業者、どこからが自社か)を文書で明確にします。サードパーティライブラリは「信頼できる配布元から取得し、バージョンを固定し、継続的に更新する」が原則です。Python なら依存関係を書く requirements.txt に次のように書きます。

```text
requests==2.32.3
```

`==` は「このバージョンだけを使う」という固定の指定です。指定しないと、取得のたびに最新版が入り、知らないうちに中身の違うものが紛れ込むおそれがあります。固定したうえで、SCA の通知を見て計画的に更新します。偽物にも注意が要ります。有名パッケージに似た名前の偽物(`requests` に対する `reqeusts` など)を登録して誤入力を待つ手口を**タイポスクワッティング**と呼びます。

💡 コツ: 「COTS はソースが見えない→ベンダーの体制を評価」「SaaS は運用ごと任せる→第三者監査報告書 (SOC 2) で確認」。中身を見られないものほど、相手の統制を文書と実績で確かめるのが CISSP 的な答えです。

### 確認問題

**問1.** 市販のパッケージソフトウェア (COTS) を基幹業務に導入する際、セキュリティ評価として最も重視すべき (MOST) なのはどれですか。

1. ソースコードの全行レビューを自社で実施すること
2. 画面デザインが自社の他システムと統一されていること
3. 開発言語が自社の標準と一致していること
4. ベンダーの脆弱性対応・パッチ提供体制とサポート期間を評価すること

<details><summary>答えと解説</summary>

正解: **4**

COTS はソースコードが開示されないブラックボックスなので、自社でコードレビューを行うことは通常できません。だからこそ、ベンダーが脆弱性にどれだけ迅速に対応しパッチを提供し続けるか、サポート期間はいつまでかという「相手の体制」の評価が中心になります。画面デザインや開発言語は運用性の観点であり、セキュリティ評価の中心ではありません。ひっかけ: 「自社でソースを精査する」は OSS やカスタム開発なら可能ですが、COTS では前提からして成立しません。

</details>

**問2.** 広く使われる OSS ライブラリに重大な脆弱性が公表されました。自社の多数の製品のうち、どれが影響を受けるかを迅速に特定するために最も有効なのはどれですか。

1. 全製品の SBOM (ソフトウェア部品表) を照会する
2. 全開発者にメールで心当たりを尋ねる
3. 全製品に対して DAST を実行する
4. 当該ライブラリの開発コミュニティに問い合わせる

<details><summary>答えと解説</summary>

正解: **1**

SBOM は製品ごとの構成コンポーネントとバージョンの一覧なので、「どの製品がこのライブラリを含むか」を機械的に即答できます。開発者への聞き取りは漏れと時間のロスが大きく、DAST は外部からの挙動テストであり特定ライブラリの使用有無の確認には不向きです。コミュニティへの問い合わせでは自社の使用状況は分かりません。ひっかけ: Log4j 型のシナリオ(有名 OSS の脆弱性公表)とくれば、答えの軸は SBOM / SCA による構成の可視化です。

</details>

**問3.** SaaS 事業者を選定するにあたり、その事業者のセキュリティ統制が有効に運用されているかを確認する方法として最も適切 (BEST) なのはどれですか。

1. 事業者の営業資料に記載されたセキュリティ機能一覧を確認する
2. 事業者の Web サイトの導入事例の数を確認する
3. 独立監査人による SOC 2 Type II 報告書をレビューする
4. 自社で事業者のデータセンターに侵入テストを行う

<details><summary>答えと解説</summary>

正解: **3**

SOC 2 Type II は独立した監査人が、一定期間にわたり統制が「実際に運用されて有効だったか」を検証した報告書であり、第三者による客観的な証拠になります。営業資料や導入事例は自己申告・実績数にすぎず、統制の有効性は証明しません。他社インフラへの無断の侵入テストは契約・法律違反になり得ます(実施するなら契約と許可が前提)。ひっかけ: Type I は「ある時点の設計」の評価のみです。「運用の有効性」と来たら Type II を選びます。

</details>

**問4.** 重要システム向けソフトウェアの調達契約に盛り込むセキュリティ要件として、最も適切な組み合わせはどれですか。

1. 脆弱性発見時の通知義務、パッチ提供義務、監査権 (right to audit)
2. 値引き率の保証、営業担当者の固定、四半期ごとの会食
3. ソフトウェアの全機能の無償カスタマイズ権
4. 障害発生時にベンダーの全責任を免除する条項

<details><summary>答えと解説</summary>

正解: **1**

調達契約は、納入後のセキュリティをベンダーに履行させる法的な拘束力を持つ唯一の手段です。脆弱性の通知、パッチ提供、監査権(自社または第三者がベンダーの統制を検証できる権利)は代表的な要件です。値引きや営業体制は商務条件でセキュリティ要件ではなく、無償カスタマイズ権は現実的でないうえ論点が違います。ベンダーの全責任免除は自社がリスクを丸ごと抱える逆効果の条項です。ひっかけ: 「契約で何を担保するか」という問題では、拘束力のあるセキュリティ条項を選びます。

</details>

**問5.** 開発チームがインターネット上の個人ブログで紹介されていたライブラリを、紹介記事内のリンクから直接ダウンロードして本番コードに組み込みました。この行為の最大のリスクはどれですか。

1. ライブラリのドキュメントが英語である可能性
2. ライブラリの実行速度が遅い可能性
3. 改ざんされた、または悪意あるコードを含む配布物を取り込む可能性
4. ライブラリの UI が自社デザインと合わない可能性

<details><summary>答えと解説</summary>

正解: **3**

信頼できない配布元からの取得は、改ざん版やマルウェア入りパッケージ(タイポスクワッティングや偽ミラーなど)を取り込むサプライチェーン攻撃の典型的な入口です。公式リポジトリなど信頼できるソースから取得し、署名やハッシュで完全性を検証し、バージョンを固定して SCA で監視するのが原則です。ドキュメントの言語、速度、UI は品質・運用の論点であり、「最大のリスク」というセキュリティの問いへの答えではありません。ひっかけ: 問題文の異常ポイントは「個人ブログのリンクから直接」です。出所の信頼性に着目しましょう。

</details>
