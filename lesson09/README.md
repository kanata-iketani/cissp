# 第9章 セキュア設計原則とセキュリティモデル【D3】

この章では、セキュアなシステム設計の土台となる設計原則と、CISSP 頻出のセキュリティモデル（Bell-LaPadula・Biba・Clark-Wilson など）を学びます。「どのモデルが機密性・完全性のどちらを守るのか」「ルールの向き（読み・書きの禁止方向）はどちらか」を混同せずに言えるようになるのがゴールです。

## 1. セキュア設計原則

### 設計の段階でセキュリティを組み込む

CISSP では「後付けのセキュリティ」ではなく、**設計段階から組み込む**考え方が一貫して問われます。代表的な設計原則を押さえましょう。

| 原則 | 意味 |
|---|---|
| 最小権限 (least privilege) | 業務に必要な最小限の権限だけを与える（似た考え方の need to know は「その仕事に必要な情報だけを知らせる」原則。L19 で詳しく扱う） |
| 多層防御 (defense in depth) | 1つの対策に頼らず、複数の層で守る |
| 職務分掌 (separation of duties) | 重要な処理を1人で完結させない（不正の抑止。例: 支払先の登録と支払の承認を別の人にする） |
| セキュアデフォルト (secure defaults) | 初期設定の時点で安全な状態にしておく |
| KISS (Keep It Simple) | 複雑さは脆弱性の温床。シンプルに保つ |
| プライバシーバイデザイン (privacy by design) | 個人情報保護を設計段階から組み込む |

**最小権限の具体例**: 経理担当の佐藤さんのアカウントを見直します。

| 権限 | 業務に必要か | 最小権限での扱い |
|---|---|---|
| 経費精算システムの閲覧・入力 | 必要 | 与える |
| 経費精算システムの承認 | 不要（上長の仕事） | 与えない |
| 全社ファイルサーバの全フォルダの読み書き | 不要（経理フォルダだけで足りる） | 経理フォルダの読み書きだけに絞る |
| サーバの管理者権限 | 不要 | 与えない |

こうしておけば、佐藤さんのアカウントが乗っ取られても、攻撃者ができるのは経理フォルダの範囲に限られます。この「侵害されたときに被害が及ぶ範囲」を**ブラストラディウス (blast radius)** と呼びます。逆に、異動のたびに権限を足すだけで外さずにいると、不要な権限がたまっていきます。これを**権限の肥大化 (privilege creep)** と呼びます。

**セキュアデフォルトの具体例**: ファイアウォールのルールは上から順に評価され、最初に当てはまった行で許可・拒否が決まります。

```
1  許可  送信元 any            → 宛先 203.0.113.5:443  （公開 Web サーバへの https）
2  許可  送信元 192.0.2.0/24   → 宛先 203.0.113.5:22   （社内からの SSH 管理接続）
3  拒否  送信元 any            → 宛先 any              （ここまでに当たらなければすべて拒否）
```

外部の 198.51.100.7 から 203.0.113.5 の 22 番（SSH）に来た通信は、1行目（宛先ポートが違う）にも2行目（送信元が 192.0.2.0/24 ではない）にも当たらず、3行目で拒否されます。このように「明示的に許可したもの以外はすべて拒否」とする考え方を**既定拒否 (implicit deny / default deny)** と呼びます。ネットワークの詳細は L14・L15 で扱います。機能を多く有効にするほど、攻撃者が狙える入口（**攻撃対象領域 / attack surface**）が増える、という点もセットで押さえましょう。

### フェイルセキュアとフェイルオープン

障害時にどちらに倒すかは**何を守るか**で決まります。

- **フェイルセキュア (fail-secure / fail-closed)**: 障害時に閉じる・拒否する。情報やシステムの保護を優先（例: ファイアウォール障害時は全遮断）
- **フェイルオープン (fail-open / fail-safe)**: 障害時に開く・許可する。**人の安全 (human safety) が絡む場合はこちら**（例: 火災時、データセンターの電気錠ドアは開いて避難を可能にする）

💡 コツ: CISSP では「人命 > 情報資産」が鉄則です。人の安全が選択肢に絡んだら、ほぼ例外なく人命優先が正解です。

### ゼロトラスト

従来の境界型防御（社内ネットワークと社外の間にファイアウォールなどの「境界」を置き、内側は信頼する考え方。trust but verify とも表現される）は、内部犯行やラテラルムーブメント（侵入後の横移動）に弱いという限界があります。たとえば社内 PC 1台がマルウェアに感染すると、境界の内側なのでほかのサーバにも自由に接続できてしまいます。**ゼロトラスト (zero trust)** は「決して信頼せず、常に検証する (never trust, always verify)」が合言葉で、場所（社内/社外）ではなく、アクセスごとに本人・デバイス・文脈を検証します。マイクロセグメンテーション（ネットワークをサーバ単位など細かく区切り、区画間の通信を個別に許可すること）や継続的な認証（ログイン時だけでなく、アクセスのたびや一定時間ごとに確認し直すこと）と組み合わせて実現します。詳細は L15 で扱います。

### 確認問題

**問1.** データセンターの電気錠つき非常ドアを設計しています。火災で電源が失われた場合の挙動として、最も適切 (BEST) なものはどれでしょう？

1. 施錠されたままにして、不正侵入を防ぐ
2. 警備員が駆けつけるまで半開きで待機する
3. 解錠して、内部の人が避難できるようにする
4. 入室は拒否するが退室はバッジ認証を要求する

<details><summary>答えと解説</summary>

正解: **3**

人の安全 (human safety) が絡む場面では、フェイルオープン（障害時に開く）が正解です。CISSP では常に「人命は情報資産より優先」が鉄則です。施錠されたまま（フェイルセキュア）は資産保護としては正しくても、避難を妨げるため不適切です。退室にバッジ認証を要求する案も、停電時に認証できず人を閉じ込めるおそれがあります。「不正侵入を防ぐ」という選択肢は、情報保護を優先させるひっかけです。

</details>

**問2.** 経理担当者が「支払先の登録」と「支払の承認」の両方を1人で実行できる状態になっていました。この状況が主に違反している設計原則はどれでしょう？

1. 職務分掌 (separation of duties)
2. 多層防御 (defense in depth)
3. セキュアデフォルト (secure defaults)
4. KISS（シンプルに保つ）

<details><summary>答えと解説</summary>

正解: **1**

重要な処理の開始から完了までを1人で実行できると、不正（架空の支払先を登録して自分で承認する等）を1人で完結できてしまいます。これを防ぐのが職務分掌です。多層防御は「複数の対策の層で守る」原則で、権限の分割とは論点が異なります。セキュアデフォルトは初期設定の話、KISS は複雑さを避ける話なので、いずれも本問の状況とは合いません。

</details>

**問3.** 最小権限 (least privilege) の説明として、最も適切なものはどれでしょう？

1. すべての利用者に同じ標準権限を与えて管理を簡素化する
2. 管理者権限は信頼できる上位役職者にまとめて付与する
3. 権限は申請があればその都度すべて承認する
4. 業務の遂行に必要な最小限の権限だけを与える

<details><summary>答えと解説</summary>

正解: **4**

最小権限は「その業務に必要な分だけ」権限を与える原則で、侵害時の被害範囲（ブラストラディウス）を小さくします。全員に同じ権限を与えるのは管理は楽でも過剰権限を生みます。役職が高いことは権限の必要性を意味しない点に注意してください（役職ベースの付与は need to know の無視になりがちです）。申請を無条件に承認する運用は権限の肥大化（privilege creep）を招きます。

</details>

**問4.** 境界型防御からゼロトラストアーキテクチャへ移行する最大の動機として、最も適切 (MOST) なものはどれでしょう？

1. 境界ファイアウォールが不要になりコストを削減できるから
2. 社内ネットワークに入った攻撃者の横移動（ラテラルムーブメント）を前提に、アクセスごとに検証する必要があるから
3. VPN の通信速度がゼロトラストより遅いから
4. すべての従業員を無条件に信頼できるようになるから

<details><summary>答えと解説</summary>

正解: **2**

ゼロトラストは「社内＝安全」という前提を捨て、侵入済みの攻撃者や内部不正による横移動に備えて、アクセスごとに本人・デバイス・文脈を検証します（never trust, always verify）。ファイアウォールが不要になるわけではなく、多層防御の一部として残ります。速度は主目的ではありません。「従業員を無条件に信頼する」はゼロトラストの正反対で、典型的なひっかけです。

</details>

**問5.** データセンターの境界ファイアウォールが故障したときの挙動を設計します。人の安全には関係しない機器だとすると、最も適切 (BEST) な設計はどれでしょう？

1. 故障時はすべての通信を許可し、業務を止めない
2. 故障時は管理者の判断を待つまで、直前の通信だけ許可し続ける
3. 故障時は再起動を繰り返して自動復旧を試み、その間は通信を許可する
4. 故障時はすべての通信を遮断する

<details><summary>答えと解説</summary>

正解: **4**

人の安全に関わらない情報システムでは、障害時に閉じて拒否するフェイルセキュア (fail-secure / fail-closed) が基本です。ファイアウォールが故障したまま通信を通すと、検査されない通信が内部に入ってしまいます。「すべて許可」や「復旧を試みる間は許可」はフェイルオープンで、可用性を優先して情報資産を危険にさらします。「直前の通信だけ許可し続ける」も、検査できない状態で通信を通す点で同じ問題があります。人命が絡む電気錠の非常ドアとは逆の結論になる、という対比で覚えましょう。

</details>

**問6.** 新しい社内システムの初期設定を検討しています。「セキュアデフォルト (secure defaults)」に最もよく合致する方針はどれでしょう？

1. 利便性のため全機能を有効にして出荷し、不要なら利用者が無効化する
2. 初期パスワードは全端末で共通にして導入作業を速くする
3. 不要なサービスは無効、通信は拒否を既定とし、必要なものだけ明示的に許可する
4. 設定変更の自由度を最大化するため、既定では制限を設けない

<details><summary>答えと解説</summary>

正解: **3**

セキュアデフォルトは「初期状態が安全」であることです。既定拒否（implicit deny）とし、必要なものだけ許可するのが基本です。全機能有効での出荷は攻撃対象領域（attack surface）を広げます。共通初期パスワードは推測・使い回しのリスクが高く重大な欠陥です。「既定で制限なし」は許可デフォルトであり、原則の正反対です。利便性を理由にした選択肢はひっかけになりやすいので注意しましょう。

</details>

## 2. 機密性のモデル — Bell-LaPadula

### 基礎の基礎 — 主体・客体・レベル

この章からは、アクセス制御（誰に何を許すか）を理論で扱います。まず4つの言葉をそろえましょう。

- **主体 (subject)**: アクセスする側。人やプログラム（プロセス）
- **客体 (object)**: アクセスされる側。ファイル、データベース、プリンタなど。オブジェクトとも呼びます
- **クリアランス (clearance)**: 主体に与えられた「どのレベルまで扱ってよいか」の資格
- **分類レベル (classification)**: 客体に付けられた機密のレベル（L07 で見た分類と同じ考え方）

この章では、上から **極秘 (Top Secret) > 秘 (Secret) > 取扱注意 (Confidential) > 区分なし (Unclassified)** の4段階を使います。

**MAC (強制アクセス制御)** は、このレベルの比較でシステムが一律にアクセスを決める方式です。ファイルの持ち主でも、ルールに反するアクセスは許可できません。これに対し、持ち主が自分の判断で権限を与えられる方式を **DAC (任意アクセス制御)** と呼びます（詳しくは L19）。

### セキュリティモデルとは

セキュリティモデルは「守りたい性質（機密性・完全性など）を数学的なルールで表現したもの」です。多くは**状態機械モデル (state machine model)**（どの状態遷移でも安全な状態を保つ）と**情報フローモデル (information flow model)**（情報の流れる方向を制御する）を土台にしています。

状態機械モデルの「状態」とは、ある瞬間の「どの主体がどの客体にどんなアクセスをしているか」の一覧です。たとえば「状態1: 佐藤が週報を読んでいる」から「状態2: 佐藤が作戦計画も読む」へ移るとき、状態2が安全でなければその遷移（変化）は拒否されます。最初が安全で、すべての遷移が安全な状態にしか移らないなら、システムはずっと安全だ、という考え方です。

また、機密レベルと区画（カテゴリ）の組み合わせで上下関係を定義する**ラティス (lattice-based)** 構造を使います。区画は「核」「暗号」のような話題ごとの仕切りで、need to know を表します。

| 主体のクリアランス | 客体のラベル | 読めるか | 理由 |
|---|---|---|---|
| 極秘 {核, 暗号} | 秘 {核} | 読める | レベルが上で、区画 {核} も持っている |
| 極秘 {暗号} | 秘 {核} | 読めない | レベルは上だが、区画 {核} を持っていない |
| 秘 {核} | 極秘 {核} | 読めない | レベルが下 |

レベルが上かつ区画もすべて含むときに「主体が客体を**支配する (dominate)**」と言い、BLP の「読める」の条件はこの支配関係です。

### Bell-LaPadula（BLP）— 機密性のモデル

軍の機密情報保護のために作られた、**機密性 (confidentiality) だけ**を守るモデルです。MAC（強制アクセス制御）の代表例で、2つの基本ルールがあります。

| ルール | 内容 | 覚え方 |
|---|---|---|
| 単純セキュリティプロパティ (simple security property) | **上読み禁止 (no read up)** | 自分より上位の機密は読めない |
| *（スター）プロパティ (star property) | **下書き禁止 (no write down)** | 自分より下位に書き込めない（機密の漏えい防止） |

「下書き禁止」が直感に反するポイントです。上位レベルの人が下位レベルの文書に書き込むと、**機密情報が低いレベルへ漏れる**おそれがあるため禁止されます。さらに**強い*プロパティ (strong star property)** では、読み書きとも**自分と同じレベルのみ**に制限されます。

### 一段ずつ確かめる — 「秘」の佐藤さんの場合

主体: 佐藤さん（クリアランス **秘**）。客体は次の4つです。

| 客体 | 分類レベル | 佐藤から見て | 読む | 書く | 判定の理由 |
|---|---|---|---|---|---|
| 作戦計画.doc | 極秘 | 上 | ✕ | ○ | 読む: 上読み禁止。書く: 上へ書くのは機密が漏れないので可 |
| 週報.doc | 秘 | 同じ | ○ | ○ | 同じレベルは読み書きとも可 |
| 部内連絡.doc | 取扱注意 | 下 | ○ | ✕ | 読む: 下は読める。書く: 下書き禁止 |
| 公開資料.doc | 区分なし | 下 | ○ | ✕ | 同上 |

強い*プロパティなら、○ が残るのは「週報.doc」の行だけになります。

**なぜ下に書いてはいけないのか**: もし書けるとすると、次の2手で機密が漏れます。

1. 佐藤さん（秘）が週報.doc（秘）を読む → ここまでは正当
2. 内容を公開資料.doc（区分なし）に書き写す → 区分なしのクリアランスの人がそれを読める

佐藤さん本人に悪意がなくても、佐藤さんの権限で動くマルウェア（トロイの木馬）が勝手に書き写すことがあります。BLP はこれを「下に書く操作そのもの」を禁止して防ぎます。

逆に「作戦計画.doc（極秘）に書く」は、秘の情報が極秘の場所に移るだけなので機密は漏れません。ただし佐藤さんは極秘を読めないため、何が書いてあるか見ずに書き込むことになります（**blind write**）。

BLP にはもう1つ、**任意セキュリティプロパティ (discretionary security property)** があり、レベルの条件を満たしたうえで、アクセス制御マトリクス（ch04 で扱う「誰が何にどんな権限を持つか」の表）でも個別に許可されている必要があります。

💡 コツ: simple＝read、star(*)＝write と機械的に対応づけましょう。これは次章の Biba でもそのまま使えます。

### BLP の限界

- **完全性は守らない**: 下位の主体が上位に書き込む（blind write）のは許されるため、データ汚染は防げません
- **可用性・隠れチャネル (covert channel。本来の通信路ではない手段で情報が漏れる経路。ch04 で扱う) は扱わない**
- **トラステッドサブジェクト (trusted subject)**: 機密レベルの変更（declassification。たとえば期限が来た極秘文書を区分なしに引き下げる操作）など、*プロパティの例外を許される特別な主体。厳格な検証が前提です

### 確認問題

**問1.** Bell-LaPadula モデルの「*（スター）プロパティ」が表すルールはどれでしょう？

1. 上読み禁止 (no read up)
2. 下書き禁止 (no write down)
3. 下読み禁止 (no read down)
4. 上書き禁止 (no write up)

<details><summary>答えと解説</summary>

正解: **2**

BLP の *プロパティは「下書き禁止 (no write down)」です。上位の機密を知る主体が下位レベルへ書き込むと機密が漏えいするため禁止されます。「上読み禁止」は単純セキュリティプロパティ（simple security property）です。「下読み禁止」「上書き禁止」は完全性モデルである Biba のルールで、BLP と向きが逆になる典型的なひっかけです。simple＝read、star＝write の対応を思い出しましょう。

</details>

**問2.** 「秘 (Secret)」レベルの職員が、「極秘 (Top Secret)」の文書を開こうとして拒否されました。Bell-LaPadula のどのルールによるものでしょう？

1. *（スター）プロパティ
2. 強い*プロパティ
3. トラステッドサブジェクトの原則
4. 単純セキュリティプロパティ

<details><summary>答えと解説</summary>

正解: **4**

自分より上位レベルの情報を読むことを禁止するのは、単純セキュリティプロパティ（simple security property、no read up）です。*プロパティは「書き込み」の制限（no write down）なので、読み取りの拒否とは関係ありません。強い*プロパティは読み書きとも同一レベルに限定する強化ルールですが、本問は基本の読み取り制限で説明できます。トラステッドサブジェクトはルールの例外を許される主体のことで、拒否の根拠ではありません。

</details>

**問3.** Bell-LaPadula モデルの限界として、最も適切 (MOST) な指摘はどれでしょう？

1. 機密性のみを対象とし、データの完全性や可用性は守らない
2. 任意アクセス制御 (DAC) 専用で、軍のシステムには適用できない
3. 読み取りを一切禁止するため実用に耐えない
4. 暗号化アルゴリズムの強度を定義していない

<details><summary>答えと解説</summary>

正解: **1**

BLP は機密性 (confidentiality) に特化したモデルで、完全性（下位主体による上位への blind write を許すためデータ汚染を防げない）や可用性は扱いません。だからこそ完全性を守る Biba や Clark-Wilson が別に存在します。BLP は軍の機密保護を目的に生まれた MAC（強制アクセス制御）の代表例なので「DAC 専用」「軍に適用できない」は逆です。読み取りは同位・下位レベルなら可能なので「一切禁止」も誤りです。暗号強度はそもそもアクセス制御モデルの守備範囲外です。

</details>

**問4.** Bell-LaPadula モデルで、クリアランス「秘 (Secret)」の主体が、分類「取扱注意 (Confidential)」の文書に対してできる操作はどれでしょう？（強い*プロパティは適用しないものとします）

1. 読むことも書くこともできる
2. 読むことはできるが、書くことはできない
3. 書くことはできるが、読むことはできない
4. 読むことも書くこともできない

<details><summary>答えと解説</summary>

正解: **2**

取扱注意は秘より下のレベルです。単純セキュリティプロパティ（no read up）が禁止するのは上を読むことなので、下は読めます。一方、*プロパティ（no write down）により下へ書くことは禁止されます。秘の情報が取扱注意の文書へ書き写されると、取扱注意のクリアランスしかない人に機密が漏れるからです。「書けるが読めない」は上位レベル（極秘）の文書に対する扱い（blind write）で、向きが逆です。読み書きとも可は同じレベルの文書の場合です。

</details>

**問5.** 強い*プロパティ (strong star property) の内容として正しいものはどれでしょう？

1. どのレベルにも自由に読み書きできる
2. 下位レベルへの読み取りだけを禁止する
3. 自分と同じ機密レベルに対してのみ読み書きできる
4. 上位レベルへの書き込みだけを許可する

<details><summary>答えと解説</summary>

正解: **3**

強い*プロパティは、通常の *プロパティ（no write down）をさらに強め、読み書きとも自分と同一レベルに限定するルールです。通常の BLP では下位への読み取りや上位への書き込み（blind write）は許されますが、強い*プロパティではそれも不可になります。「自由に読み書き」はモデルの否定、「下位への読み取り禁止」は Biba の simple integrity と混同させるひっかけ、「上位への書き込みだけ許可」は通常の *プロパティの説明に近く、強い版の説明ではありません。

</details>

**問6.** 機密レベルの引き下げ（declassification）のように、*プロパティの例外的な操作を許される Bell-LaPadula 上の存在はどれでしょう？

1. セキュリティカーネル (security kernel)
2. トラステッドサブジェクト (trusted subject)
3. リファレンスモニタ (reference monitor)
4. データオーナー (data owner)

<details><summary>答えと解説</summary>

正解: **2**

トラステッドサブジェクトは、厳格に検証されたうえで *プロパティ（no write down）の例外を許される特別な主体で、機密指定の解除や引き下げなどを担います。リファレンスモニタはアクセスの可否を検証する抽象概念、セキュリティカーネルはそれを実装する TCB の中核で、どちらも「例外を許される主体」ではありません。データオーナーは分類の決定に責任を持つ役割ですが、BLP のルール上の例外主体を指す用語ではありません。

</details>

## 3. 完全性のモデル — BibaとClark-Wilson

### Biba — BLP を逆さにした完全性モデル

Biba は**完全性 (integrity) だけ**を守るモデルです。「信頼できない（完全性の低い）情報が、信頼性の高いデータを汚染しないようにする」ことが目的で、ルールの向きは BLP の**ちょうど逆**です。

| モデル | read のルール | write のルール | 守るもの |
|---|---|---|---|
| Bell-LaPadula | 上読み禁止 (no read up) | 下書き禁止 (no write down) | 機密性 |
| Biba | **下読み禁止 (no read down)** | **上書き禁止 (no write up)** | 完全性 |

- **単純完全性プロパティ (simple integrity property)**: 下読み禁止。信頼性の低い情報を読んで判断を汚染されない
- **\*（スター）完全性プロパティ (star integrity property)**: 上書き禁止。信頼性の低い主体が高品質なデータを書き換えられない
- **呼び出しプロパティ (invocation property)**: 主体は、自分より完全性レベルの高い主体（プログラム）を呼び出して代わりに処理させることができない

ここでの「上・下」は機密の高さではなく**信頼できる度合い（完全性レベル）**です。「書き換えられては困る・内容が正しいと確認済み」ほど上になります。

### 一段ずつ確かめる — 完全性レベル「中」の業務アプリの場合

主体: 受注処理アプリ（完全性レベル **中**）。客体は次の3つです。

| 客体 | 完全性レベル | アプリから見て | 読む | 書く | 判定の理由 |
|---|---|---|---|---|---|
| 監査済みの商品マスタ | 高 | 上 | ○ | ✕ | 読む: 上の正しい情報は読んでよい。書く: 上書き禁止 |
| 受注データ | 中 | 同じ | ○ | ○ | 同じレベルは読み書きとも可 |
| ネットからダウンロードした価格表.csv | 低 | 下 | ✕ | ○ | 読む: 下読み禁止。書く: 下へ書いても上のデータは汚れないので可 |

BLP の表（ch02）と見比べると、○ と ✕ の位置がちょうど上下逆になっています。出所の分からない価格表.csv を読んで受注データを計算すると、誤った値が「中」のデータに混ざる（汚染される）ため、Biba は読むこと自体を止めます。

💡 コツ: 「機密は下に漏らすな（BLP）、ゴミは上に流すな（Biba）」。この対比表は丸ごと暗記する価値があります。

### Clark-Wilson — 商用の完全性モデル

Biba がレベルの上下だけで考えるのに対し、**Clark-Wilson** は商用取引の現実に合わせたモデルです。キーワードは次の3つです。

1. **整形式トランザクション (well-formed transaction)**: データは検証済みのプログラムを通してしか変更できない（トランザクションは「振込」のように、まとめて全部成功するか全部取り消すかの一連の処理）
2. **アクセス三要素 (access control triple)**: 主体 (subject) → プログラム (transformation procedure, TP) → オブジェクト (CDI: constrained data item) という経路を強制し、主体がデータを直接触れない
3. **職務分掌と監査**: 操作する人と検証する人を分け、すべての変更を記録する

そのほかの部品として、**UDI (unconstrained data item)**（まだ検証されていない入力。例: 利用者が画面に入力した振込依頼）と、**IVP (integrity verification procedure)**（CDI が正しい状態かを確かめる検証手続き）があります。

**振込の例で一段ずつ見る**

| 段階 | 部品 | 中身の例 |
|---|---|---|
| 1. 入力 | UDI | 窓口担当の田中さんが「口座 X → 口座 Y へ 30,000 円」と入力 |
| 2. 経路の確認 | アクセス三要素 | 許可リストに (田中, 振込TP, 口座残高表) がある → 田中さんは振込TP を通してのみ口座残高表を変更できる |
| 3. 変更 | TP | 振込TP が残高を確かめ、X: 100,000 → 70,000、Y: 50,000 → 80,000 と更新 |
| 4. 承認 | 職務分掌 | 一定額以上は別の担当者の承認がないと確定しない |
| 5. 記録 | 監査 | `2026-11-13 10:05:12 tanaka 振込TP X→Y 30000 OK` をログに残す |
| 6. 検証 | IVP | 夜間に全口座の残高合計が、入出金の記録と一致するかを照合 |

田中さんがデータベースを直接開いて残高の数字を書き換える経路は用意されていません。これが「主体がデータを直接触れない」の意味です。

銀行の勘定系のように「正しい手続きを通した変更しか許さない」世界観で、**完全性の3目標**（不正な変更の防止・正規ユーザーの誤変更の防止・内部と外部の一貫性維持）をすべて扱える点が Biba より実務的です。

### 確認問題

**問1.** Biba モデルの「単純完全性プロパティ (simple integrity property)」が禁止する操作はどれでしょう？

1. 自分より完全性レベルの低い情報を読むこと (no read down)
2. 自分より完全性レベルの高い情報を読むこと (no read up)
3. 自分より完全性レベルの低いデータへ書き込むこと (no write down)
4. 自分と同じ完全性レベルのデータを読むこと

<details><summary>答えと解説</summary>

正解: **1**

Biba の simple integrity property は「下読み禁止 (no read down)」です。信頼性の低い情報源を読むと、自分の処理や判断がその汚染された情報に基づいてしまうためです。simple＝read の対応は BLP と共通ですが、向きが逆になります。「上読み禁止」は BLP の単純セキュリティプロパティ、「下書き禁止」は BLP の *プロパティで、どちらも機密性モデルのルールを混ぜたひっかけです。同一レベルの読み取りはどちらのモデルでも禁止されません。

</details>

**問2.** Biba モデルで、完全性レベル「中」のプロセスが、完全性レベル「低」のファイル（出所の確認されていないダウンロードファイル）に対してできる操作はどれでしょう？

1. 読むことも書くこともできる
2. 読むことはできるが、書くことはできない
3. 読むことも書くこともできない
4. 書くことはできるが、読むことはできない

<details><summary>答えと解説</summary>

正解: **4**

低は中より下のレベルです。Biba の単純完全性プロパティ（no read down）により、下の信頼できない情報を読むことは禁止されます。読んだ内容で処理すると中のデータが汚染されるからです。一方、*完全性プロパティが禁止するのは上へ書くこと（no write up）なので、下へ書くことはできます。「読めるが書けない」は BLP で下位の文書を扱う場合の答えで、向きを取り違えたひっかけです。読み書きとも可は同じレベルの場合、両方不可はどの基本ルールにも当てはまりません。

</details>

**問3.** 一般の派遣スタッフ用アカウントが、監査済みの基準データ（マスタデータ）を直接更新しようとして拒否されました。Biba モデルで考えた場合、根拠となるルールはどれでしょう？

1. 単純セキュリティプロパティ (no read up)
2. 単純完全性プロパティ (no read down)
3. *（スター）完全性プロパティ (no write up)
4. 強い*プロパティ (同一レベルのみ読み書き可)

<details><summary>答えと解説</summary>

正解: **3**

完全性レベルの低い主体（派遣スタッフ用アカウント）が、より高い完全性レベルのデータ（監査済みマスタ）へ書き込むことを禁止するのは、* 完全性プロパティ（star integrity property、no write up）です。star＝write の対応で判断できます。単純完全性プロパティは「読み」の制限なので書き込み拒否の根拠になりません。単純セキュリティプロパティと強い*プロパティは機密性モデル BLP 側のルールで、完全性の文脈では使いません。

</details>

**問4.** Clark-Wilson モデルの「アクセス三要素 (access control triple)」の構成として正しいものはどれでしょう？

1. ユーザー → オペレーティングシステム → ファイル
2. 主体 → 変換手続き (TP) → 制約付きデータ項目 (CDI)
3. 読み取り → 書き込み → 実行
4. 識別 → 認証 → 認可

<details><summary>答えと解説</summary>

正解: **2**

Clark-Wilson では、主体 (subject) が制約付きデータ項目 (CDI) を直接操作することを禁止し、必ず検証済みの変換手続き (transformation procedure, TP) を経由させます。この「主体・TP・CDI」の3点セットがアクセス三要素です。整形式トランザクション (well-formed transaction) を強制する仕組みそのものと言えます。「読み書き実行」はアクセス権の種類、「識別・認証・認可」はアクセス管理の流れ (IAA) で、いずれも用語のすり替えです。OS を挟む説明は TP の役割を曖昧にした不正確な表現です。

</details>

**問5.** 銀行が「振込処理は検証済みのアプリケーションを通してのみ実行でき、入力担当と承認担当を分離し、全操作を記録する」仕組みを設計しています。この要件に最もよく合致 (BEST) するモデルはどれでしょう？

1. Bell-LaPadula
2. Brewer-Nash
3. 非干渉モデル (noninterference model)
4. Clark-Wilson

<details><summary>答えと解説</summary>

正解: **4**

「検証済みプログラム経由の変更（整形式トランザクション）」「職務分掌」「監査」の3点が揃ったら Clark-Wilson です。商用システムの完全性要件にそのまま対応します。Bell-LaPadula は機密性のモデルで、変更手続きや職務分掌は扱いません。Brewer-Nash は利益相反の防止（チャイニーズウォール）、非干渉モデルは上位レベルの活動が下位から観測できないことを扱うモデルで、問題文の要件とは目的が異なります。

</details>

**問6.** Biba と比べたときの Clark-Wilson の特徴として、最も適切なものはどれでしょう？

1. 完全性レベルの上下関係だけで読み書きを統制する
2. 完全性ではなく機密性の保護を主目的とする
3. 職務分掌や監査を組み込み、正規ユーザーの誤変更まで含む完全性の3目標を扱う
4. 軍事システム専用に設計されており商用には適さない

<details><summary>答えと解説</summary>

正解: **3**

Clark-Wilson は、不正な変更の防止だけでなく「正規ユーザーによる誤った変更の防止」「内部整合性と外部整合性の維持」という完全性の3目標を、整形式トランザクション・職務分掌・監査の組み合わせで扱います。レベルの上下だけで統制するのは Biba の説明です。どちらも完全性のモデルなので「機密性が主目的」は誤りです。Clark-Wilson はむしろ商用（銀行取引など）を想定して生まれたモデルなので「軍事専用」も逆です。

</details>

## 4. その他のモデルと情報フロー

### 利益相反を防ぐ — Brewer-Nash（チャイニーズウォール）

**Brewer-Nash** は、コンサルティング会社や監査法人のように**利益相反 (conflict of interest)** が問題になる組織のためのモデルです。「A 銀行のデータに触れた人は、競合する B 銀行のデータには触れられない」というように、**過去に何へアクセスしたかに応じてアクセス権が動的に変わる**のが最大の特徴です。別名**チャイニーズウォールモデル (Chinese Wall model)** と呼ばれます。

**一段ずつ見る**: 会社を、競合関係ごとの「利益相反クラス」に分けておきます。

- 銀行クラス: A 銀行、B 銀行
- 製薬クラス: X 社、Y 社

コンサルタントの佐藤さんのアクセス可否は、アクセス履歴によって次のように変わります。

| 時点 | 佐藤さんのアクセス履歴 | A 銀行 | B 銀行 | X 社 | Y 社 |
|---|---|---|---|---|---|
| 初日 | なし | ○ | ○ | ○ | ○ |
| A 銀行の資料を開いた後 | A 銀行 | ○ | ✕ | ○ | ○ |
| さらに X 社の資料を開いた後 | A 銀行、X 社 | ○ | ✕ | ○ | ✕ |

最初は全社に触れられますが、1社を選ぶと同じクラスの競合他社に壁（ウォール）が立ちます。別クラスの X 社には触れられる点がポイントです。

### 権限の受け渡しを形式化したモデル

| モデル | ポイント |
|---|---|
| Graham-Denning | 主体・オブジェクトの作成/削除、権限の付与/剥奪など**8つの保護ルール**を定義 |
| Harrison-Ruzzo-Ullman (HRU) | Graham-Denning を発展させ、権限の変化を**コマンド単位**で扱う。任意の保護状態の安全性判定は一般には決定不能（どんな場合でも必ず答えを出す手順は作れないと証明されていること）、という理論的結果でも有名 |
| Take-Grant | take（奪う）・grant（与える）・create・remove の4ルールの**有向グラフ**で、権限がどこまで伝播し得るかを分析 |

**Take-Grant の例**: 有向グラフは、主体や客体を点、権限を矢印で表した図です。

```
田中 --take--> 鈴木 --read--> 給与.xlsx
```

田中さんは鈴木さんに対する take 権限を持ち、鈴木さんは給与.xlsx の read 権限を持っています。take ルールにより、田中さんは鈴木さんの read 権限を取得でき、結果として給与.xlsx を読めるようになり得ます。給与.xlsx に直接の権限がなくても「たどれば届く」ことを見つけるのがこのモデルの使い道です。

### 非干渉モデルとアクセス制御マトリクス

- **非干渉モデル (noninterference model)**: 上位レベルの主体の行動が、下位レベルの主体から**観測・推測できない**ことを要求します。処理時間の差などから情報が漏れる**隠れチャネル (covert channel)** への対策につながる考え方です。隠れチャネルには2種類あります
- **隠れチャネル①: タイミングチャネル**: 時間の変化で伝える。例: 極秘の処理が動いている間は、区分なしの利用者から見た応答が 0.2 秒から 1.5 秒に遅くなるので「何か大きな処理が動いている」と推測できる
- **隠れチャネル②: ストレージチャネル**: 共有の記録場所で伝える。例: 上位のプロセスが共有ディスクの空き容量を増減させ、下位のプロセスがそれを読んで1ビットずつ情報を受け取る
- **アクセス制御マトリクス (access control matrix)**: 主体を行、オブジェクトを列にした表。**行**を取り出したものが**ケーパビリティリスト (capability list)**（その主体が何をできるか）、**列**を取り出したものが **ACL**（Access Control List。そのオブジェクトに誰が何をできるか）です

| 主体 \ 客体 | 給与.xlsx | 日報.txt | プリンタ |
|---|---|---|---|
| 佐藤 | 読み・書き | 読み | 印刷 |
| 鈴木 | なし | 読み・書き | 印刷 |
| バックアップ処理 | 読み | 読み | なし |

- 佐藤の**行**を取り出す → ケーパビリティリスト「給与.xlsx: 読み・書き、日報.txt: 読み、プリンタ: 印刷」
- 給与.xlsx の**列**を取り出す → ACL「佐藤: 読み・書き、鈴木: なし、バックアップ処理: 読み」

実際の OS のファイル権限は、ファイルごとに ACL を持つ形がほとんどです。

### 総まとめ — どのモデルが何を守るか

| モデル | 守るもの・目的 |
|---|---|
| Bell-LaPadula | 機密性 |
| Biba / Clark-Wilson | 完全性 |
| Brewer-Nash | 利益相反の防止（動的） |
| 非干渉 | 上位の活動の秘匿（推測の防止） |

### 確認問題

**問1.** 監査法人のコンサルタントが X 社（製薬）の案件データにアクセスした後、競合する Y 社（製薬）の案件データへのアクセスが自動的に禁止されました。このアクセス制御に最もよく合致するモデルはどれでしょう？

1. Clark-Wilson
2. Graham-Denning
3. Take-Grant
4. Brewer-Nash

<details><summary>答えと解説</summary>

正解: **4**

「過去のアクセス履歴に応じて、利益相反する相手へのアクセスが動的に禁止される」のは Brewer-Nash（チャイニーズウォール）モデルの定義そのものです。Clark-Wilson は検証済み手続きによる完全性の保護、Graham-Denning は権限操作の8ルール、Take-Grant は権限伝播のグラフ分析で、いずれも利益相反は扱いません。「アクセス権が時間とともに動的に変わる」というキーワードが出たら Brewer-Nash を思い出してください。

</details>

**問2.** 主体やオブジェクトの作成・削除、アクセス権の付与・剥奪といった操作を「8つの保護ルール」として定義したモデルはどれでしょう？

1. 非干渉モデル
2. Graham-Denning
3. Bell-LaPadula
4. Biba

<details><summary>答えと解説</summary>

正解: **2**

Graham-Denning モデルは、オブジェクトの作成/削除・主体の作成/削除・アクセス権の付与(grant)/剥奪・読み取り権と移転権の管理といった8つのルールで、権限がどう操作されるべきかを定義します。これを発展させたのが Harrison-Ruzzo-Ullman (HRU) です。Bell-LaPadula と Biba は読み書きの方向を制限する機密性・完全性のモデルで、権限操作そのものの8ルールは定義しません。非干渉モデルは上位の活動が下位から観測できないことを扱います。「8つのルール」という数字がそのまま決め手になる知識問題です。

</details>

**問3.** アクセス制御マトリクスについて、正しい説明はどれでしょう？

1. 列を取り出すとケーパビリティリスト、行を取り出すと ACL になる
2. 主体同士の信頼関係を有向グラフで表現する
3. 行を取り出すとケーパビリティリスト、列を取り出すと ACL になる
4. 機密レベルの上下関係をラティスで表現する

<details><summary>答えと解説</summary>

正解: **3**

アクセス制御マトリクスは主体を行、オブジェクトを列にした表です。行（ある主体の視点）を取り出すと「その主体が各オブジェクトに何をできるか」＝ケーパビリティリスト、列（あるオブジェクトの視点）を取り出すと「誰がこのオブジェクトに何をできるか」＝ ACL になります。行と列を逆にした選択肢は定番のひっかけです。有向グラフで権限の伝播を扱うのは Take-Grant、ラティスで上下関係を表すのは BLP などのラティスベースモデルの説明です。

</details>

**問4.** マルチレベルセキュリティのシステムで、下位レベルの利用者が「処理の応答時間の変化」から上位レベルの機密処理の存在を推測できてしまいます。この問題への対策を理論的に支えるモデルとして、最も適切 (BEST) なものはどれでしょう？

1. 非干渉モデル (noninterference model)
2. Brewer-Nash
3. Clark-Wilson
4. Graham-Denning

<details><summary>答えと解説</summary>

正解: **1**

非干渉モデルは「上位レベルの主体の活動が、下位レベルの主体の見える世界に一切影響（干渉）しないこと」を要求します。応答時間の差などから情報が漏れるのは隠れチャネル（covert timing channel）であり、まさに上位の活動が下位から観測できてしまう干渉の例です。Brewer-Nash は利益相反、Clark-Wilson は完全性、Graham-Denning は権限操作のルールが守備範囲で、推測による漏えいは扱いません。「推測」「観測できてしまう」というキーワードから非干渉モデルに結びつけましょう。

</details>

**問5.** take・grant・create・remove の4つのルールを使い、権限がシステム内でどこまで伝播し得るかを有向グラフで分析するモデルはどれでしょう？

1. Harrison-Ruzzo-Ullman
2. Take-Grant
3. 強い*プロパティ
4. 情報フローモデル

<details><summary>答えと解説</summary>

正解: **2**

Take-Grant モデルは、take（他者から権限を奪う）・grant（他者へ権限を与える）・create・remove の4ルールによる有向グラフで、権限の伝播経路を数学的に分析します。「4つのルール」「有向グラフ」が決め手です。Harrison-Ruzzo-Ullman も権限の変化を扱いますが、コマンドと行列で形式化するモデルでグラフの4ルールではありません。強い*プロパティは BLP の読み書き制限ルール、情報フローモデルは情報の流れる方向を統制する一般的な枠組みの名称です。

</details>
