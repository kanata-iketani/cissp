# 第20章 フェデレーション・SSO・IDライフサイクル【D5】

複数システム・複数組織にまたがる「ID のつなぎ方」を学ぶ章です。SSO・SAML・OAuth・Kerberos といった仕組みの違いと、ID を作ってから消すまでのライフサイクル管理、特権アカウントの統制までを一気に押さえます。D5 のシナリオ問題で最も狙われるゾーンです。

## 1. SSOとフェデレーション（SAML・OAuth・OIDC）

### SSO — 鍵を1つにまとめる

**シングルサインオン (SSO: Single Sign-On)** は、1回の認証で複数のシステムを利用できる仕組みです。利点はパスワード使い回しの防止・利便性向上・管理コスト削減ですが、裏返すと**「その1つの鍵が破られたら全システムに入られる」**のが最大のリスクです。だからこそ SSO の入口には MFA を組み合わせるのが定石です。

### フェデレーション — 組織をまたぐ信頼

**フェデレーテッドアイデンティティ (federated identity)** は、組織やサービスの境界を越えて ID を信頼し合う仕組みです。登場人物は 2 つだけです。

- **IdP (Identity Provider)**: 認証を行い、「この人は本人です」と証明を発行する側
- **SP (Service Provider、RP: Relying Party とも)**: その証明を信頼してサービスを提供する側

### 3つのプロトコルの使い分け（超頻出）

| プロトコル | 役割 | 形式 | 典型的な用途 |
|---|---|---|---|
| **SAML** | 認証 + 認可の伝達 | XML（アサーション） | 企業の Web SSO の定番 |
| **OAuth 2.0** | **認可 (authorization) のみ** | トークン | 「アプリに連絡先の読み取りを許可」 |
| **OIDC (OpenID Connect)** | OAuth 2.0 の上に**認証**を追加 | ID トークン (JWT) | ソーシャルログイン |

💡 コツ: 試験最大のひっかけは **「OAuth は認証プロトコルではない」** という点です。OAuth が渡すのは「何をしてよいか」の許可であり、「誰であるか」の証明は OIDC や SAML の仕事です。「認証」と書かれた選択肢に OAuth 2.0 があったら疑ってください。

フェデレーション環境では、初回ログイン時に SP 側へ自動的にアカウントを作る**ジャストインタイムプロビジョニング (JIT provisioning)** もよく使われます。SAML アサーションの属性からアカウントを生成するため、事前の一括登録が不要になります。

### 確認問題

**問1.** ある企業が、自社の従業員がパートナー企業のWebサービスを追加のパスワードなしで利用できるようにしたいと考えています。自社がユーザーの認証を行い、パートナー側はその結果を信頼します。このとき自社が果たす役割はどれでしょう？

1. SP (Service Provider)
2. RP (Relying Party)
3. IdP (Identity Provider)
4. KDC (Key Distribution Center)

<details><summary>答えと解説</summary>

正解: **3**

認証を実施して「本人である」という証明（アサーション）を発行する側が IdP (Identity Provider) です。SP と RP はその証明を受け取ってサービスを提供する側（この問題ではパートナー企業）で、呼び方が違うだけでほぼ同じ役割です。KDC は Kerberos の構成要素であり、フェデレーションの用語ではありません。試験では「どちらが IdP か」を文章から読み取らせる問題が定番なので、「認証する側=IdP、信頼する側=SP/RP」と整理しておきましょう。

</details>

**問2.** モバイルアプリが、ユーザーのカレンダーサービス上の予定を読み取る許可を安全に取得するために設計されたフレームワークはどれでしょう？

1. OAuth 2.0
2. SAML
3. LDAP
4. Kerberos

<details><summary>答えと解説</summary>

正解: **1**

「第三者のアプリにリソースへのアクセス許可（認可）を与える」のは OAuth 2.0 の設計目的そのものです。パスワードをアプリに渡さず、範囲を限定したトークンで許可を与えます。SAML も認可情報を運べますが、主に企業の Web SSO（ブラウザベース）で使われる XML ベースの仕組みです。LDAP はディレクトリへの問い合わせプロトコル、Kerberos は組織内ネットワークの認証プロトコルで、どちらも第三者アプリへの委任認可の仕組みではありません。

</details>

**問3.** SSO導入の提案に対し、経営層から「セキュリティ上の最大の懸念は何か」と問われました。MOST appropriate（最も適切）な回答はどれでしょう？

1. ユーザーが覚えるパスワードの数が増えること
2. 認証情報が1つ侵害されると、連携する全システムへアクセスされ得ること
3. 各システムのログイン画面の表示が遅くなること
4. パスワードポリシーをシステムごとに変えられなくなること

<details><summary>答えと解説</summary>

正解: **2**

SSO は「鍵を1つにまとめる」仕組みなので、その1つの認証情報が破られると影響が全システムに波及します。これが SSO 固有の最大リスクで、対策として MFA の併用が定石です。「ユーザーが覚えるパスワードの数が増えること」は逆（SSO は覚えるパスワードを減らします）、「各システムのログイン画面の表示が遅くなること」は本質的なセキュリティ懸念ではありません。「パスワードポリシーをシステムごとに変…」は運用上の論点ではあるものの「最大の懸念」とは言えません。BEST/MOST 問題では「もっともらしいが小さい論点」と「本質的なリスク」を見分けることが問われます。

</details>

**問4.** OIDC (OpenID Connect) が OAuth 2.0 に追加した機能として正しいものはどれでしょう？

1. XMLベースのアサーションによる属性交換
2. 対称鍵によるチケット発行
3. 通信全体のパケット暗号化
4. IDトークンによる認証（ユーザーが誰であるかの証明）

<details><summary>答えと解説</summary>

正解: **4**

OIDC は OAuth 2.0 の認可フローの上に「認証」のレイヤーを追加したもので、JWT 形式の ID トークンによって「ユーザーが誰か」を証明できるようにしました。XML ベースのアサーションは SAML の特徴、対称鍵によるチケットは Kerberos の仕組み、通信全体の暗号化は TLS などの役割です。「OAuth 2.0 = 認可のみ、OIDC = OAuth + 認証」という対応は試験で繰り返し問われる超頻出ポイントです。

</details>

**問5.** フェデレーション連携した外部サービスに、従業員が初めてログインした瞬間、SAMLアサーションの属性情報をもとにそのサービス側のアカウントが自動作成されました。この仕組みはどれでしょう？

1. セルフサービスパスワードリセット
2. ジャストインタイムプロビジョニング (JIT provisioning)
3. アカウントの再認定 (recertification)
4. デプロビジョニング

<details><summary>答えと解説</summary>

正解: **2**

初回アクセス時にアサーションの属性からアカウントをその場で自動生成するのがジャストインタイムプロビジョニングです。事前の一括アカウント登録が不要になり、フェデレーション環境と相性が良い方式です。セルフサービスパスワードリセットはユーザー自身によるパスワード再設定、再認定は既存アクセス権が今も適切かの定期見直し、デプロビジョニングは退職時などのアカウント削除・無効化で、いずれも「初回ログイン時の自動作成」ではありません。

</details>

## 2. ディレクトリとKerberos・AAAプロトコル

### ディレクトリ — 組織内IDの土台

**LDAP (Lightweight Directory Access Protocol)** は、ユーザーやグループの情報を木構造で管理するディレクトリサービスへの問い合わせプロトコルです。Microsoft の **Active Directory** は LDAP と Kerberos を組み合わせた代表的な実装で、組織内の認証・認可の土台になります。ディレクトリが侵害されると全アカウントが危険にさらされるため、最優先で保護すべき資産です。

### Kerberos — チケットで認証する（超頻出）

Kerberos は組織内ネットワークの SSO を実現する認証プロトコルです。**対称鍵暗号**とチケットを使います。

1. ユーザーが **KDC (Key Distribution Center)** の **AS (認証サーバー)** に認証を要求
2. 成功すると **TGT (Ticket Granting Ticket)** を受け取る
3. サービスを使うたびに TGT を **TGS (チケット交付サーバー)** に見せ、**サービスチケット**をもらう
4. サービスチケットをサーバーに提示してアクセス

チケットには**タイムスタンプ**が含まれ、通常5分程度のずれまでしか許容されません。これは**リプレイ攻撃**（盗んだチケットの再利用）への対策です。

**Kerberos の弱点**: KDC が単一障害点（止まると誰も認証できない）かつ侵害されると全滅、全端末の**時刻同期が必須**、最初の認証がパスワードに依存する、という点を押さえましょう。

### AAAプロトコルの対比（頻出）

| 項目 | RADIUS | TACACS+ | Diameter |
|---|---|---|---|
| トランスポート | UDP | TCP | TCP/SCTP |
| 暗号化 | **パスワードのみ** | **パケット全体** | TLS/IPsec 利用 |
| AAA の分離 | 認証と認可が一体 | **認証・認可・アカウンティングを分離** | 柔軟 |
| 主な用途 | リモートアクセス・無線LAN | ネットワーク機器の管理者認証 | 通信事業者 (4G/5G) |

💡 コツ: 「機器管理者のコマンド単位の認可が必要」なら TACACS+、「無線LAN の 802.1X」なら RADIUS、と用途で選ばせる問題が出ます。RADIUS はパスワード以外が平文という弱点も問われます。

### 確認問題

**問1.** Kerberos認証で、ユーザーが最初の認証に成功した直後にKDCから受け取るものはどれでしょう？

1. サービスチケット
2. TGT (Ticket Granting Ticket)
3. IDトークン (JWT)
4. 公開鍵証明書

<details><summary>答えと解説</summary>

正解: **2**

最初の認証（AS との交換）に成功すると TGT を受け取ります。TGT は「以後チケットを発行してもらうためのチケット」で、個々のサービスにアクセスする際は TGT を TGS に提示してサービスチケットをもらいます。つまりサービスチケットは2段階目です。ID トークンは OIDC の用語、公開鍵証明書は PKI の仕組みで、Kerberos は対称鍵ベースという点もあわせて覚えておきましょう。「TGT が先、サービスチケットが後」の順序は超頻出です。

</details>

**問2.** Kerberosがチケットにタイムスタンプを含め、端末間の時刻のずれを5分程度までしか許容しない主な目的はどれでしょう？

1. KDCの負荷を分散するため
2. パスワードの有効期限を強制するため
3. ネットワーク遅延を測定するため
4. 盗まれたチケットを後から再利用するリプレイ攻撃を防ぐため

<details><summary>答えと解説</summary>

正解: **4**

タイムスタンプの検証により、過去に盗聴・取得されたチケットを後から使い回す「リプレイ攻撃 (replay attack)」を防ぎます。有効期間がごく短ければ、盗んだチケットはすぐに使えなくなります。負荷分散・パスワード有効期限・遅延測定はいずれもタイムスタンプの目的ではありません。裏返しとして「Kerberos は全端末の時刻同期 (NTP) が必須」という運用上の弱点が生まれる、という表裏の関係まで問われることがあります。

</details>

**問3.** ネットワーク機器の管理者アクセスを統制するため、「認証・認可・アカウンティングを分離して管理でき、通信パケット全体が暗号化される」プロトコルを選定したい。BESTな選択はどれでしょう？

1. TACACS+
2. RADIUS
3. SAML
4. LDAP

<details><summary>答えと解説</summary>

正解: **1**

TACACS+ は TCP 上で動作し、パケット全体を暗号化し、AAA（認証・認可・アカウンティング）を分離して扱えるため、機器管理者のコマンド単位の認可に適しています。RADIUS は UDP ベースでパスワード部分しか暗号化されず、認証と認可が一体です（無線 LAN やリモートアクセスの認証では定番ですが、この要件には不適合）。SAML は Web SSO のフェデレーション、LDAP はディレクトリ問い合わせのプロトコルで、AAA プロトコルではありません。要件のキーワードから選ばせるのが典型パターンです。

</details>

**問4.** Kerberosを全社認証基盤として導入する際、可用性の観点でMOSTに重大な考慮点はどれでしょう？

1. チケットのサイズがネットワーク帯域を圧迫すること
2. ユーザーごとに公開鍵ペアを発行する手間がかかること
3. KDCが停止すると全ユーザーが認証できなくなること
4. パスワードが平文でネットワークを流れること

<details><summary>答えと解説</summary>

正解: **3**

KDC は Kerberos の中核であり、単一障害点 (single point of failure) です。停止すれば新規の認証・チケット発行ができなくなるため、冗長化が必須になります。チケットサイズは実用上問題になりません。Kerberos は対称鍵ベースなので公開鍵ペアの発行は不要（「ユーザーごとに公開鍵ペアを発行する手間がかかること」は PKI との混同を狙ったひっかけ）です。また Kerberos はパスワード自体をネットワークに流さない設計なので「パスワードが平文でネットワークを流れること」も誤りです。「可用性の観点で」という限定条件を読み落とさないことも大切です。

</details>

**問5.** RADIUSのセキュリティ上の弱点として正しいものはどれでしょう？

1. TCPを使うためDoS攻撃に弱い
2. パスワード以外の属性情報（ユーザー名など）が暗号化されずに送られる
3. アカウンティング機能を持たない
4. チケットの有効期限を設定できない

<details><summary>答えと解説</summary>

正解: **2**

RADIUS が暗号化するのはパスワード部分だけで、ユーザー名やその他の属性は平文で流れます。これが「パケット全体を暗号化する TACACS+」との対比で最も問われる弱点です。RADIUS は UDP を使うため「TCPを使うためDoS攻撃に弱い」は前提から誤り。RADIUS は AAA の Accounting 機能を持っています（ポート1813など）。チケットは Kerberos の概念であり RADIUS にはありません。対比表の「どの行がどのプロトコルか」を入れ替えるひっかけに注意しましょう。

</details>

## 3. IDライフサイクルと特権アクセス管理 (PAM)

### IDのライフサイクル

アカウントは「作って終わり」ではなく、一生を通じて管理します。

**プロビジョニング (provisioning)** → **利用と見直し** → **デプロビジョニング (deprovisioning)**

- **オンボーディング**: 入社時。職務に必要な最小限の権限だけを付与します（最小権限、ロールベースでの付与が定石）
- **アクセスレビューと再認定 (access review / recertification)**: 「その権限は今も必要か」を定期的に確認します。異動を繰り返した人に権限が溜まっていく**権限の蓄積 (privilege creep)** を発見するのが狙いです
- **オフボーディング**: 退職・契約終了時。**アカウントは即時に無効化 (disable)** します

💡 コツ: 退職者のアカウントは「削除」より先に「**無効化**」が正解になりやすいです。削除するとその人のファイルや暗号鍵、監査証跡へのアクセスまで失われるため、まず無効化してデータを保全し、規程に沿って後から削除します。また、**休眠アカウント (dormant account)** は攻撃者の格好の足がかりなので、定期検出と無効化が必要です。

### 特権アクセス管理 (PAM)

管理者権限は「侵害されたときの被害」が桁違いなので、一般アカウントより厳しく統制します。**PAM (Privileged Access Management)** の主な機能は次のとおりです。

| 機能 | 内容 |
|---|---|
| パスワードボールト | 特権パスワードを金庫で集中管理し、都度払い出し・自動変更 |
| セッション記録 | 特権操作を録画・ログ化し、監査とアカウンタビリティを確保 |
| **JIT 特権昇格 (Just-in-Time)** | 常時付与をやめ、必要なときだけ時間限定で昇格させる |
| 承認ワークフロー | 特権利用に上長承認を要求 |

JIT は「常設の管理者アカウントを極小化する」考え方で、ゼロトラストとも相性が良い重要キーワードです。

**サービスアカウント**（人ではなくプログラムが使うアカウント）も忘れがちな統制対象です。パスワードが固定されがち・ログインが自動なので、棚卸し、不要権限の剥奪、資格情報のローテーションが求められます。クラウドの **IDaaS (Identity as a Service)** を使う場合は、可用性・データ所在・ベンダーロックインなどを第三者リスクとして評価します。

### 確認問題

**問1.** 従業員が本日付で退職しました。そのユーザーアカウントに対して FIRST（最初）に行うべき対応はどれでしょう？

1. アカウントを無効化する
2. アカウントを即座に削除する
3. パスワードを本人に変更させる
4. 次回のアクセスレビューまで現状を維持する

<details><summary>答えと解説</summary>

正解: **1**

退職時はまずアカウントの無効化です。これで不正アクセスの入口を即座に塞ぎつつ、本人のファイル・メール・暗号鍵・監査証跡は保全されます。即削除はデータや証跡へのアクセス手段まで失うため先には行いません（削除は保持規程に沿って後で実施）。パスワード変更を本人に任せるのは統制になっておらず、レビューまでの放置は休眠アカウントを放置するのと同じで論外です。「無効化が先、削除は後」は FIRST 問題の定番です。

</details>

**問2.** 長年勤務して部署異動を繰り返した従業員が、過去の部署の権限を持ち続けている状態が監査で見つかりました。この状態を表す用語と、発見に有効な統制の組み合わせはどれでしょう？

1. 権限の蓄積 — パスワードボールトの導入
2. 職務分掌違反 — MFAの導入
3. 権限の蓄積 (privilege creep) — 定期的なアクセスレビュー（再認定）
4. 休眠アカウント — アカウントロックアウトの設定

<details><summary>答えと解説</summary>

正解: **3**

異動のたびに古い権限が剥奪されず溜まっていく状態が権限の蓄積 (privilege creep) で、発見する統制は定期的なアクセスレビュー（再認定、recertification）です。パスワードボールトは特権パスワードの保管の仕組みで権限の棚卸しはできません。MFA は認証強化であり権限の適切性は確認できません。休眠アカウントは「使われていないアカウント」のことで、本問の「使っている人に不要権限が溜まる」状況とは別物です。用語と統制を正しく対応づけられるかが問われます。

</details>

**問3.** 管理者権限の常時付与をやめ、必要な作業のときだけ時間を区切って権限を昇格させるPAMの手法はどれでしょう？

1. シングルサインオン (SSO)
2. ジャストインタイムプロビジョニング
3. セッション記録
4. ジャストインタイム (JIT) 特権昇格

<details><summary>答えと解説</summary>

正解: **4**

必要時のみ・時間限定で特権を付与するのが JIT 特権昇格です。常設の管理者アカウントを減らし、侵害時の攻撃面を小さくします。紛らわしいのは「ジャストインタイムプロビジョニング」のジャストインタイムプロビジョニングで、こちらはフェデレーションで初回ログイン時にアカウントを自動作成する仕組みです（「JIT」つながりのひっかけ）。SSO は認証の一元化、セッション記録は特権操作の監査証跡化であり、権限付与のタイミング制御ではありません。

**問4.** サービスアカウント（アプリケーションが使用するアカウント）の統制として、MOSTに優先して対処すべきリスクはどれでしょう？

1. ログイン画面のデザインが統一されていないこと
2. 資格情報が長期間変更されず、退職者にも知られたままになり得ること
3. アカウント名が命名規則に従っていないこと
4. 利用部門がヘルプデスクに問い合わせできないこと

<details><summary>答えと解説</summary>

正解: **2**

サービスアカウントはパスワードが固定されがちで、設定した担当者の退職後も変わらないことが多く、知っている人間が使えば検知されにくい不正アクセスの温床になります。資格情報のローテーション（PAM のボールトによる自動変更が理想）が最優先の統制です。命名規則やデザイン、問い合わせ窓口は運用品質の話であり、セキュリティリスクの大きさでは比較になりません。MOST 問題では「リスクの大きさ」で優先順位をつけます。

</details>

**問5.** IDaaS（クラウド型のID管理サービス）の採用を検討する際の考慮点として、適切でないものはどれでしょう？

1. サービス停止時に全社の認証が止まる可能性
2. ID情報がどの国・リージョンに保存されるか
3. ベンダーの財務健全性と事業継続性
4. 自社データセンターの空調能力

<details><summary>答えと解説</summary>

正解: **4**

IDaaS はクラウドサービスなので、自社データセンターの空調能力は無関係です（オンプレミスで ID 基盤を自前運用する場合の考慮点)。残りはすべて重要です。認証はあらゆる業務の入口なので可用性の影響は全社に及び、ID 情報は個人データとしてデータ所在(レジデンシー)や越境移転の規制対象になり、ベンダーが倒産・撤退すれば認証基盤ごと失うため第三者リスク評価(デューデリジェンス)が必要です。「適切でないもの」を選ぶ否定形の設問は読み飛ばしに注意しましょう。

</details>
