# 第21章 セキュリティテストと脆弱性評価【D6】

D6「セキュリティの評価とテスト」の前半です。対策(コントロール)が本当に機能しているかを証拠で確かめる方法として、評価戦略の立て方、脆弱性評価、ペネトレーションテストを学びます。「脆弱性スキャンとペネトレの違い」「書面の許可が必須」など、試験で繰り返し問われる論点が詰まった章です。

## 1. セキュリティ評価とテストの戦略

### なぜ「評価とテスト」が独立ドメインなのか

セキュリティ対策は導入した瞬間から劣化が始まります。設定ミス、構成変更、新しい攻撃手法——「導入した」ことと「機能している」ことは別物です。そこで**コントロールが意図どおり機能している証拠を定期的に集める**活動が、セキュリティ評価とテスト (security assessment and testing) です。ここでいうコントロールは、第2章で見たリスクを下げるための対策(パスワード規則、ファイアウォール、アクセス権の定期点検など)のことです。

### 評価の実施主体は3種類

| 実施主体 | 特徴 | 向いている場面 |
|---|---|---|
| 内部評価 (internal) | 自組織の要員が実施。安価で頻繁にできるが客観性に限界 | 日常的な点検・継続的モニタリング |
| 外部評価 (external) | 社外の専門家を雇って実施。客観性と専門性が高い | 年次評価、重要システムの評価 |
| 第三者評価 (third-party) | 規制当局・取引先など**外部の利害関係者が要求**して行われる | 法規制対応、取引先への保証 |

💡 コツ: 「監査人の独立性」が論点になったら、評価対象から独立した主体を選ぶのが CISSP 的正解です。自分のシステムを自分で評価した結果だけで経営判断するのは NG です。

### 検証と妥当性確認の違い

- **検証 (verification)**: 仕様どおりに作られたか(Are we building it right?)
- **妥当性確認 (validation)**: そもそも目的・ニーズを満たすか(Are we building the right thing?)

例: 仕様が「パスワードは8文字以上」なら、7文字のパスワードがきちんと拒否されるかを確かめるのが検証です。そもそも8文字のルールで利用者のアカウント乗っ取りを防げるのかを確かめるのが妥当性確認です。

### 評価手法の全体像(超頻出)

| 手法 | 何をするか | 深さ |
|---|---|---|
| 脆弱性評価 (vulnerability assessment) | 弱点を**特定・列挙**する | 広く浅く |
| ペネトレーションテスト (penetration test) | 弱点を**実際に悪用**して侵入可否を実証 | 狭く深く |
| 監査 (audit) | 基準への**準拠**を独立した立場で検証 | 準拠性 |

脆弱性 (vulnerability) は、攻撃に悪用できる弱点(古いソフトのバグ、設定ミスなど)のことです。同じ Web サーバー1台で比べると、成果は次のように違います。

| 手法 | 成果の例 |
|---|---|
| 脆弱性評価 | 「Apache 2.4.49 が動いており、既知の脆弱性 CVE-2021-41773 に該当する」という一覧 |
| ペネトレーションテスト | その脆弱性を実際に突き、サーバー内の設定ファイルを読み出せたという実証 |
| 監査 | 「重大な脆弱性は30日以内に修正する」という社内規程どおりに直されてきたかを、記録で確認 |

CVE という番号の意味は次のチャプターで説明します。

テスト計画では、本番環境(利用者が実際に使っているシステム)への影響(可用性)を必ず考慮し、**経営層の承認**を得てから実施します。テスト自体が障害を起こしては本末転倒だからです。

### 確認問題

**問1.** セキュリティ評価とテストのプログラムを組織に導入する目的として、最も適切な(BEST)ものはどれでしょう？

1. すべての脆弱性を完全に排除するため
2. セキュリティコントロールが意図どおり機能している証拠を継続的に得るため
3. セキュリティ予算を削減するため
4. 攻撃者を特定して法的措置をとるため

<details><summary>答えと解説</summary>

正解: **2**

評価とテストの目的は、導入済みコントロールが実際に機能しているかを証拠(エビデンス)で確認し続けることです。「すべての脆弱性の完全排除」は不可能であり(リスクはゼロにできない)、予算削減や攻撃者の特定は副次的・別目的の活動です。CISSPでは『完全に・すべて』という選択肢はほぼ誤りというひっかけパターンも覚えておきましょう。

</details>

**問2.** 金融規制当局が、監督対象の銀行に対してセキュリティ評価の実施と報告を要求しました。この評価の分類として最も適切なものはどれでしょう？

1. 内部評価
2. ペネトレーションテスト
3. 第三者評価
4. 自己点検

<details><summary>答えと解説</summary>

正解: **3**

規制当局や取引先など、外部の利害関係者の要求に基づいて行われる評価は第三者評価 (third-party assessment) です。内部評価・自己点検は自組織の判断で行うもので、客観性の保証が目的の規制要求には合いません。ペネトレーションテストは評価の「手法」であって実施主体の分類ではない、という点もひっかけどころです。

</details>

**問3.** 「このシステムは要求仕様どおりに実装されているか」を確かめる活動を指す用語はどれでしょう？

1. 検証 (verification)
2. 妥当性確認 (validation)
3. 認定 (accreditation)
4. 監査 (audit)

<details><summary>答えと解説</summary>

正解: **1**

仕様どおりに作られているかの確認は検証 (verification) です。妥当性確認 (validation) は「そもそも利用者のニーズ・目的を満たすか」を確かめる活動で、対象が一段上です。認定は経営層がリスクを受容してシステム運用を承認する行為、監査は基準への準拠を独立した立場で確かめる活動です。verification と validation の対比は D6 と D8(ソフトウェアテスト)の両方で問われます。

</details>

**問4.** 脆弱性評価とペネトレーションテストの違いの説明として、最も適切な(MOST accurate)ものはどれでしょう？

1. 脆弱性評価は外部業者が行い、ペネトレーションテストは内部要員が行う
2. 脆弱性評価は弱点を列挙し、ペネトレーションテストは弱点を実際に悪用して侵入可否を実証する
3. 脆弱性評価は本番環境で行い、ペネトレーションテストはテスト環境でのみ行う
4. 両者は同じ活動の別名である

<details><summary>答えと解説</summary>

正解: **2**

脆弱性評価は「広く浅く」弱点を特定・列挙する活動、ペネトレーションテストは特定した弱点を実際に悪用 (exploit) して「本当に侵入できるか」を実証する活動です。実施主体(内部か外部か)や実施環境はどちらの手法でも選択可能なので、それらで両者を区別する説明は誤りです。この違いは D6 で最も出題されやすい論点のひとつです。

</details>

**問5.** 本番システムに対するセキュリティテストを計画する際、最初に(FIRST)行うべきことはどれでしょう？

1. テストツールの選定
2. 脆弱性スキャンの実行
3. テストによる業務影響の評価と経営層の承認取得
4. テスト結果の報告書テンプレート作成

<details><summary>答えと解説</summary>

正解: **3**

CISSPの鉄則「実行の前に計画と承認」です。テスト自体がシステム停止や性能劣化を招き得るため、まず業務影響(可用性への影響)を評価し、責任を持つ経営層・システムオーナーの承認を得るのが FIRST です。ツール選定やスキャン実行は承認後の話で、報告書テンプレートはさらに後工程です。『技術的な作業より先にマネジメントプロセス』という CISSP 的思考を思い出しましょう。

</details>

## 2. 脆弱性評価

### 脆弱性スキャンの基本

脆弱性スキャン (vulnerability scan) は、既知の弱点をツールで自動的に洗い出す活動です。対象によりネットワークスキャン、Web アプリケーションスキャン、データベーススキャンなどを使い分けます。

### スキャナがしていること

スキャナは対象の機器に通信を送り、返ってきた応答から「どのポート(第14章で見た、通信の窓口番号)が開いているか」「どのソフトのどの版が動いているか」を調べます。それを既知の脆弱性のデータベースと照らし合わせて一覧にします。結果はたとえば次のようになります。

```
192.0.2.10  22/tcp   open  OpenSSH 7.2p2  CVE-2016-6210   CVSS 5.9
192.0.2.10  443/tcp  open  Apache 2.4.49  CVE-2021-41773  CVSS 7.5
```

- 1行目: 192.0.2.10 の22番ポート(SSH。遠隔ログイン用)が開いていて、OpenSSH 7.2p2 が動いています。この版には CVE-2016-6210 という脆弱性があり、深刻度は 5.9 です
- 2行目: 443番ポート(HTTPS)で Apache 2.4.49 が動いていて、CVE-2021-41773(深刻度 7.5)に該当します

ソフトの版は、接続したときにサービスが名乗る**バナー**(例: `Server: Apache/2.4.49`)から読み取ることが多いです。

### 認証スキャンと非認証スキャン

| 種類 | やり方 | 特徴 |
|---|---|---|
| 非認証スキャン (unauthenticated) | ログインせず外から調べる | 攻撃者から見える姿がわかるが、検出は浅い |
| 認証スキャン (authenticated/credentialed) | 有効なアカウントでログインして調べる | パッチ(不具合を直す修正プログラム)の適用状況や設定まで**深く正確に**検出、誤検知も減る |

非認証スキャンはバナーなど外から見える情報で版を推測するだけです。認証スキャンはログインして、インストール済みのソフトと版を直接読むので推測が要りません。

### CVE と CVSS

- **CVE (Common Vulnerabilities and Exposures)**: 脆弱性に付く世界共通の識別番号(例: CVE-2021-44228。2021年に見つかった Log4j というソフトの脆弱性で、「CVE-発見年-通し番号」の形)
- **CVSS (Common Vulnerability Scoring System)**: 深刻度を 0.0〜10.0 で表すスコア(上の CVE-2021-44228 は最大の 10.0)。基本値だけでなく、**自組織の環境**(その資産の重要度、代替策の有無)で補正して優先度を決めます
- **SCAP (Security Content Automation Protocol)**: これらを機械処理するための標準規格群

### 誤検知と見逃し

- **誤検知 (false positive)**: 存在しない脆弱性を「ある」と報告。調査工数を浪費させる
- **見逃し (false negative)**: 実在する脆弱性を報告しない。**セキュリティ上はこちらが深刻**

| | 脆弱性が実在する | 実在しない |
|---|---|---|
| スキャナが「ある」と報告 | 正しい検知 | 誤検知 (false positive) |
| スキャナが「ない」と報告 | 見逃し (false negative) | 正しい判定 |

💡 コツ: スキャン結果への対応順は「CVSS の数字が大きい順」ではなく、**資産の重要度 × 悪用可能性**で決めるのが CISSP 的正解です。スコア 9.0 でも隔離された検証機より、スコア 7.0 でもインターネット公開の決済サーバーが先です。

スキャンは一度やって終わりではなく、「スキャン → 優先度付け → 修正 → 再スキャンで確認」という**継続的な脆弱性管理サイクル**として回します。バナー情報だけに頼るスキャンは、誤った結果を出すことがある点にも注意しましょう。たとえば Linux の配布元は、新しい版の修正だけを古い版番号のまま取り込むこと(backport)があります。バナーの版番号は古いままなので、修正済みでも「脆弱」と報告されます(誤検知)。逆に管理者がバナーの版番号を偽装していると、見逃しの原因になります。

### 確認問題

**問1.** 認証スキャン(credentialed scan)が非認証スキャンより優れている点として、最も適切なものはどれでしょう？

1. ネットワーク帯域を一切消費しない
2. 攻撃者から見えるシステムの姿を正確に再現できる
3. パッチ適用状況や内部設定まで深く正確に検出でき、誤検知も減る
4. 書面の許可なしに実施できる

<details><summary>答えと解説</summary>

正解: **3**

認証スキャンは有効なアカウントでログインして内部から調べるため、パッチレベルや設定不備まで正確に検出でき、誤検知 (false positive) も減ります。「攻撃者から見える姿の再現」はむしろ非認証スキャンの特徴なので「攻撃者から見えるシステムの姿を正確に再現できる」は逆です。帯域は両方とも消費しますし、スキャンの種類にかかわらず組織の承認は必要です。

</details>

**問2.** 脆弱性スキャンの結果、次の4つが検出されました。最初に(FIRST)対応すべきものはどれでしょう？

1. 隔離された開発用サーバーの CVSS 9.8 の脆弱性
2. インターネット公開中の決済サーバーの CVSS 7.5 の脆弱性
3. 廃止予定の社内掲示板の CVSS 6.0 の脆弱性
4. 検証環境のプリンタの CVSS 8.0 の脆弱性

<details><summary>答えと解説</summary>

正解: **2**

対応優先度は CVSS の数字だけでなく「資産の重要度 × 悪用可能性(露出)」で決めます。インターネットに公開された決済サーバーは、事業影響も攻撃を受ける可能性も最大なので、スコアが 7.5 でも最優先です。隔離された開発機や検証環境は露出が小さく、スコアが高くても優先度は下がります。『数字が一番大きいものを選ばせる』のが典型的なひっかけです。

</details>

**問3.** 脆弱性の深刻度を 0.0〜10.0 のスコアで表す共通基準はどれでしょう？

1. CVE
2. SCAP
3. OVAL
4. CVSS

<details><summary>答えと解説</summary>

正解: **4**

深刻度スコアは CVSS (Common Vulnerability Scoring System) です。CVE は脆弱性の識別番号(名前)であってスコアではありません——この2つの混同を狙う問題が頻出です。SCAP は脆弱性情報を自動処理するための標準規格群、OVAL はその構成要素のひとつ(検査手順の記述言語)です。

</details>

**問4.** セキュリティの観点で、脆弱性スキャンにおける「見逃し (false negative)」が「誤検知 (false positive)」より深刻とされる理由として最も適切なものはどれでしょう？

1. 実在する脆弱性が報告されず、無防備なまま放置されるため
2. 調査工数が増えて運用チームが疲弊するため
3. スキャンツールのライセンス費用が増えるため
4. 報告書のページ数が増えて経営層が読まなくなるため

<details><summary>答えと解説</summary>

正解: **1**

見逃しは「実在する弱点に誰も気づかない」状態を生み、攻撃者だけがそれを知っている最悪の構図になります。誤検知の弊害は調査工数の浪費で、疲弊は問題ですが脆弱性が放置されるわけではありません。ライセンス費用や報告書の分量は本質と無関係です。false positive / false negative の定義と深刻度の比較は、IDS や生体認証の文脈でも繰り返し問われます。

</details>

**問5.** 組織の脆弱性管理プログラムとして最も適切な(BEST)アプローチはどれでしょう？

1. 年に一度の包括的スキャンを実施し、結果をすべて即日修正する
2. スキャン→リスクに基づく優先度付け→修正→再スキャンによる確認、を継続的に回す
3. CVSS 9.0 以上の脆弱性のみを監視し、それ未満は無視する
4. スキャンは外部業者に任せ、結果の確認は行わない

<details><summary>答えと解説</summary>

正解: **2**

脆弱性管理は一回のイベントではなく継続的なサイクル(スキャン→優先度付け→修正→再スキャンで修正を確認)です。年1回では新たな脆弱性に追随できず、「すべて即日修正」は現実的でもリスクベースでもありません。スコアで足切りして無視するのはリスク受容の判断プロセスを飛ばしており、外部委託しても結果確認の責任は組織に残ります(説明責任は移転できない)。

</details>

**問6.** スキャナが、バナーに表示された版番号「Apache 2.4.6」を根拠に、既知の脆弱性があると報告しました。調べると、OS の配布元が修正を版番号を変えずに取り込んだ(backport した)修正済みのパッケージでした。この報告は何に当たるでしょう？

1. 見逃し (false negative)
2. 正しい検知 (true positive)
3. ゼロデイ脆弱性
4. 誤検知 (false positive)

<details><summary>答えと解説</summary>

正解: **4**

実際には脆弱性が残っていないのに「ある」と報告しているので、誤検知 (false positive) です。版番号だけで判定する非認証スキャンで起きやすく、認証スキャンでインストール済みパッケージの修正状況を直接確かめると減らせます。見逃しは逆に、実在する脆弱性を報告しないことです。ゼロデイは修正プログラムがまだ存在しない脆弱性のことで、この状況とは関係ありません。

</details>

## 3. ペネトレーションテスト

### ペネトレーションテストとは

ペネトレーションテスト (penetration test) は、発見した脆弱性を**実際に悪用して**「本当に侵入できるのか、どこまで到達できるのか」を実証する活動です。スキャンが「弱点のリスト化」なら、ペネトレは「攻撃の実証実験」です。

### 実施前の鉄則(超頻出)

テスト行為は外形的には攻撃そのものです。必ず事前に、**経営層の書面による許可**と**交戦規定 (rules of engagement)** ——対象範囲、時間帯、使ってよい手法、緊急連絡先——を取り決めます。これを欠くと不正アクセスとして法的責任を問われかねません。

交戦規定の例です。

```
対象範囲: 203.0.113.10〜203.0.113.12(公開 Web サーバー3台)
対象外  : 決済データベース、取引先のシステム
実施時間: 6月14日(土)22:00〜翌6:00
禁止事項: サービス停止を狙う攻撃(DoS)、本番データの削除・変更
緊急連絡: 障害が起きたら直ちに中止し、情報システム部の当番へ電話
```

### テストのフェーズ

1. 偵察 (reconnaissance) — 公開情報収集(会社の Web サイト、DNS、SNS から社員名やメールアドレスの形式などを集める)
2. スキャンと列挙 (scanning/enumeration) — 開いているポートや動いているソフトを調べ、ユーザー名や共有フォルダなどを一覧にする
3. アクセス獲得 (gaining access) — 脆弱性の悪用(例: 古い Web サーバーの脆弱性を突き、サーバー上でコマンドを実行できる状態にする)
4. アクセス維持 (maintaining access) — 侵入を続けられるか(再侵入用の裏口=バックドアを置けるかなど)を確かめる
5. 報告 (reporting) — **最も価値のある成果物**

### 事前知識による分類

| 方式 | テスターに与える情報 | ねらい |
|---|---|---|
| ホワイトボックス (white/crystal box) | 構成図・ソースなど全情報 | 短時間で深く網羅的に |
| グレーボックス (gray box) | 一部の情報 | 内部犯・準内部者の想定 |
| ブラックボックス (black box) | ほぼゼロ | 外部攻撃者のリアルな想定 |

### チーム演習

- **レッドチーム**: 攻撃役
- **ブルーチーム**: 防御役
- **パープルチーム**: 両者の学びを共有・統合して改善につなげる役割
- **ホワイトチーム**: 演習の審判・運営役(ルールを決め、進行を管理する)

💡 コツ: テストが終わったら報告書の指摘を修正し、**再テストで修正を確認**するまでがワンセットです。また、ソーシャルエンジニアリング(人をだまして情報や操作を引き出す手口。偽メールで誘うフィッシングなど)のテストは、人事・法務と調整し「従業員を罰するためではなく教育のため」に行うのが CISSP 的な姿勢です。

### 確認問題

**問1.** ペネトレーションテストを開始する前に、必ず(MUST)整えておくべきものはどれでしょう？

1. 最新のゼロデイ攻撃ツール
2. 対象範囲と手法を定めた交戦規定と、経営層の書面による許可
3. 全従業員への事前周知メール
4. テスト対象システムの完全なソースコード

<details><summary>答えと解説</summary>

正解: **2**

ペネトレは外形的に攻撃と同じ行為なので、範囲・時間帯・手法・連絡体制を定めた交戦規定 (rules of engagement) と書面の許可が必須です。これを欠くと法的責任問題になります。全従業員への周知は、防御側の反応も見たいテスト(とくにレッドチーム演習)ではむしろ行わないことが多く、ソースコードが要るのはホワイトボックス方式だけです。ゼロデイ(修正プログラムがまだ出ていない脆弱性)を突くツールも要件ではありません。

</details>

**問2.** 外部の攻撃者が得られる情報だけでどこまで侵入できるかを最も現実的に模擬したい場合、採用すべきテスト方式はどれでしょう？

1. ホワイトボックステスト
2. グレーボックステスト
3. ブラックボックステスト
4. ソースコードレビュー

<details><summary>答えと解説</summary>

正解: **3**

ブラックボックステストはテスターに内部情報をほぼ与えず、外部攻撃者と同じ条件で実施するため、外部からの攻撃の現実的な模擬に最適です。ホワイトボックスは全情報を与えて短時間で深く調べる方式、グレーボックスは一部情報を与えて内部者や準内部者を想定する方式です。ソースコードレビューは静的な検査であり侵入の実証にはなりません。『目的に合う知識レベルを選ぶ』のがこの論点の問われ方です。

</details>

**問3.** レッドチーム演習の結果を防御側と共有し、攻撃と防御双方の知見を統合して組織の検知・対応能力を改善する役割はどれでしょう？

1. ブルーチーム
2. ホワイトチーム
3. グリーンチーム
4. パープルチーム

<details><summary>答えと解説</summary>

正解: **4**

攻撃役(レッド)と防御役(ブルー)の知見を混ぜて改善につなげるのがパープルチームです(赤+青=紫、と覚えます)。ブルーチームは防御役そのもの、ホワイトチームは演習の審判・運営役を指すことがあります。グリーンチームは一般的な用語ではありません。チームの色の役割分担は知識問題として素直に出ます。

</details>

**問4.** ペネトレーションテストの成果物のうち、組織にとって最も価値がある(MOST valuable)ものはどれでしょう？

1. 侵入に成功した証拠のスクリーンショット
2. 発見事項・リスク・修正の推奨を含む最終報告書
3. テスト中に取得した管理者パスワードの一覧
4. 使用した攻撃ツールの一覧

<details><summary>答えと解説</summary>

正解: **2**

テストの目的は「侵入できた」と自慢することではなく、組織が弱点を理解して直せるようになることです。したがって発見事項とリスク評価、修正の推奨をまとめた報告書が最大の価値を持ちます。スクリーンショットやパスワードは報告書を裏付ける素材にすぎず、むしろ厳重に保護・廃棄すべき機微情報です。ツール一覧は参考情報です。『テストは報告と修正確認までがワンセット』と覚えましょう。

</details>

**問5.** フィッシングメールへの耐性を測るソーシャルエンジニアリングテストを実施したところ、開封した従業員が多数いました。セキュリティ管理者として最も適切な(BEST)対応はどれでしょう？

1. 開封した従業員の氏名を社内に公表して再発を防ぐ
2. 開封した従業員を懲戒処分にする
3. 結果を匿名化して傾向を分析し、教育・訓練プログラムを強化する
4. テスト結果を破棄し、何もしなかったことにする

<details><summary>答えと解説</summary>

正解: **3**

ソーシャルエンジニアリングテストの目的は従業員を罰することではなく、組織の弱点を把握して教育で改善することです。氏名公表や懲戒は信頼を壊し、以後の報告文化(怪しいメールを申告する行動)を萎縮させるため逆効果です。結果の破棄はテストの意味を失わせ、デューケアにも反します。『人を罰するより、プロセスと教育を改善する』という CISSP のマネジメント視点が問われる典型問題です。

</details>
