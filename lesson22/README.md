# 第22章 監査・ログレビュー・報告とメトリクス【D6】

セキュリティ対策は「作って終わり」ではなく、第三者の目で検証し、結果を経営層に伝えて初めて機能します。この章では監査の種類とSOC報告書の読み分け、ログレビューや合成トランザクションなど技術的コントロールのテスト手法、そしてKPI/KRIを使った報告のしかたを学びます。「どの報告書を求めるべきか」「誰に・どの言葉で伝えるか」というシナリオ問題が頻出の分野です。

## 1. セキュリティ監査とSOC報告書

### 監査の大原則 — 独立性

監査 (audit) の価値は**独立性 (independence)** に支えられています。自分が構築・運用したコントロールを自分で監査すると、利害の衝突で甘い評価になりがちです。「セキュリティ運用チームが自分たちの作業をレビューしている」という状況は、試験では真っ先に直すべき問題点として出題されます。

| 監査の種類 | 実施者 | 特徴 |
|---|---|---|
| 内部監査 (internal audit) | 自組織の内部監査部門 | 継続的・低コスト。経営陣への報告ラインで独立性を確保 |
| 外部監査 (external audit) | 独立した監査法人 | 客観性が高く、規制対応や株主向けに信頼される |
| 第三者監査 (third-party audit) | 取引先・規制当局(またはその代理) | 契約の監査権 (right to audit) 条項などに基づき実施される |

### SOC報告書 — クラウド時代の「成績表」

クラウド事業者の内部統制は、SSAE 18(米国)/ ISAE 3402(国際)という監査基準に基づく **SOC (System and Organization Controls) 報告書**で確認します。

| 報告書 | 対象 | 共有範囲 |
|---|---|---|
| SOC 1 | 財務報告に関わる統制 | 利用企業の経理・監査人 |
| SOC 2 | セキュリティ・可用性などのTrustサービス基準 | NDA のもとで顧客に共有 |
| SOC 3 | SOC 2 の要約 | 一般公開可能(Webサイト掲載など) |

さらに **Type Ⅰ**(ある時点のコントロールの「設計」の評価)と **Type Ⅱ**(通常6〜12か月の期間にわたる「運用の有効性」の評価)に分かれます。

💡 コツ: クラウドベンダーのセキュリティを評価するなら、求めるべきは **SOC 2 Type Ⅱ** が定番の正解です。「Type Ⅱは期間・運用・最も信頼できる」とセットで覚えましょう。SOC 3 は公開用のダイジェストなので、深い評価には使えません。

### 確認問題

**問1.** クラウド事業者の選定にあたり、セキュリティ統制が過去1年間にわたって有効に運用されていたことを確認したいと考えています。入手すべき報告書として最も適切 (BEST) なものはどれでしょうか？

1. SOC 1 Type Ⅱ
2. SOC 2 Type Ⅰ
3. SOC 2 Type Ⅱ
4. SOC 3

<details><summary>答えと解説</summary>

正解: **3**

「セキュリティ統制」なので SOC 2、「1年間にわたる運用の有効性」なので Type Ⅱです。SOC 1 は財務報告に関わる統制が対象なので目的が違います。SOC 2 Type Ⅰ はある時点の設計評価にすぎず、期間の運用状況はわかりません。SOC 3 は一般公開用の要約で、詳細な評価には不十分です。「セキュリティ=SOC 2」「期間=Type Ⅱ」の2段階で絞るのがひっかけ対策です。

</details>

**問2.** セキュリティ運用チームが、自分たちの管理するファイアウォールのルールセットを四半期ごとに自らレビューし、問題なしと報告しています。この体制の最大の問題点はどれでしょうか？

1. 監査の独立性が確保されていない
2. レビューの頻度が多すぎる
3. ファイアウォールのレビューは年1回で十分である
4. レビュー結果を文書化していない

<details><summary>答えと解説</summary>

正解: **1**

自分が構築・運用したコントロールを自分で評価すると利害が衝突し、客観的な評価になりません。これが独立性 (independence) の欠如です。四半期ごとのレビューはむしろ望ましい頻度であり、「多すぎる」「年1回で十分」はいずれも誤りです。文書化の有無は問題文からは判断できません。試験では「誰がレビューしているか」に注目するのがコツです。

</details>

**問3.** SOC 3 報告書の説明として正しいものはどれでしょうか？

1. 財務報告に関わる内部統制を詳細に評価した報告書である
2. NDA を結んだ顧客だけに開示される詳細な報告書である
3. 特定時点におけるコントロール設計のみを評価した報告書である
4. 一般公開できる要約版の報告書である

<details><summary>答えと解説</summary>

正解: **4**

SOC 3 は SOC 2 の内容を要約し、マーケティング目的などで一般公開できるようにした報告書です。財務報告の統制を扱うのは SOC 1、NDA のもとで顧客に共有される詳細版は SOC 2 です。「特定時点の設計評価」は Type Ⅰ の説明で、SOC 1〜3 の区分とは軸が異なります。SOC の番号(何を評価するか)と Type(いつ・どう評価するか)を混ぜてくるのが典型的なひっかけです。

</details>

**問4.** SOC 2 の Type Ⅰ と Type Ⅱ の違いの説明として最も適切なものはどれでしょうか？

1. Type Ⅰ は内部監査、Type Ⅱ は外部監査を指す
2. Type Ⅰ はある時点の統制の設計を、Type Ⅱ は一定期間にわたる運用の有効性を評価する
3. Type Ⅰ はセキュリティ、Type Ⅱ は可用性を評価する
4. Type Ⅰ は公開用、Type Ⅱ は社内用の報告書である

<details><summary>答えと解説</summary>

正解: **2**

Type Ⅰ は「ある時点 (point in time)」にコントロールが適切に設計されているかを、Type Ⅱ は通常6〜12か月の「期間」にわたり実際に有効に運用されたかを評価します。だからこそ Type Ⅱ の方が信頼性が高いのです。SOC 報告書はどちらも独立した監査人(外部)が作成するため「内部/外部」の区別ではありません。セキュリティや可用性は SOC 2 の Trust サービス基準の区分であり、公開用は SOC 3 の特徴です。

</details>

**問5.** あなたは委託先のデータセンター事業者に対する監査を計画しています。契約に基づいて自社(顧客)側の要求で監査を実施できる根拠として、契約に含めておくべき条項はどれでしょうか？

1. 秘密保持 (NDA) 条項
2. 監査権 (right to audit) 条項
3. サービスレベル (SLA) 条項
4. 損害賠償条項

<details><summary>答えと解説</summary>

正解: **2**

顧客側が委託先を監査(第三者監査)するには、契約に監査権 (right to audit) 条項を入れておく必要があります。NDA は情報の秘密保持、SLA はサービス品質の保証水準、損害賠償条項は事故後の金銭的補償に関するもので、いずれも「監査を実施する権利」の根拠にはなりません。ベンダー管理では「監査したければ契約時に権利を確保しておく」が鉄則で、契約後に要求しても拒否されうる点がひっかけどころです。

</details>

## 2. 技術的コントロールのテスト

### コントロールは「動いているか」を試験する

セキュリティコントロールは導入しただけでは信用できません。定期的にテストして、設計どおり動いていることを確認します。

### ログレビューと時刻同期

ログは**定期的にレビュー**して初めて発見的コントロールとして機能します。複数システムのログを突き合わせる前提として、**NTP (Network Time Protocol) による時刻同期**が不可欠です。時刻がずれていると、イベントの前後関係を再構成できず、調査でも証拠価値が下がります。

### 稼働監視の2つのアプローチ

| 手法 | 仕組み | 特徴 |
|---|---|---|
| 合成トランザクション (synthetic transaction) | スクリプトが擬似的な操作(ログイン→検索→購入など)を定期実行 | 実ユーザーがいない深夜でも異常を検知できる |
| 実ユーザー監視 (RUM: Real User Monitoring) | 実際の利用者のトラフィックを観測 | 現実の体感品質がわかるが、利用がないと検知できない |

### コードとインターフェースのテスト

- **コードレビュー**: 他人の目でソースを確認します。最も形式的な手法が **Fagan 検査**で、計画→概要説明→準備→検査→手直し→フォローアップの6段階を踏みます
- **インターフェーステスト**: API・ユーザーインターフェース・物理インターフェースの境界面を検証します
- **ミスユースケーステスト (misuse case testing)**: 「攻撃者ならどう悪用するか」というシナリオを作って試します
- **テストカバレッジ分析**: 文 (statement)・分岐 (branch)・条件 (condition)・ループの各カバレッジで「どこまでテストしたか」を測ります

💡 コツ: 「深夜や休日も含めてサイトの異常に気づきたい」→合成トランザクション、「実際の顧客の体験を知りたい」→RUM、と目的語で選び分けます。

### 確認問題

**問1.** ECサイトの購入フローが深夜や休日でも正常に動作していることを継続的に確認したいと考えています。最も適切 (BEST) な手法はどれでしょうか？

1. 実ユーザー監視 (RUM)
2. 合成トランザクション
3. 年次のペネトレーションテスト
4. 月次のログレビュー

<details><summary>答えと解説</summary>

正解: **2**

合成トランザクションは、スクリプトが擬似ユーザーとして購入フローなどを定期実行する監視手法で、実ユーザーがいない時間帯でも異常を検知できます。RUM は実際の利用者のトラフィックを観測するため、深夜に利用者がいなければ異常に気づけません。ペネトレーションテストは脆弱性の発見が目的で頻度も低く、ログレビューは月次では「継続的な確認」になりません。「利用者ゼロでも監視したい」というキーワードが合成トランザクションのサインです。

</details>

**問2.** 複数のサーバーやネットワーク機器のログを突き合わせてインシデントの時系列を再構成するために、前提として最も重要 (MOST important) なものはどれでしょうか？

1. すべてのログを同一のファイル形式に統一すること
2. ログを毎日印刷して保管すること
3. ログの保存期間を無期限にすること
4. NTP によって全機器の時刻を同期しておくこと

<details><summary>答えと解説</summary>

正解: **4**

イベントの前後関係を正しく並べるには、各機器のタイムスタンプが同じ時刻源に同期している必要があります。これを実現するのが NTP です。ファイル形式の統一は便利ですが SIEM 側で正規化できるため「前提」ではありません。印刷保管は非現実的で、保存期間の無期限化は保持ポリシーに反しコストとリスクを増やします。「時系列の再構成」と来たら時刻同期、が定番の対応づけです。

</details>

**問3.** 最も形式的で構造化されたコードレビュー手法として知られ、計画からフォローアップまでの決まった段階を踏むものはどれでしょうか？

1. Fagan 検査 (Fagan inspection)
2. ペアプログラミング
3. オーバーザショルダーレビュー
4. ツールによる静的解析

<details><summary>答えと解説</summary>

正解: **1**

Fagan 検査は、計画→概要説明→準備→検査→手直し→フォローアップの6段階を踏む、最も形式的なコードレビュー手法です。ペアプログラミングやオーバーザショルダー(肩越しの確認)は軽量で非形式的なレビューです。静的解析はツールによる自動チェックであり、人によるレビューの形式度という軸の話ではありません。「最も形式的なレビュー=Fagan」は一対一で覚えてよい知識です。

</details>

**問4.** Webアプリケーションのテストで「攻撃者がパスワードリセット機能を悪用してアカウントを乗っ取るシナリオ」を作成して検証しました。このテストはどれに分類されるでしょうか？

1. ユースケーステスト
2. 回帰テスト
3. ミスユースケーステスト
4. 単体テスト

<details><summary>答えと解説</summary>

正解: **3**

正規の使い方ではなく「悪用シナリオ」を起点に検証するのがミスユースケーステスト (misuse case testing) です。ユースケーステストは正規の利用シナリオの検証、回帰テストは変更後に既存機能が壊れていないかの確認、単体テストは関数・モジュール単位の動作確認です。「attacker の視点のシナリオ」という言葉が出たらミスユースケースを選ぶのがポイントで、ユースケーステストとの対比がひっかけに使われます。

</details>

**問5.** テストカバレッジ分析において「すべての if 文の真と偽の両方の経路を少なくとも1回実行したか」を測る指標はどれでしょうか？

1. 文カバレッジ (statement coverage)
2. 分岐カバレッジ (branch coverage)
3. ループカバレッジ (loop coverage)
4. インターフェースカバレッジ

<details><summary>答えと解説</summary>

正解: **2**

if 文などの分岐の真・偽両方の経路を通したかを測るのが分岐カバレッジです。文カバレッジは「各行を1回でも実行したか」なので、真側だけ通っても満たせてしまう点が分岐カバレッジとの違いです。ループカバレッジは繰り返し回数(0回・1回・複数回)の網羅を見ます。インターフェースカバレッジという標準的なカバレッジ指標はなく、インターフェーステストと混同させるダミーです。

</details>

## 3. メトリクスと経営層への報告

### 測れないものは管理できない

セキュリティプログラムの成果は**メトリクス (metrics)** で示します。よいメトリクスの条件は、**一貫して客観的に測定できる**こと、**収集コストが見合う**こと、そして**意思決定に使える**ことです。

| 指標 | 意味 | 例 |
|---|---|---|
| KPI (Key Performance Indicator) | これまでの達成度を示す「実績」の指標 | パッチ適用までの平均日数、インシデント対応時間 |
| KRI (Key Risk Indicator) | 将来のリスク上昇を示す「先行」指標 | 未対応脆弱性の増加傾向、退職率の急上昇 |

KPI は「うまくやれているか」、KRI は「この先危なくないか」を見る、と覚えましょう。

### 経営層への伝え方

経営層 (senior management) への報告は、技術用語ではなく**ビジネスへの影響**(金額・事業停止時間・法的リスク)の言葉に翻訳するのが鉄則です。「CVSS 9.8 の脆弱性が42件」ではなく「決済サービスが停止し1日あたり○百万円の損失につながるリスク」と伝えます。

### 監査報告書と指摘事項への対応

監査報告書は「事実(発見事項)→リスク(影響)→推奨(改善提案)」の順で構成します。指摘事項には是正計画 (remediation plan) を立てて対応しますが、コストが見合わない場合は**経営陣がリスク受容を正式に文書化**するという選択肢もあります。放置と受容はまったく別物です。

### トレーニングの効果測定

セキュリティ教育も測定対象です。フィッシング訓練の**クリック率や報告率の推移**は、意識向上の効果を示す代表的なメトリクスです。

💡 コツ: 「経営層に報告する」と来たら、正解はほぼ必ず「ビジネス影響の言葉で・簡潔に」です。技術的詳細を並べる選択肢はダミーと考えましょう。

### 確認問題

**問1.** 「未対応の脆弱性件数がこの3か月で2倍に増えている」という指標は、将来のリスク上昇の兆候を捉えるために使われます。この種の指標を何と呼ぶでしょうか？

1. KPI (重要業績評価指標)
2. SLA (サービスレベル合意)
3. ROI (投資対効果)
4. KRI (重要リスク指標)

<details><summary>答えと解説</summary>

正解: **4**

将来のリスク上昇を先行して示す指標が KRI (Key Risk Indicator) です。KPI は過去〜現在の達成度(実績)を測る指標で、「increase する前に気づく」という目的には向きません。SLA はサービス品質の合意水準、ROI は投資の費用対効果で、どちらもリスクの先行指標ではありません。「先行指標・将来・兆候」というキーワードが KRI、「実績・達成度」が KPI という対応づけがひっかけ対策です。

</details>

**問2.** CISO が取締役会にセキュリティ状況を報告します。最も適切 (BEST) な報告のしかたはどれでしょうか？

1. リスクを事業への影響(金額や停止時間)に翻訳して簡潔に伝える
2. 検出した脆弱性の CVSS スコア一覧を全件提示する
3. 導入済みセキュリティ製品の設定値を詳細に説明する
4. 専門性を示すため技術用語を多用して網羅的に報告する

<details><summary>答えと解説</summary>

正解: **1**

経営層への報告は、技術的事実をビジネスの言葉(損失額・事業停止・法的リスク)に翻訳し、意思決定に必要な粒度で簡潔に伝えるのが正解です。CVSS 全件一覧や製品の設定値は経営の意思決定に直結せず、技術用語の多用はむしろ伝達を妨げます。CISSP では「聞き手が誰か」で答えが変わります。経営層=ビジネス影響、技術チーム=技術的詳細、という使い分けを問うのが定番パターンです。

</details>

**問3.** 監査で指摘された統制の不備について、是正コストが想定損失を大きく上回ることが判明しました。組織として最も適切 (MOST appropriate) な対応はどれでしょうか？

1. 指摘事項を監査報告書から削除してもらう
2. 担当者レベルの判断で対応を保留する
3. 経営陣がリスク受容を正式に決定し、文書化する
4. コストに関係なく直ちに是正する

<details><summary>答えと解説</summary>

正解: **3**

対策コストがリスク(想定損失)を上回る場合、リスク受容は合理的な選択肢ですが、必ず経営陣が正式に決定し文書化する必要があります。受容の権限は経営側にあり、担当者の独断での保留は「放置」であって受容ではありません。監査報告書から指摘を削除させるのは監査の独立性を損なう不正行為です。「コストに関係なく是正」は費用対効果の原則に反します。「受容=経営陣+文書化」のセットで覚えましょう。

</details>

**問4.** セキュリティ意識向上トレーニングの効果を測定する指標として最も直接的なものはどれでしょうか？

1. トレーニング教材の作成に要した時間
2. フィッシング訓練でリンクをクリックした従業員の割合の推移
3. セキュリティ部門の人員数
4. 導入しているセキュリティ製品の数

<details><summary>答えと解説</summary>

正解: **2**

**問5.** セキュリティメトリクスとして採用する指標を選ぶ際の考え方として最も適切なものはどれでしょうか？

1. 収集できるデータはすべて指標化し、できるだけ多く報告する
2. 測定者の主観的な印象を重視した指標を選ぶ
3. 一度決めた指標は状況が変わっても変更しない
4. 一貫して客観的に測定でき、収集コストに見合い、意思決定に役立つ指標を選ぶ

<details><summary>答えと解説</summary>

正解: **4**

よいメトリクスの条件は「一貫性・客観性・費用対効果・意思決定への有用性」です。収集できるものを全部報告すると重要な情報が埋もれ、かえって意思決定を妨げます。主観的な印象は人や日によってぶれるため指標に不向きです。指標は事業環境や脅威の変化に合わせて定期的に見直すべきもので、固定化は形骸化を招きます。「多ければよい」という選択肢は量と質をすり替えるひっかけです。

</details>
