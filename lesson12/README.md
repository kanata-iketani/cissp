# 第12章 暗号技術②（PKI・鍵管理・暗号への攻撃）【D3】

暗号アルゴリズム単体が安全でも、鍵の管理や運用が甘ければシステム全体は破られます。この章では公開鍵を「信頼できるもの」にする PKI の仕組み、鍵のライフサイクル管理、そして攻撃者が暗号をどう破ろうとするかを学びます。CISSP では「アルゴリズムの数学」よりも「運用と管理の正しさ」が問われることを意識して読み進めてください。

## 1. PKI（公開鍵基盤）— 公開鍵を信頼できるものにする仕組み

### なぜ PKI が必要か

公開鍵暗号は便利ですが、「この公開鍵は本当に本人のものか？」を保証する仕組みがなければ、攻撃者が偽の公開鍵をばらまけてしまいます。そこで信頼できる第三者が「この公開鍵は確かにこの人・このサーバーのものです」と証明する仕組みが **PKI (Public Key Infrastructure)** です。

### デジタル証明書とは

**デジタル証明書**は「持ち主の名前+その公開鍵」に、CA(認証局)が自分の秘密鍵で**デジタル署名**(L11 ch04)を付けたデータです。受け取った人は CA の公開鍵で署名を検証し、成功すれば「この公開鍵は確かに www.example.com のもの」と信じられます。署名があるので、途中で公開鍵を差し替えると検証に失敗します。

### 登場人物と役割

| 役割 | 仕事 |
|---|---|
| **CA** (Certification Authority / 認証局) | デジタル証明書を**発行・失効**する。自分の秘密鍵で証明書に署名する |
| **RA** (Registration Authority / 登録局) | 申請者の**本人確認（登録審査）だけ**を行う。**証明書の発行はしない** |
| **CRL** (Certificate Revocation List) | 失効(有効期限前に無効にすること)した証明書の一覧。定期更新のため**タイムラグがある** |
| **OCSP** (Online Certificate Status Protocol) | 証明書の失効状態を**リアルタイム**に問い合わせるプロトコル |
| **OCSP ステープリング** | サーバー自身が CA から取得した失効情報の証明を TLS 接続に**同梱**する。クライアントが CA に問い合わせる必要がなくなり、負荷とプライバシーの問題を解決 |

💡 コツ: 「RA が証明書を発行する」は超頻出のひっかけです。RA は**身元確認のみ**、発行と失効は CA の仕事です。

### 失効確認を値で見る (CRL と OCSP)

シリアル番号 `04:a1:3f:9c:…` の証明書の秘密鍵が漏れ、2026-11-10 に失効させたとします。

**CRL の場合**: CA が署名した一覧ファイルを、ブラウザが CRL 配布点からダウンロードして中を探します。

| 項目 | 値 |
|---|---|
| 発行日 (thisUpdate) | 2026-11-10 |
| 次回更新 (nextUpdate) | 2026-11-17 |
| 失効した証明書 | シリアル `04:a1:3f:9c:…` / 失効日 2026-11-10 / 理由 keyCompromise(鍵の漏えい) |

ブラウザは次回更新まで手元の一覧を使い回すことがあるため、11-10 以降に失効した証明書は、古い一覧を持つブラウザには最大で 11-17 まで有効に見えます。これがタイムラグです。一覧は失効が増えるほど大きくなります。

**OCSP の場合**: ブラウザが OCSP サーバーに「シリアル `04:a1:3f:9c:…` は?」と1件だけ問い合わせ、CA が署名した応答 **good(有効)/ revoked(失効)/ unknown(不明)** を受け取ります。上の例なら即座に revoked が返ります。ただし、ブラウザが問い合わせるたびに「誰がどのサイトを見ようとしているか」が OCSP サーバーに伝わります。

**OCSP ステープリングの場合**: サーバー (www.example.com) が数時間〜数日ごとに自分の証明書の OCSP 応答を取得しておき、TLS の接続時に証明書と一緒に渡します。応答には CA の署名があるのでサーバーが偽造することはできず、ブラウザは CA に問い合わせずに済みます。

### 証明書と信頼の連鎖

証明書は **X.509**(証明書の書式を定めた国際規格)形式が標準で、サブジェクト名・公開鍵・有効期間・発行者・シリアル番号・CA の署名などが入っています。www.example.com のサーバー証明書なら、主なフィールドは例えば次のようになります。

| フィールド | 値の例 | 意味 |
|---|---|---|
| バージョン | v3 | X.509 の版 |
| シリアル番号 | `04:a1:3f:9c:…` | 発行した CA の中で一意の番号。失効の指定に使う |
| 署名アルゴリズム | sha256WithRSAEncryption | CA が署名に使った方式(SHA-256 + RSA) |
| 発行者 (Issuer) | CN=Example Intermediate CA | 署名した CA の名前 |
| 有効期間 | 2026-11-01 〜 2027-05-19 | この期間外は無効 |
| サブジェクト (Subject) | CN=www.example.com | 証明書の持ち主 |
| サブジェクトの公開鍵 | RSA 2048ビット の公開鍵 | 持ち主の公開鍵そのもの |
| SAN (サブジェクト代替名) | DNS:www.example.com, DNS:example.com | この証明書が使えるホスト名の一覧。ブラウザは接続先の名前がここにあるかを確かめる |
| 鍵用途 (Key Usage) | digitalSignature | 公開鍵を何に使ってよいか |
| CRL 配布点 / OCSP の場所 | http://crl.example.com/int.crl / http://ocsp.example.com | 失効を確認する問い合わせ先 |
| CA の署名 | (バイト列) | 上の全項目に対する発行者 CA の署名 |

ブラウザは「サーバー証明書 → 中間 CA → ルート CA」と**証明書チェーン**をたどり、あらかじめ信頼済みのルート CA に行き着けば信頼します。

| 証明書 | 発行者 (誰が署名したか) | 置き場所 |
|---|---|---|
| ルート CA 証明書 (CN=Example Root CA) | 自分自身(**自己署名**) | OS やブラウザの**トラストストア**(最初から信頼済みとして入っている証明書の一覧) |
| 中間 CA 証明書 (CN=Example Intermediate CA) | ルート CA | サーバーが接続時にサーバー証明書と一緒に送る |
| サーバー証明書 (CN=www.example.com) | 中間 CA | サーバーが接続時に送る |

ブラウザの検証は一段ずつ進みます。①サーバー証明書の署名を**中間 CA の公開鍵**で検証 → ②中間 CA 証明書の署名を**ルート CA の公開鍵**で検証 → ③そのルート CA 証明書がトラストストアにあるか確認 → ④各証明書の有効期間、SAN に接続先の名前があるか、失効していないかを確認。どれか1つでも失敗すると警告画面になります。ルート CA の秘密鍵が漏れると配下の証明書すべてが信頼を失うため、ルート CA は**オフライン**で厳重に保管するのが鉄則です。

そのほか、検証レベルによる証明書の種類（**DV**=ドメイン所有のみ確認 / **OV**=組織の実在確認 / **EV**=最も厳格な審査）、特定の証明書や公開鍵だけを受け入れる**証明書ピンニング** (certificate pinning)、異なる PKI 同士が相互に信頼し合う**クロス認証** (cross-certification)、CA の運用ルールを定めた **CPS** (Certification Practice Statement) も押さえておきましょう。

### 確認問題

**問1.** PKI における RA（登録局）の役割として最も適切なものはどれですか。

1. デジタル証明書を発行し、CA の秘密鍵で署名する
2. 失効した証明書の一覧（CRL）を配布する
3. 証明書の申請者の本人確認（登録審査）を行う
4. ルート CA の秘密鍵をオフラインで保管する

<details><summary>答えと解説</summary>

正解: **3**

RA (Registration Authority) は証明書申請者の身元確認・登録審査だけを担当し、証明書の発行や署名は行いません。発行・署名・失効はすべて CA の仕事です。「RA が証明書を発行する」は CISSP で定番のひっかけ選択肢なので、『RA = 受付と本人確認の窓口』と覚えてください。CRL の配布もルート鍵の保管も CA 側の責務です。

</details>

**問2.** CRL と比較したときの OCSP の最大の利点はどれですか。

1. 証明書の失効状態をほぼリアルタイムに確認できる
2. CA への問い合わせが一切不要になる
3. 証明書そのものの改ざんを検知できる
4. 失効情報を暗号化して秘匿できる

<details><summary>答えと解説</summary>

正解: **1**

CRL は定期的に発行される失効リストなので、次回更新までのタイムラグの間は失効済み証明書が有効に見えてしまいます。OCSP は照会時点の失効状態をオンラインで確認できるため、この遅延をほぼ解消できます。OCSP も CA（の応答サーバー）への問い合わせは必要なので「CA への問い合わせが一切不要になる」は誤り。改ざん検知は証明書の署名検証の役割、失効情報は秘匿するものではないので残りも誤りです。

</details>

**問3.** 多数の利用者を抱える Web サービスで、クライアントから CA への失効確認の通信をなくし、プライバシーと性能の両方を改善したいと考えています。最も適切 (BEST) な技術はどれですか。

1. CRL の更新間隔を短くする
2. 証明書ピンニングを導入する
3. EV 証明書に切り替える
4. OCSP ステープリングを導入する

<details><summary>答えと解説</summary>

正解: **4**

OCSP ステープリングは、サーバー自身が CA から署名付きの失効ステータスを取得し、TLS ハンドシェイクに同梱（ステープル＝ホチキス留め）してクライアントへ渡す仕組みです。クライアントが CA に直接問い合わせなくて済むため、「どのユーザーがどのサイトを見たか」が CA に伝わるプライバシー問題と、問い合わせ負荷の両方を解決します。CRL の更新間隔短縮では通信は減らず、ピンニングと EV 証明書は失効確認の仕組みではありません。

</details>

**問4.** ルート CA の秘密鍵を保護する方法として最も適切 (BEST) なものはどれですか。

1. ルート CA を社内ネットワークの専用セグメントで常時稼働させる
2. ルート CA をオフラインにし、発行業務は中間 CA に任せる
3. ルート CA の秘密鍵を毎月ローテーションする
4. ルート CA の証明書を OCSP で常時監視する

<details><summary>答えと解説</summary>

正解: **2**

ルート CA の秘密鍵が侵害されると、その配下で発行されたすべての証明書の信頼が崩壊します。そのため、ルート CA はネットワークから切り離して（オフライン）厳重に保管し、日常の証明書発行はオンラインの中間 CA（下位 CA）に任せるのがベストプラクティスです。社内セグメントでも常時稼働ならネットワーク経由の攻撃にさらされます。ルート鍵の頻繁なローテーションは信頼チェーン全体の再構築が必要で現実的でなく、OCSP は失効確認の仕組みであって鍵の保護策ではありません。

</details>

**問5.** サーバー証明書の秘密鍵が漏えいした疑いが発覚しました。セキュリティ管理者が最初に行うべき (FIRST) ことはどれですか。

1. 新しい証明書を発行して旧証明書と並行運用する
2. 利用者全員にパスワード変更を依頼する
3. CA に失効を申請し、CRL / OCSP に反映させる
4. サーバーの TLS バージョンを最新に更新する

<details><summary>答えと解説</summary>

正解: **3**

秘密鍵が漏えいした証明書は、攻撃者がなりすましに使える状態です。最優先は CA への失効申請で、CRL / OCSP を通じて世界中のクライアントに「この証明書はもう信頼するな」と伝えることです。新証明書の発行は失効と並行して行いますが、旧証明書を生かしたままの並行運用は危険を放置します。パスワード変更や TLS バージョン更新は、この漏えいへの直接の対処ではありません。CISSP では「失効を最優先」の型を覚えておきましょう。

</details>

**問6.** ブラウザが「サーバー証明書 → 中間 CA 証明書 → ルート CA 証明書」の証明書チェーンを検証しています。サーバー証明書に付いている署名を検証するときに使う鍵はどれでしょう？

1. サーバーの秘密鍵
2. ルート CA の秘密鍵
3. 中間 CA の公開鍵
4. ブラウザの公開鍵

<details><summary>答えと解説</summary>

正解: **3**

サーバー証明書に署名したのは、その発行者である中間 CA です。署名は「発行者の秘密鍵で作り、発行者の公開鍵で検証する」ので、使うのは中間 CA の公開鍵です(中間 CA の公開鍵は、サーバーが一緒に送ってくる中間 CA 証明書に入っています)。次の段階では、中間 CA 証明書の署名をルート CA の公開鍵で検証し、最後にルート CA がトラストストアにあるかを確かめます。「サーバーの秘密鍵」と「ルート CA の秘密鍵」は持ち主しか持っておらず、検証する側が使うことはありません。「ブラウザの公開鍵」は、通常のサーバー証明書の検証には登場しません。

</details>

## 2. 鍵管理 — 暗号の強さは鍵の守り方で決まる

### 鍵のライフサイクル

どんなに強いアルゴリズムでも、鍵がずさんに扱われれば意味がありません。鍵には **生成 → 配送 → 保管 → 利用 → ローテーション（更新）→ 破棄** というライフサイクルがあり、各段階に管理策が必要です。

| 段階 | ポイント |
|---|---|
| 生成 | 十分な鍵長と、予測不能な乱数で生成する |
| 配送 | 共通鍵は安全な経路で渡す（公開鍵暗号やディフィー・ヘルマンで解決） |
| 保管 | 鍵は**平文で保存しない**。暗号化したデータと鍵は**別の場所**に置く |
| 利用 | 用途ごとに鍵を分ける（署名用と暗号化用を兼用しない） |
| ローテーション | 定期的・または漏えい疑い時に更新し、漏えい時の影響範囲を限定する |
| 破棄 | 不要になった鍵は完全に消去する（鍵を消せば暗号文は実質読めなくなる） |

「データと鍵を分離」を具体的に書くと、例えば次のような配置になります。

| もの | 置き場所 |
|---|---|
| 顧客データベース (AES-256 で暗号化済み) | DB サーバー |
| データを暗号化した鍵 (DEK: データ暗号化鍵) | DB サーバー。ただし**別の鍵で暗号化した状態**で保存 |
| DEK を暗号化した鍵 (KEK: 鍵暗号化鍵) | HSM (下で説明) や鍵管理サービスの中。外には出さない |

DB サーバーが丸ごと盗まれても、KEK がないので DEK を取り出せず、データも読めません。ローテーションでは KEK を新しくして DEK を包み直すだけで済み、大量のデータを暗号化し直さなくてよいのも利点です。

### 組織的な鍵の守り方

- **鍵エスクロー (key escrow)**: 鍵のコピーを信頼できる第三者や組織内の管理部門に預け、鍵の紛失や退職・捜査などの際に復元できるようにする仕組みです。復元を行う担当者を**リカバリエージェント** (recovery agent) と呼びます
- **M of N 制御（分割知識 / split knowledge）**: 重要な鍵の操作に「N 人中 M 人以上の同意」を必要とする仕組みです。例えば 3 of 5 なら 5 人の管理者のうち 3 人が揃わないとルート鍵を復元できません。単独の内部犯行を防ぎます
- **HSM (Hardware Security Module)**: 鍵の生成・保管・暗号演算を行う耐タンパー性(こじ開けや分解を検知すると中の鍵を消去するなど、物理的な攻撃に強い性質)のある専用ハードウェアです。鍵が装置の外に平文で出ないことが最大の価値で、CA の署名鍵や決済システムで使われます。**TPM** は PC のマザーボードに載る同種のチップです

### 鍵長とアジリティ

鍵長は長いほど安全ですが処理は遅くなります。楕円曲線暗号 (ECC) は短い鍵で RSA と同等の強度を持ち、**ECC 256 ビット ≒ RSA 3072 ビット**が目安です。方式が違うと同じ強さでも鍵長がまったく違う点に注意します(NIST SP 800-57 の目安)。

| 強さ(共通鍵に換算) | 共通鍵 | RSA・DH | ECC |
|---|---|---|---|
| 112 ビット | 3DES(3鍵) | 2048 ビット | 224 ビット |
| 128 ビット | AES-128 | 3072 ビット | 256 ビット |
| 256 ビット | AES-256 | 15360 ビット | 512 ビット |

また、アルゴリズムが危殆化(弱点が見つかり安全性が損なわれること)したとき速やかに別方式へ移行できる設計を**暗号アジリティ** (cryptographic agility) と呼び、近年の設計で重視されます。

💡 コツ: 鍵管理の問題で迷ったら「鍵を平文で置かない」「鍵とデータを分離」「単独の人間に全権を持たせない」の3原則に沿う選択肢を選びましょう。

### 確認問題

**問1.** 組織のルート CA の秘密鍵の復元操作に、5 人の管理者のうち 3 人以上の同席を必須とする運用を導入しました。この管理策の主な目的はどれですか。

1. 鍵の復元作業を高速化する
2. 単独の管理者による不正な鍵の持ち出しを防ぐ
3. 鍵のバックアップ容量を削減する
4. 管理者の教育コストを削減する

<details><summary>答えと解説</summary>

正解: **2**

これは M of N 制御（分割知識 / split knowledge）で、重要な鍵操作に複数人の同意を要求することで、1 人の内部者による不正（単独犯行）を防ぐのが目的です。職務分掌・ツーパーソンコントロールと同じ発想の暗号運用版と覚えましょう。複数人を集める分だけ作業はむしろ遅くなるので「鍵の復元作業を高速化する」は誤り。容量や教育コストとは無関係です。

</details>

**問2.** 鍵エスクロー (key escrow) を導入する主な目的として最も適切なものはどれですか。

1. 暗号化処理を高速化するため
2. 鍵の生成に使う乱数の品質を高めるため
3. 通信相手に安全に共通鍵を配送するため
4. 鍵の紛失や担当者の退職時にもデータを復元できるようにするため

<details><summary>答えと解説</summary>

正解: **4**

鍵エスクローは、鍵のコピーを信頼できる第三者または組織内の管理部門に預けておき、鍵の紛失・担当者の退職・法執行機関の捜査などの際にリカバリエージェントがデータを復元できるようにする仕組みです。暗号化されたまま誰も読めなくなる「データの人質化」を防ぎます。処理速度や乱数品質とは無関係で、鍵配送の問題を解決するのは公開鍵暗号や鍵交換プロトコルの役割です。

</details>

**問3.** 決済システムで使う署名鍵について「鍵が装置の外に平文で出ない」ことを保証したい場合、最も適切 (BEST) な保管場所はどれですか。

1. HSM（ハードウェアセキュリティモジュール）
2. アクセス制御された共有ファイルサーバー
3. 管理者端末の暗号化されたフォルダ
4. パスワード付きの ZIP ファイル

<details><summary>答えと解説</summary>

正解: **1**

HSM は鍵の生成・保管・暗号演算を内部で完結させる耐タンパー性の専用ハードウェアで、鍵が平文のまま装置外へ出ないことが最大の特徴です。CA の署名鍵や決済基盤など、最重要の鍵は HSM に置くのが定石です。ファイルサーバーや管理者端末では、OS やバックアップ経由で鍵が平文で読み出されるリスクが残ります。パスワード付き ZIP は論外の弱さで、ひっかけの「もっともらしいが弱い」選択肢です。

</details>

**問4.** 共通鍵暗号の「鍵配送問題」を解決する方法として最も適切 (BEST) なものはどれですか。

1. 鍵を複数の CD に分けて郵送する
2. 鍵を SMS で送信する
3. 公開鍵暗号や Diffie-Hellman 鍵交換を使ってセッション鍵を共有する

正解: **3**

</details>

**問5.** 「現在使用中の暗号アルゴリズムが将来危殆化しても、システム改修を最小限にして新しいアルゴリズムへ移行できるように設計しておく」考え方を何と呼びますか。

1. 暗号エスクロー
2. 暗号アジリティ (cryptographic agility)
3. フォワードシークレシー
4. ゼロ知識証明

<details><summary>答えと解説</summary>

正解: **2**

暗号アジリティは、アルゴリズムや鍵長をハードコードせず、設定や部品の差し替えで移行できるようにしておく設計思想です。量子コンピュータによる既存公開鍵暗号の危殆化が見込まれる今、ポスト量子暗号への移行準備として特に重視されています。エスクローは鍵の預託、フォワードシークレシー（前方秘匿性）は長期鍵が漏れても過去のセッションが解読されない性質、ゼロ知識証明は秘密を明かさず知っていることを証明する技術で、いずれも別概念です。

</details>

## 3. 暗号への攻撃 — 攻撃者は数学ではなく運用と実装を狙う

### 攻撃者が持つ情報による4分類（超頻出）

暗号解読攻撃は「攻撃者が何を手にしているか」で分類されます。下に行くほど攻撃者に有利です。

| 攻撃 | 攻撃者が持っているもの |
|---|---|
| **暗号文単独攻撃** (ciphertext-only) | 暗号文だけ |
| **既知平文攻撃** (known-plaintext) | 平文と対応する暗号文の**ペア** |
| **選択平文攻撃** (chosen-plaintext) | 自分が**選んだ平文**を暗号化させた結果 |
| **選択暗号文攻撃** (chosen-ciphertext) | 自分が**選んだ暗号文**を復号させた結果 |

L11 ch01 のシーザー暗号(鍵=ずらす数)で、4分類がどう違うかを見ます。

| 攻撃 | 攻撃者の手元 | 攻撃者がすること |
|---|---|---|
| 暗号文単独 | `DWWDFN` だけ | 鍵 1〜25 を全部試し、意味の通る単語になるものを探す |
| 既知平文 | `ATTACK` ↔ `DWWDFN` のペア | A→D から鍵が 3 だとすぐ分かる |
| 選択平文 | 暗号化装置に `AAAAAA` を入れさせ `DDDDDD` を得る | 選んだ入力なので鍵 3 が一目で分かる |
| 選択暗号文 | 復号装置に `BBBBBB` を入れさせ `YYYYYY` を得る | B→Y(3つ戻す)から鍵 3 が分かる |

現代の暗号(AES など)は、選択平文や選択暗号文の条件でも鍵が分からないように設計されています。

💡 コツ: 「入手した」なら既知 (known)、「自分で選んで暗号化/復号させられる」なら選択 (chosen) です。問題文の動詞に注目しましょう。

### 代表的な攻撃手法

- **総当たり攻撃** (brute force): すべての鍵を試す。56ビットの DES は 2^56 通りなので専用機で数日以内に破れた実績がありますが、AES-128 の 2^128 通りは現実的な時間では試しきれません。対策は十分な鍵長と試行回数制限
- **頻度分析** (frequency analysis): 文字の出現頻度から古典的な換字式暗号を破る
- **リプレイ攻撃** (replay): 正規の通信を記録してそのまま再送する。対策は**タイムスタンプとノンス**（使い捨ての乱数）。例えばカウンタ方式の車のキーでは、押すたびに番号が増え(…1040, 1041, 1042)、車は「最後に受け付けた番号より大きいものだけ有効」とします。攻撃者が録音した 1041 の信号を後から再送しても、車はすでに 1042 まで受け付けているので拒否します
- **中間者攻撃** (man-in-the-middle / on-path): 通信の間に割り込み双方になりすます。例えば利用者の PC (192.0.2.10) が www.example.com (203.0.113.5) へ接続したつもりが、実際は攻撃者の機器 (198.51.100.7) につながり、攻撃者が中身を読みながら本物のサーバーへ中継します。対策は証明書による相手認証(攻撃者は www.example.com の正しい証明書と秘密鍵を持っていないので、ブラウザの検証で警告が出ます)
- **レインボーテーブル** (rainbow table): ハッシュ値の逆引き表。対策は**ソルト**（ユーザーごとのランダム値の付加）
- **誕生日攻撃** (birthday attack): 「同じ誕生日のペアは意外と見つかる」という確率論を使い、ハッシュの**衝突**を探す。365通りの誕生日でも、23人集まれば同じ誕生日の2人がいる確率は50%を超えます。同じように、出力が n ビットのハッシュでは、約 2^(n/2) 個の入力を試せば衝突が見つかる見込みが高くなります(128ビットの MD5 なら約 2^64、SHA-256 なら約 2^128)。対策は十分長いハッシュ出力
- **ダウングレード攻撃** (downgrade): 古く弱いプロトコルバージョンに合意させる。例えば両者とも TLS 1.3 に対応しているのに、間に入った攻撃者が「TLS 1.0 しか使えない」と見せかけて弱い方式で通信させます。対策は弱い方式の無効化

### 実装を狙うサイドチャネル攻撃

**サイドチャネル攻撃** (side-channel attack) は、アルゴリズムの数学ではなく**実装の物理的な副産物**（消費電力・処理時間・電磁波・音・キャッシュの挙動）を観測して鍵を推定します。暗号装置に意図的にエラーを起こさせて内部情報を引き出す**フォールト注入** (fault injection) も実装への攻撃です。対策は処理時間を一定にする実装、電磁シールド、耐タンパー性ハードウェア（HSM）などです。

CISSP では「アルゴリズムが破られた」事例よりも「運用・実装の穴を突かれた」事例が問われます。攻撃名と対策のペアをしっかり結びつけておきましょう。

### 確認問題

**問1.** 攻撃者が、盗聴で入手した「平文とそれに対応する暗号文のペア」を手がかりに鍵を推定しようとしています。この攻撃の分類はどれですか。

1. 既知平文攻撃 (known-plaintext attack)
2. 暗号文単独攻撃 (ciphertext-only attack)
3. 選択暗号文攻撃 (chosen-ciphertext attack)
4. 誕生日攻撃 (birthday attack)

<details><summary>答えと解説</summary>

正解: **1**

平文と暗号文のペアを「入手して」解析するのは既知平文攻撃です。暗号文単独攻撃は暗号文しか持っていない場合、選択暗号文攻撃は攻撃者が自分で選んだ暗号文を復号「させられる」場合で、動詞が「入手した」か「選んで処理させた」かが分類の分かれ目です。誕生日攻撃はハッシュの衝突を探す攻撃で、鍵の推定とは目的が異なります。

</details>

**問2.** スマートカードの暗号処理中の消費電力の変化を精密に測定し、内部の秘密鍵を推定する攻撃はどれに分類されますか。

1. 総当たり攻撃
2. 選択平文攻撃
3. サイドチャネル攻撃
4. ダウングレード攻撃

<details><summary>答えと解説</summary>

正解: **3**

消費電力・処理時間・電磁波・音といった実装の物理的な副産物から秘密情報を推定するのがサイドチャネル攻撃です。アルゴリズムの数学的弱点ではなく「実装」を狙う点が特徴で、対策は処理時間を一定にする実装や耐タンパー性ハードウェアです。総当たりは全鍵の試行、選択平文は選んだ平文を暗号化させる攻撃、ダウングレードは弱いプロトコルに合意させる攻撃で、いずれも物理観測は使いません。

</details>

**問3.** パスワードのハッシュ値がレインボーテーブルで逆引きされるのを防ぐ対策として最も効果的 (BEST) なものはどれですか。

1. パスワードの定期変更を義務付ける
2. ユーザーごとに異なるソルトを付加してハッシュ化する
3. ハッシュ値を Base64 でエンコードして保存する
4. パスワードの最小文字数を 6 文字にする

<details><summary>答えと解説</summary>

正解: **2**

レインボーテーブルは「よくあるパスワード→ハッシュ値」の事前計算表です。ユーザーごとに異なるソルト（ランダム値）を付けてからハッシュ化すると、同じパスワードでも異なるハッシュになり、事前計算表が無力化されます。定期変更は漏えい後の被害期間を縮めるだけで逆引き自体は防げません。Base64 は暗号化ではなく単なる表現形式の変換、6 文字の最小長はむしろ弱い基準です。

</details>

**問4.** 誕生日攻撃 (birthday attack) が狙うのは、暗号技術のどの性質の弱点ですか。

1. 共通鍵暗号の鍵長の短さ
2. 公開鍵暗号の素因数分解の容易さ
3. 乱数生成器の周期性
4. ハッシュ関数の衝突耐性

<details><summary>答えと解説</summary>

正解: **4**

誕生日攻撃は「23 人いれば同じ誕生日のペアがいる確率が 50% を超える」という誕生日のパラドックスを応用し、同じハッシュ値になる別の入力（衝突）を総当たりより遥かに少ない試行で見つける攻撃です。衝突が作れると、正規の文書と同じハッシュを持つ偽文書でデジタル署名を悪用できます。対策は十分に長い出力を持つハッシュ関数（SHA-256 以上）の採用です。鍵長・素因数分解・乱数の周期はそれぞれ別の攻撃の話です。

</details>

**問5.** 無線で解錠する社用車のスマートキーの信号を攻撃者が記録し、後で同じ信号を再送して解錠されてしまいました。この攻撃への対策として最も適切 (BEST) なものはどれですか。

1. 信号の暗号化に使う鍵長を2倍にする
2. 信号の送信出力を下げる
3. ノンス（使い捨ての乱数）やカウンタを使い、同じ信号を2度と有効にしない
4. 信号の周波数を非公開にする

<details><summary>答えと解説</summary>

正解: **3**

これはリプレイ攻撃で、正規の信号を「そのまま再送」する攻撃です。信号自体は正規のものなので、鍵長を増やしても暗号を解かずに再送するだけの攻撃には無力です。対策は、ノンス・カウンタ・タイムスタンプなどで信号に一回性を持たせ、同じ信号の再利用を拒否することです。出力低減は盗聴をやや難しくするだけ、周波数の秘匿は「隠蔽によるセキュリティ (security through obscurity)」で、どちらも根本対策になりません。

</details>

## 4. 暗号の応用と新潮流 — TLS・ブロックチェーン・ポスト量子暗号

### TLS — ハイブリッド暗号の代表例

Web を守る **TLS** は、公開鍵暗号と共通鍵暗号のいいとこ取り（ハイブリッド暗号）です。TLS 1.3 のハンドシェイクの流れはおおまかに次のとおりです。

1. クライアントが対応方式の候補と鍵交換用の情報を送る (ClientHello)
2. サーバーが方式を決め、**証明書**と鍵交換情報を返す (ServerHello)
3. 双方が（一時的な）**Diffie-Hellman 鍵交換**でセッション鍵を合意する
4. 以降の通信は高速な**共通鍵暗号** (AES-GCM など) で暗号化する

ブラウザ (192.0.2.10:51514) が https://www.example.com (203.0.113.5:443) に接続する場合を、メッセージごとに追います。

| 順 | 向き | メッセージ | 主な中身 | 何のため |
|---|---|---|---|---|
| 1 | ブラウザ→サーバー | ClientHello | 対応バージョン TLS 1.3、暗号スイート候補 `TLS_AES_128_GCM_SHA256` など、DH の公開値 | 方式の候補と鍵交換の材料を送る |
| 2 | サーバー→ブラウザ | ServerHello | 選んだ `TLS_AES_128_GCM_SHA256`、サーバー側の DH の公開値 | ここで双方が同じ共有値を計算でき、以降は暗号化される |
| 3 | サーバー→ブラウザ | Certificate | サーバー証明書+中間 CA 証明書 | ch01 の証明書チェーン検証に使う |
| 4 | サーバー→ブラウザ | CertificateVerify | ここまでのやり取りに対する、**サーバーの秘密鍵**による署名 | 証明書の秘密鍵を持つ本物のサーバーだと証明する(中間者攻撃対策) |
| 5 | 両方向 | Finished | ここまでのやり取り全体から作った検証値 | 途中で書き換えがないことを確認 |
| 6 | 両方向 | アプリケーションデータ | HTTP のリクエストとレスポンス | 合意したセッション鍵で AES-128-GCM により暗号化 |

暗号スイート名 `TLS_AES_128_GCM_SHA256` は「データの暗号化は AES 128ビット鍵の GCM モード、鍵の導出などに SHA-256 を使う」という組み合わせを表します。L11 ch03 では「セッション鍵をサーバーの公開鍵で暗号化して送る」方式を見ましたが、これは TLS 1.2 以前の RSA 鍵交換の形です。TLS 1.3 では証明書の鍵は**署名(本人確認)だけ**に使い、セッション鍵は DH で合意します。

TLS 1.3 では毎回使い捨ての鍵で交換する ephemeral(エフェメラル=一時的な)方式が必須になり、サーバーの長期秘密鍵(証明書に対応する、何か月も使い続ける秘密鍵)が将来漏えいしても過去の通信は解読されない**前方秘匿性** (forward secrecy) が標準になりました。

例えば 2026-11 の通信を攻撃者がすべて録画しておき、2028 年にサーバーの秘密鍵を盗んだとします。RSA 鍵交換なら、録画から「秘密鍵で暗号化されたセッション鍵」を取り出して復号でき、2026 年の通信が読めてしまいます。ephemeral DH なら、セッション鍵の材料は接続のたびに作って捨てた一時的な秘密の数なので、2028 年に秘密鍵を盗んでも過去のセッション鍵は計算できません。古い SSL や TLS 1.0/1.1 は無効化すべき、も頻出ポイントです。

### メールと信頼モデル

- **S/MIME**: X.509 証明書（= CA への信頼）を使うメールの暗号化・署名の標準
- **PGP**: CA を使わず、利用者同士が互いの鍵に署名し合う **Web of Trust**（信頼の網）モデル

### 新潮流のキーワード

| 技術 | 要点 |
|---|---|
| **ブロックチェーン** | 取引をハッシュで連鎖させた分散台帳。各ブロックが1つ前のブロックのハッシュ値を含むため、過去のブロックを1文字変えるとそのハッシュ値が変わり、次のブロックに記録された値と食い違って改ざんがばれる。ただし「台帳に書かれた内容が真実か」までは保証しない |
| **準同型暗号** (homomorphic encryption) | **暗号化したまま計算**できる。クラウドに復号させずにデータ分析を委託でき、使用中データ (data in use) の保護に有効 |
| **ポスト量子暗号** (PQC) | 量子コンピュータは **RSA・DH・ECC など公開鍵暗号**を破る（ショアのアルゴリズム）。NIST は 2024 年に最初の耐量子アルゴリズムの標準 (FIPS 203 の ML-KEM=鍵交換用、FIPS 204 の ML-DSA・FIPS 205 の SLH-DSA=署名用) を公開しており、移行計画が必要。共通鍵暗号 (AES) は鍵長を増やせば当面耐える |
| **ステガノグラフィ** (steganography) | 画像や音声の中にデータを隠し、**通信の存在自体を隠蔽**する。暗号化（内容の秘匿）との違いが頻出。電子透かし (watermarking) は著作権保護への応用 |

💡 コツ: 「暗号化 = 内容を隠す」「ステガノグラフィ = 存在を隠す」「ハッシュ = 改ざんを検知する」。何を守る技術なのかで整理すると選択肢を切り分けられます。

### 確認問題

**問1.** TLS 1.3 が ephemeral（使い捨て）な Diffie-Hellman 鍵交換を必須とした主な理由はどれですか。

1. サーバーの長期秘密鍵が漏えいしても過去の通信が解読されない前方秘匿性を確保するため
2. ハンドシェイクの通信量を削減するため
3. 証明書の発行コストを削減するため
4. 共通鍵暗号を使わずに済ませるため

<details><summary>答えと解説</summary>

正解: **1**

セッションごとに使い捨ての鍵で鍵交換を行うと、将来サーバーの長期秘密鍵が漏えいしても、記録されていた過去の暗号文を復号できません。これが前方秘匿性 (forward secrecy) で、TLS 1.3 で必須になりました。通信量削減は目的ではなく（TLS 1.3 の往復数削減は別の改善）、証明書は引き続き必要で、セッション確立後のデータ暗号化には高速な共通鍵暗号を使い続けます。

</details>

**問2.** PGP の信頼モデルが S/MIME と根本的に異なる点はどれですか。

1. PGP はメール本文を暗号化できない
2. PGP は CA を使わず、利用者同士が署名し合う Web of Trust で公開鍵を信頼する
3. PGP は共通鍵暗号を使用しない
4. PGP はデジタル署名をサポートしない

<details><summary>答えと解説</summary>

正解: **2**

S/MIME は CA が発行する X.509 証明書という階層型の信頼（PKI）に依拠しますが、PGP は中央機関を置かず、利用者が互いの公開鍵の正しさに署名し合う分散型の Web of Trust（信頼の網）を採用しています。PGP も本文の暗号化・デジタル署名・ハイブリッド方式（共通鍵+公開鍵）をすべてサポートするので、他の選択肢はいずれも事実に反します。

**問3.** 医療データの分析をクラウド事業者に委託したいが、事業者にはデータの中身を一切見せたくありません。「暗号化したまま計算処理を行える」ことを特徴とする、最も適切 (BEST) な技術はどれですか。

1. 準同型暗号 (homomorphic encryption)
2. ステガノグラフィ
3. ブロックチェーン
4. OCSP ステープリング

<details><summary>答えと解説</summary>

正解: **1**

準同型暗号は暗号文のまま加算や乗算などの計算ができ、結果を復号すると平文で計算した場合と一致します。クラウドに復号鍵を渡さずに分析を委託できるため、使用中データ (data in use) の保護の代表例として出題されます。ステガノグラフィはデータの存在を隠す技術、ブロックチェーンは改ざん困難な分散台帳、OCSP ステープリングは証明書失効確認の仕組みで、いずれも「暗号化したまま計算」はできません。

</details>

**問4.** 実用的な量子コンピュータが登場した場合、最も深刻な影響を受けると考えられている暗号技術はどれですか。

1. AES-256 などの共通鍵暗号
2. SHA-3 などのハッシュ関数
3. RSA や楕円曲線暗号 (ECC) などの公開鍵暗号
4. ワンタイムパッド

<details><summary>答えと解説</summary>

正解: **3**

ショアのアルゴリズムを使う量子コンピュータは、素因数分解や離散対数問題を効率的に解けるため、それらの困難性に依拠する RSA・Diffie-Hellman・ECC といった公開鍵暗号が根本から破られます。これに備えるのがポスト量子暗号 (PQC) で、NIST が標準化を進めています。共通鍵暗号とハッシュはグローバーのアルゴリズムで強度が落ちるものの、鍵長・出力長を増やせば当面対応可能です。ワンタイムパッドは正しく運用すれば情報理論的に安全で、量子計算でも破れません。

</details>

**問5.** 退職予定の従業員が、機密設計図を風景写真の画像データの中に埋め込み、私用メールで社外へ送信していました。使われた技術はどれですか。

1. デジタル署名
2. トークン化
3. 準同型暗号
4. ステガノグラフィ

<details><summary>答えと解説</summary>

正解: **4**

画像・音声などの無害に見えるファイルにデータを埋め込み、秘密の通信が存在すること自体を隠すのがステガノグラフィです。暗号化は「内容」を隠しますが通信の存在は見えるのに対し、ステガノグラフィは「存在」を隠すため DLP でも検知が難しく、情報持ち出しの手口として出題されます。デジタル署名は完全性と否認防止、トークン化は機微データの置き換え、準同型暗号は暗号化したままの計算で、いずれも「隠して持ち出す」技術ではありません。

</details>
