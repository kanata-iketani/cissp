# 第11章 暗号技術①（共通鍵・公開鍵・ハッシュ）【D3】

暗号はドメイン3の最重要テーマで、CAT本試験でも必ず複数問が出ます。この章では暗号の目的とケルクホフスの原理から始め、共通鍵・公開鍵・ハッシュという3本柱を「どの性質(機密性・完全性・真正性・否認防止)を満たすか」という試験特有の切り口で整理します。鍵の本数計算や「どちらの鍵で暗号化するか」は超頻出なので、手を動かして確実に身につけましょう。

## 1. 暗号の基礎概念

### 暗号は「何を守るか」で問われる

CISSPでは暗号のアルゴリズムの数学より、**その技術がどのセキュリティ目標を満たすか**が問われます。暗号が提供できるのは次の4つです。

| 目標 | 意味 | 実現する代表技術 |
|---|---|---|
| 機密性 (confidentiality) | 盗み見られても読めない | 暗号化 |
| 完全性 (integrity) | 改ざんを検知できる | ハッシュ・MAC |
| 真正性 (authenticity) | 相手が本物だと確認できる | MAC・デジタル署名 |
| 否認防止 (nonrepudiation) | 「送っていない」と言い逃れできない | デジタル署名のみ |

**可用性は暗号では提供できません**。むしろ鍵を失うとデータが読めなくなるため、可用性とはトレードオフです。

### ケルクホフスの原理 (Kerckhoffs's principle)

「**暗号システムは、鍵以外のすべてが公開されても安全でなければならない**」という原則です。アルゴリズムを秘密にして安全を保とうとする「隠蔽によるセキュリティ (security through obscurity)」は、CISSPでは常に不正解側の考え方です。

### 基本のしくみ

- **コード (code) と暗号 (cipher) の違い**: コードは単語や文全体を別の記号に置き換える体系(必ずしも秘匿目的ではない)、暗号はビットや文字の単位で変換する数学的手法です
- **換字式 (substitution)**: 文字を別の文字に置き換える(シーザー暗号など)
- **転置式 (transposition)**: 文字の順番を並べ替える
- **XOR**: 同じビットなら 0、違うビットなら 1。同じ鍵で2回XORすると元に戻る性質が、ストリーム暗号の心臓部です

### ワンタイムパッド (one-time pad)

**理論的に解読不可能と証明されている唯一の暗号**です。ただし条件が4つあり、1つでも破ると安全ではなくなります。①鍵が完全にランダム ②鍵は平文と同じ長さ以上 ③鍵は一度しか使わない ④鍵を安全に配送・保管する — 実運用がほぼ不可能な点も含めて頻出です。

### 鍵にまつわる概念

- **鍵空間 (key space)**: 鍵のとりうる総数。鍵長 n ビットなら 2^n 通り
- **ワークファクター (work factor)**: 解読に要する時間とコストの見積もり。これが資産価値を上回れば実用上安全です
- **ゼロ知識証明 (zero-knowledge proof)**: 秘密そのものを見せずに「知っている」ことだけを証明する手法
- **分割知識 (split knowledge)**: 鍵の管理権限を複数人に分割し、1人では操作できなくするしくみ。職務分掌の暗号版です

💡 コツ: 「否認防止はデジタル署名だけ」「可用性は暗号の目標ではない」「隠蔽によるセキュリティは×」の3点は即答できるようにしましょう。

### 確認問題

**問1.** ケルクホフスの原理 (Kerckhoffs's principle) の説明として最も適切なものはどれでしょう？

1. 暗号アルゴリズムは秘密にすることで安全性が高まる
2. 鍵は平文と同じ長さ以上でなければならない
3. 暗号システムは鍵以外のすべてが公開されても安全でなければならない
4. 暗号強度は鍵空間の大きさだけで決まる

<details><summary>答えと解説</summary>

正解: **3**

ケルクホフスの原理は「秘密にすべきは鍵だけ」という考え方で、アルゴリズム公開を前提に設計された AES などの現代暗号の土台です。「暗号アルゴリズムは秘密にすることで安全性が高まる」はまさに逆の「隠蔽によるセキュリティ (security through obscurity)」で、CISSPでは不適切な考え方の代表です。「鍵は平文と同じ長さ以上でなければならない」はワンタイムパッドの条件、「暗号強度は鍵空間の大きさだけで決まる」は鍵空間以外にアルゴリズムの強度や実装も影響するため誤りです。試験では「アルゴリズムを独自開発して秘密にする」という選択肢が出たら、ほぼ確実に誤答側だと覚えておきましょう。

</details>

**問2.** ワンタイムパッド (one-time pad) が理論的に解読不可能であるために必要な条件として、正しい組み合わせはどれでしょう？

1. 鍵が完全にランダムで、平文と同じ長さ以上あり、一度しか使わず、安全に保管される
2. 鍵が擬似乱数で生成され、256ビット以上あり、定期的に交換され、安全に保管される
3. 鍵が完全にランダムで、128ビット以上あり、通信ごとにハッシュ化される
4. 鍵が送信者と受信者で別々に生成され、XORで合成される

<details><summary>答えと解説</summary>

正解: **1**

ワンタイムパッドの4条件は「完全ランダム・平文以上の長さ・使い回し禁止・安全な配送と保管」です。どれか1つでも欠けると理論的な安全性は崩れます。「256ビット以上」「128ビット以上」のように鍵長が固定ビット数で足りるとしている選択肢は誤りで、ワンタイムパッドは平文と同じ長さ以上の鍵が必要です。擬似乱数も「完全にランダム」の条件を満たしません。「鍵が送信者と受信者で別々に生成され、…」はそのような方式ではありません。ひっかけとして「実用的で広く使われている」という記述が出たら誤りです。運用コストが高すぎて一般には使われません。

</details>

**問3.** 暗号技術が単独では提供できないセキュリティ目標はどれでしょう？

1. 機密性 (confidentiality)
2. 完全性 (integrity)
3. 否認防止 (nonrepudiation)
4. 可用性 (availability)

<details><summary>答えと解説</summary>

正解: **4**

可用性は暗号の目標ではなく、冗長化やバックアップで実現します。むしろ暗号化は「鍵を失うとデータにアクセスできなくなる」という形で可用性のリスクにもなります(ランサムウェアはこれを悪用した攻撃です)。機密性は暗号化、完全性はハッシュやMAC、否認防止はデジタル署名でそれぞれ提供できます。試験で「暗号化を導入すれば可用性も向上する」という選択肢が出たら誤りです。

</details>

**問4.** あなたは CISO として、ルート CA の秘密鍵の復旧操作を 1 人の管理者が単独で実行できないようにしたいと考えています。この要件を満たす最も適切な (BEST) 手法はどれでしょう？

1. 鍵をHSMに保管し、管理者全員に同じPINを配布する
2. 鍵の構成要素を複数人に分割して保持させる分割知識 (split knowledge) を導入する
3. 鍵をより長いビット長で再生成する
4. 管理者の操作をすべてログに記録して毎月レビューする

<details><summary>答えと解説</summary>

正解: **2**

分割知識は鍵の管理権限を複数人に分け、全員(または定足数)が揃わないと操作できなくするしくみで、「単独で実行できない」という要件を直接満たします。デュアルコントロールと合わせて問われる頻出論点です。「鍵をHSMに保管し、管理者全員に同じPINを配布する」はHSM自体は良い対策ですが、全員が同じPINを持つなら単独操作を防げません。「鍵をより長いビット長で再生成する」の鍵長は解読耐性の話で、内部者の単独操作とは無関係です。「管理者の操作をすべてログに記録して毎月レビューする」のログは発見的統制であり、操作そのものを防ぐ予防的統制にはなりません。「防ぎたい」のか「検知したい」のかを問題文から読み取るのがコツです。

</details>

**問5.** 2進数 1010 と鍵 0110 を XOR 演算した結果はどれでしょう？

1. 0100
2. 1110
3. 1100
4. 0010

<details><summary>答えと解説</summary>

正解: **3**

XORは「ビットが異なれば1、同じなら0」です。桁ごとに見ると 1⊕0=1、0⊕1=1、1⊕1=0、0⊕0=0 となり、答えは 1100 です。なお、この結果 1100 にもう一度同じ鍵 0110 をXORすると元の 1010 に戻ります。この「同じ鍵で2回XORすると復元できる」性質がストリーム暗号の基本原理で、だからこそ鍵ストリームの使い回しが致命的な弱点になる、という流れで試験に出ます。

</details>

## 2. 共通鍵暗号

### 共通鍵暗号 (symmetric cryptography) の特徴

暗号化と復号に**同じ鍵**を使う方式です。特徴は3点セットで覚えます。

| 観点 | 共通鍵暗号 |
|---|---|
| 速度 | **高速**(大量データ向き) |
| 鍵配送 | 事前に安全な経路で共有が必要(**鍵配送問題**) |
| 必要な鍵数 | n 人の相互通信で **n(n-1)/2** 本 |

鍵数の計算は超頻出です。例えば10人なら 10×9÷2 = **45本**。人数が増えると鍵管理が破綻する、という文脈で公開鍵暗号の必要性につながります。また、共通鍵暗号は**否認防止を提供できません**(鍵を2人が持つため、どちらが作成したか証明できない)。

### 代表的なアルゴリズム

| アルゴリズム | 鍵長 | 現在の評価 |
|---|---|---|
| DES | 56ビット | 短すぎて**脆弱**(総当たりで解読可能) |
| 3DES | 112/168ビット | 非推奨・廃止の流れ(遅い) |
| **AES** | **128/192/256ビット** | **現行標準**(Rijndael が採用) |
| RC4 | 可変 | ストリーム暗号。WEP等で使われ**脆弱** |

### ブロック暗号とストリーム暗号

- **ブロック暗号**: データを固定長(AESは128ビット)のブロックに区切って暗号化
- **ストリーム暗号**: 1ビット/1バイトずつ鍵ストリームとXORして暗号化(高速・リアルタイム通信向き)

### ブロック暗号のモード(頻出)

| モード | 特徴 | 注意点 |
|---|---|---|
| ECB | ブロックごとに独立に暗号化 | **同じ平文→同じ暗号文**になりパターンが漏れる。**使用禁止が原則** |
| CBC | 前の暗号文とチェーンして暗号化 | IV(初期化ベクトル)が必要。並列化できない |
| CTR | カウンタ値を暗号化してXOR | 並列処理が可能で高速 |
| **GCM** | CTR + 認証タグ | **認証付き暗号 (AEAD)**。機密性と完全性を同時に提供し、TLS 1.3 の主流 |

💡 コツ: 「ECBはなぜダメか(ペンギンの画像が透ける話が有名)」「GCMだけが完全性も守る」が問われどころです。鍵数の計算は 共通鍵 n(n-1)/2、公開鍵 2n とセットで暗記しましょう。

### 確認問題

**問1.** 10人のメンバー全員が共通鍵暗号で相互に秘密通信を行う場合、必要な鍵の総数はいくつでしょう？

1. 20本
2. 45本
3. 90本
4. 100本

<details><summary>答えと解説</summary>

正解: **2**

共通鍵暗号ではペアごとに1本の鍵が必要なので、n(n-1)/2 = 10×9÷2 = 45本です。90本は「÷2」を忘れた値、20本は公開鍵暗号の場合の 2n(各自が公開鍵と秘密鍵の2本)、100本は n² でいずれも誤りです。この計算は CISSP の定番で、「人数が増えると鍵管理が爆発する → 公開鍵暗号やKDCが必要になる」という文脈ごと理解しておくと応用問題にも対応できます。

</details>

**問2.** ブロック暗号の ECB モードの最大の問題点はどれでしょう？

1. 暗号化の処理速度が他のモードより極端に遅い
2. 初期化ベクトル (IV) の管理が複雑になる
3. 復号時に全ブロックを順番に処理する必要がある
4. 同じ平文ブロックが常に同じ暗号文ブロックになり、データのパターンが漏れる

<details><summary>答えと解説</summary>

正解: **4**

ECB (Electronic Codebook) はブロックごとに独立して同じ鍵で暗号化するため、同じ平文ブロックは必ず同じ暗号文になります。その結果、画像などを暗号化しても輪郭やパターンが透けて見えてしまいます。速度はむしろ並列化できて速い部類なので「暗号化の処理速度が他のモードより極端に遅い」は誤り、ECBはIVを使わないので「初期化ベクトル (IV) の管理が複雑になる」も誤り、ブロックが独立しているため順番に処理する必要もなく「復号時に全ブロックを順番に処理する必要がある」も誤りです。「ECBは原則使用禁止、CBCやGCMを使う」が実務上もCISSP上も正解の方向です。

</details>

**問3.** AES (Advanced Encryption Standard) の説明として正しいものはどれでしょう？

1. Rijndael アルゴリズムが採用され、鍵長は 128/192/256 ビットから選べる
2. DES を3回繰り返すことで強度を高めた方式である
3. ストリーム暗号であり、1ビットずつ暗号化する
4. 公開鍵暗号の一種で、鍵配送問題を解決する

<details><summary>答えと解説</summary>

正解: **1**

AES は NIST のコンペで Rijndael が選ばれた現行の共通鍵ブロック暗号標準で、ブロック長128ビット、鍵長は128/192/256ビットです。「DES を3回繰り返すことで強度を高めた方式である」は 3DES の説明、「ストリーム暗号であり、1ビットずつ暗号化する」は誤りで AES はブロック暗号、「公開鍵暗号の一種で、鍵配送問題を解決する」も誤りで AES は共通鍵暗号なので鍵配送問題はそのまま残ります(だから公開鍵暗号と組み合わせるハイブリッド構成にします)。「AES=共通鍵・ブロック・現行標準」の3点が揃っているかを選択肢で確認しましょう。

</details>

**問4.** あなたのチームは大容量データを高速に暗号化しつつ、改ざんの検知も同時に行いたいと考えています。最も適切な (BEST) 選択はどれでしょう？

1. AES-ECB で暗号化し、ファイルサイズを記録する
2. AES-CBC で暗号化する
3. AES-GCM で暗号化する
4. RSA でデータ全体を暗号化する

<details><summary>答えと解説</summary>

正解: **3**

GCM は認証付き暗号 (AEAD) で、暗号化(機密性)と認証タグによる完全性・真正性の検証を同時に提供します。「暗号化と改ざん検知を両方」とくれば GCM が BEST です。ECB はパターン漏えいの問題があり論外、CBC は機密性のみで改ざん検知は別途 MAC が必要、RSA は公開鍵暗号で低速なため大容量データの直接暗号化には不向きです。ファイルサイズの記録は改ざん検知になりません(サイズを変えない改ざんが可能)。

</details>

**問5.** レガシーシステムで 3DES が使われていることが判明しました。セキュリティ管理者として最も適切な (MOST appropriate) 対応はどれでしょう？

1. 3DES は DES の3倍安全なので継続使用する
2. AES への移行計画を立案し、リスク評価のうえ段階的に移行する
3. 鍵長を2倍にして 3DES を使い続ける
4. ただちにシステムを停止する

<details><summary>答えと解説</summary>

正解: **2**

3DES は非推奨(deprecated)であり、現行標準の AES へ移行するのが正解です。ただし CISSP 的には「ただちに停止」ではなく、リスク評価を行い業務影響を考慮した計画的な移行が BEST です(可用性も守るのがマネジメント視点)。「3DES は DES の3倍安全なので継続使用する」は誤りで、3DES は遅いうえに将来性がなく「3倍安全」という理解も不正確です。「鍵長を2倍にして 3DES を使い続ける」の鍵長変更は 3DES の仕様上の選択肢として本質的な解決になりません。「ただちにシステムを停止する」は事業継続を無視した過剰反応で、CISSPでは「業務を止める」が正解になるのは人命や法令違反など限定的な場面だけです。

</details>

## 3. 公開鍵暗号とハイブリッド暗号

### 公開鍵暗号 (asymmetric cryptography) の特徴

数学的に対になった**公開鍵 (public key)** と**秘密鍵 (private key)** を使う方式です。公開鍵は誰に知られてもよく、秘密鍵は本人だけが持ちます。

| 観点 | 共通鍵暗号 | 公開鍵暗号 |
|---|---|---|
| 速度 | 高速 | **低速**(約1000倍遅い) |
| 鍵配送 | 問題あり | **不要**(公開鍵は配ってよい) |
| 鍵数(n人) | n(n-1)/2 | **2n** |
| 否認防止 | 不可 | **可能**(署名) |

### どちらの鍵を使うか(超頻出)

**目的によって使う鍵が逆になる**のが最大のポイントです。

| 目的 | 使う鍵 | 復号・検証する鍵 |
|---|---|---|
| 機密性(暗号化) | **受信者の公開鍵**で暗号化 | 受信者の秘密鍵で復号 |
| 署名(真正性・否認防止) | **送信者の秘密鍵**で署名 | 送信者の公開鍵で検証 |

「アリスがボブに秘密のメッセージを送る → ボブの公開鍵で暗号化」「アリスが自分が書いたと証明する → アリスの秘密鍵で署名」。主語と目的を取り違えさせる問題が繰り返し出ます。

### 代表的なアルゴリズム

- **RSA**: 大きな数の**素因数分解**の困難さが安全性の根拠。暗号化も署名も可能な万能選手
- **Diffie-Hellman (DH)**: **鍵合意 (key agreement)** 専用。安全でない経路上で共通鍵(セッション鍵)を合意できる。根拠は**離散対数問題**。認証機能がないため中間者攻撃に注意
- **ECC (楕円曲線暗号)**: 楕円曲線上の離散対数問題が根拠。**RSA より大幅に短い鍵長で同等の強度**(例: ECC 256ビット ≒ RSA 3072ビット)。計算資源の限られる**モバイル・IoT に最適**
- **ElGamal**: DH を拡張した方式。暗号文が平文の2倍になる欠点

### ハイブリッド暗号 — 両者のいいとこ取り

実際の通信(TLS など)では、**公開鍵暗号でセッション鍵(共通鍵)を安全に共有し、以降の大量データは高速な共通鍵暗号で保護**します。これがハイブリッド暗号で、「公開鍵の鍵配送の安全さ」と「共通鍵の速度」を両立します。

💡 コツ: 「暗号化は相手(受信者)の公開鍵、署名は自分(送信者)の秘密鍵」と唱えて覚えましょう。DH は「暗号化アルゴリズムではなく鍵合意」という点もひっかけの定番です。

### 確認問題

**問1.** アリスがボブに機密性を確保してメッセージを送りたい場合、メッセージの暗号化に使う鍵はどれでしょう？

1. アリスの秘密鍵
2. アリスの公開鍵
3. ボブの公開鍵
4. ボブの秘密鍵

<details><summary>答えと解説</summary>

正解: **3**

機密性が目的なら「受信者の公開鍵」で暗号化します。こうすれば対になるボブの秘密鍵を持つボブだけが復号でき、途中で盗聴されても読まれません。アリスの秘密鍵で暗号化するのはデジタル署名(真正性・否認防止)の場合で、誰でもアリスの公開鍵で復号できてしまうため機密性には使えません。アリスの公開鍵で暗号化するとアリス自身しか復号できず意味がなく、ボブの秘密鍵はボブ以外使えません。「目的が機密性か署名か」をまず見極めるのが鉄則です。

</details>

**問2.** デジタル署名を作成するとき、送信者が使用する鍵はどれでしょう？

1. 送信者の秘密鍵
2. 送信者の公開鍵
3. 受信者の公開鍵
4. 受信者の秘密鍵

<details><summary>答えと解説</summary>

正解: **1**

署名は「本人しか持っていない鍵で作る」からこそ本人証明になります。つまり送信者の秘密鍵で署名し、受け取った側は送信者の公開鍵で検証します。秘密鍵は本人だけが持つため、署名が検証できれば「本人が作成した」ことの証明(真正性)となり、後から「送っていない」と言えなくなります(否認防止)。受信者の公開鍵を使うのは機密性のための暗号化であり、署名とは目的も使う鍵も逆です。暗号化と署名で鍵の使い方が逆になる点が最大のひっかけポイントです。

</details>

**問3.** Diffie-Hellman アルゴリズムの主な用途として最も適切なものはどれでしょう？

1. 大量データの高速な暗号化
2. メッセージのハッシュ値の計算
3. デジタル証明書の発行
4. 安全でない通信路上でのセッション鍵の合意

<details><summary>答えと解説</summary>

正解: **4**

Diffie-Hellman は暗号化アルゴリズムではなく「鍵合意 (key agreement)」のプロトコルです。盗聴されている経路上でも、双方が交換した情報から同じ共通鍵を導出でき、盗聴者には計算できない(離散対数問題の困難さ)という仕組みです。「大量データの高速な暗号化」はAESなど共通鍵暗号の役割、「メッセージのハッシュ値の計算」はSHAなどハッシュ関数、「デジタル証明書の発行」は認証局(CA)の役割です。ひっかけとして「DHでデータを暗号化する」という選択肢がよく出ますが、DH自体はデータを暗号化しません。また認証機能がないため中間者攻撃に弱い点も覚えておきましょう。

</details>

**問4.** 処理能力とバッテリーが限られる IoT デバイスに公開鍵暗号を実装します。最も適切な (BEST) アルゴリズムはどれでしょう？

1. RSA 4096ビット
2. ECC (楕円曲線暗号)
3. 3DES
4. SHA-256

<details><summary>答えと解説</summary>

正解: **2**

ECC は RSA よりはるかに短い鍵長で同等の強度を実現できる(例: ECC 256ビット ≒ RSA 3072ビット)ため、計算量・メモリ・消費電力を抑えられ、IoT やモバイルに最適です。RSA 4096ビットは強度は十分でも計算負荷が大きく、制約のあるデバイスには不向きです。3DES は共通鍵暗号であり「公開鍵暗号を実装する」という要件に合わず、しかも非推奨です。SHA-256 はハッシュ関数で暗号化はできません。「リソース制約 → ECC」は条件反射で選べるようにしましょう。

</details>

**問5.** TLS などで使われるハイブリッド暗号方式において、公開鍵暗号が果たす役割はどれでしょう？

1. 通信データ全体の暗号化
2. 通信データの圧縮
3. セッション鍵(共通鍵)の安全な交換・合意
4. パケットの順序制御

<details><summary>答えと解説</summary>

正解: **3**

ハイブリッド暗号では、低速だが鍵配送に強い公開鍵暗号で「セッション鍵」を安全に共有し、以降の大量データは高速な共通鍵暗号(AES-GCMなど)で暗号化します。公開鍵暗号でデータ全体を暗号化すると遅すぎるため「通信データ全体の暗号化」は誤りです(これが最も狙われるひっかけです)。圧縮や順序制御は暗号の役割ではありません。「公開鍵=鍵の配送係、共通鍵=本番の暗号化係」という分担を押さえれば、TLSの仕組みを問うシナリオ問題にも応用できます。

</details>

## 4. ハッシュ・MAC・デジタル署名

### ハッシュ関数の条件

ハッシュ関数は任意の長さの入力から固定長の**ハッシュ値(メッセージダイジェスト)**を作る関数で、次の条件を満たす必要があります。

1. どんな長さの入力も受け付ける
2. 出力は**固定長**
3. 計算が容易である
4. **一方向性 (one-way)**: ハッシュ値から元データを復元できない
5. **衝突耐性 (collision resistance)**: 同じハッシュ値になる別の入力を見つけられない

**暗号化と違い、ハッシュは復号できません**(鍵もありません)。MD5 と SHA-1 は衝突が現実に発見されたため**非推奨**で、現在は SHA-2 (SHA-256 など) や SHA-3 を使います。

### パスワード保存の技法

- **ソルト (salt)**: パスワードごとにランダム値を付加してからハッシュ化。**レインボーテーブル攻撃**(ハッシュ値の逆引き表)を無効化します
- **ペッパー (pepper)**: 全体に共通の秘密値をDB外(HSM等)に保管して付加
- **キーストレッチング (key stretching)**: PBKDF2・bcrypt・scrypt のようにハッシュを何千回も繰り返し、総当たりを遅くする

### 提供する機能の対比(超頻出)

| 技術 | 完全性 | 真正性 | 否認防止 |
|---|---|---|---|
| ハッシュ単体 | ○ | × | × |
| **HMAC**(鍵付きハッシュ) | ○ | ○ | **×**(鍵を2人が共有するため) |
| **デジタル署名** | ○ | ○ | **○** |

### デジタル署名のしくみ

①メッセージのハッシュ値を計算 → ②そのハッシュ値を**送信者の秘密鍵**で暗号化(これが署名) → ③受信者は送信者の公開鍵で署名を復号し、自分で計算したハッシュ値と比較。一致すれば「改ざんされていない(完全性)」「本人が作成した(真正性)」「本人は否定できない(否認防止)」が揃います。**機密性は提供しない**点に注意(本文は平文のまま)。

規格には RSA 署名、DSA、ECDSA(楕円曲線版)があります。米国の**デジタル署名標準 (DSS, FIPS 186)** が規定しています。

💡 コツ: 「HMACと署名の違いは否認防止の有無」「署名は機密性を提供しない」の2点が最頻出のひっかけです。

### 確認問題

**問1.** 暗号学的ハッシュ関数の性質として誤っているものはどれでしょう？

1. 任意の長さの入力から固定長の出力を生成する
2. 正しい鍵を使えばハッシュ値から元のデータを復元できる
3. 同じハッシュ値を持つ別の入力を見つけることが困難である
4. 入力が1ビット変わると出力は大きく変化する

<details><summary>答えと解説</summary>

正解: **2**

ハッシュ関数は一方向性関数であり、そもそも鍵を使いませんし、ハッシュ値から元データを復元することはできません。「ハッシュ化=暗号化」と混同させるのが定番のひっかけで、暗号化は復号できる(可逆)、ハッシュは復元できない(不可逆)という違いを押さえましょう。「任意の長さの入力から固定長の出力を生成する」の固定長出力、「同じハッシュ値を持つ別の入力を見つけ…」の衝突耐性(第二原像計算困難性)、「入力が1ビット変わると出力は大きく変化する」の雪崩効果(avalanche effect)はいずれもハッシュ関数の正しい性質です。

</details>

**問2.** パスワードをデータベースに保存する際にソルト (salt) を使用する主な目的はどれでしょう？

1. パスワードの入力ミスを検出するため
2. ハッシュ計算を高速化するため
3. パスワードを暗号化して復元可能にするため
4. レインボーテーブル攻撃を無効化するため

<details><summary>答えと解説</summary>

正解: **4**

ソルトはユーザーごとのランダム値をパスワードに付加してからハッシュ化する技法です。同じパスワードでも異なるハッシュ値になるため、事前計算されたハッシュの逆引き表(レインボーテーブル)が役に立たなくなります。「ハッシュ計算を高速化するため」は逆で、ソルトは速度に寄与せず、むしろ総当たりを遅くしたいなら bcrypt や PBKDF2 のキーストレッチングを併用します。「パスワードを暗号化して復元可能にするため」は誤りで、ソルトを使ってもハッシュは復元不能なままです(それが狙いです)。「ソルト=レインボーテーブル対策、キーストレッチング=総当たり対策」とセットで覚えましょう。

</details>

**問3.** HMAC が提供できないセキュリティ機能はどれでしょう？

1. 否認防止 (nonrepudiation)
2. メッセージの完全性
3. 送信元の真正性
4. 改ざんの検知

<details><summary>答えと解説</summary>

正解: **1**

HMAC は送信者と受信者が共有する秘密鍵を使った鍵付きハッシュで、完全性(改ざん検知)と真正性(鍵を持つ相手が作成した)を提供します。しかし鍵を送信者と受信者の2者が共有しているため、「送信者が作った」のか「受信者が自作した」のか第三者には区別できず、否認防止は提供できません。否認防止が必要なら、本人だけが持つ秘密鍵で作るデジタル署名が必要です。「HMACとデジタル署名の違いは否認防止」は最頻出の比較ポイントです。

</details>

**問4.** デジタル署名が提供するセキュリティ機能の組み合わせとして正しいものはどれでしょう？

1. 機密性・完全性・可用性
2. 機密性・真正性・否認防止
3. 完全性・真正性・否認防止
4. 完全性・可用性・否認防止

<details><summary>答えと解説</summary>

正解: **3**

デジタル署名はハッシュ値を送信者の秘密鍵で暗号化したもので、①ハッシュの一致で完全性、②秘密鍵の所有者しか作れないことで真正性、③本人しか作れない証拠が残ることで否認防止を提供します。一方、メッセージ本文は平文のままなので機密性は提供しません。ここが最大のひっかけで、「署名したから盗聴されても安全」は誤りです。機密性も必要なら受信者の公開鍵による暗号化を併用します。可用性はそもそも暗号技術の守備範囲外です。

</details>

**問5.** Web アプリケーションのパスワード保存方式として最も適切な (BEST) ものはどれでしょう？

1. AES-256 で暗号化して保存する
2. ユーザーごとのソルトを付加し、bcrypt でハッシュ化して保存する
3. SHA-256 で1回ハッシュ化して保存する
4. MD5 でハッシュ化し、ソルトを付加して保存する

<details><summary>答えと解説</summary>

正解: **2**

パスワード保存のベストプラクティスは「ソルト+キーストレッチング(bcrypt / PBKDF2 / scrypt など)」です。ソルトでレインボーテーブルを無効化し、意図的に遅いハッシュで総当たりのコストを跳ね上げます。「AES-256 で暗号化して保存する」の暗号化は復号できてしまう(鍵が漏れれば全パスワードが平文に戻る)ため不適切で、パスワードは復元できる必要がありません。「SHA-256 で1回ハッシュ化して保存する」は高速な汎用ハッシュ1回のみでソルトもなく、GPUによる総当たりに弱すぎます。「MD5 でハッシュ化し、ソルトを付加して保存する」のMD5は衝突が発見された非推奨アルゴリズムで、ソルトを付けても使うべきではありません。

</details>
