# 第7章 資産の分類とデータライフサイクル【D2】

データを守る第一歩は「何がどれだけ大事か」を決めることです。この章では、データ分類の体系、オーナー・カストディアンなどの役割分担、そして収集から廃棄までのライフサイクル管理を学びます。D2（資産のセキュリティ）の土台であり、「誰の責任か」を問うシナリオ問題の頻出地帯です。

## 1. 情報と資産の分類

### なぜ分類するのか

すべてのデータを最高レベルで守ろうとすると、コストがいくらあっても足りません。**分類（Classification）**の目的は、データの価値や漏えい時の影響に応じて保護のレベルを変え、**保護コストを最適化する**ことです。「大事なものほど厚く守り、公開情報にはお金をかけない」——この発想が D2 の出発点です。

### 政府分類と商用分類（超頻出の対比表）

| レベル | 政府（Government） | 商用（Commercial） |
|---|---|---|
| 最高 | Top Secret（トップシークレット）: 漏えいで**極めて重大な損害** | Confidential / Proprietary（機密）: 企業秘密・ソースコードなど |
| 高 | Secret（シークレット）: 漏えいで**重大な損害** | Private（プライベート）: 個人情報・給与情報など |
| 中 | Confidential（コンフィデンシャル）: 漏えいで**損害** | Sensitive（センシティブ）: 社内限りの情報 |
| 低 | Unclassified（非機密） | Public（公開）: 漏えいしても損害なし |

💡 コツ: 「Top Secret」「Secret」が出てきたら政府分類、「Proprietary」「Public」が出てきたら商用分類です。試験ではこの2系統を混ぜた選択肢でひっかけてきます。

### 分類の基準とプロセス

分類レベルは、データの**価値（Value）**、漏えい・改ざん時の**影響（Impact）**、法規制の要求（個人情報保護法、GDPR など）を基準に決めます。そして重要なのは、**分類を決めるのはデータオーナー（経営側の責任者）**だということです。IT 部門や管理者が勝手に決めるものではありません。

時間が経てば価値は変わります。製品発表前の設計書は Confidential でも、発表後は格下げ（Declassification / Downgrade）してよいかもしれません。**定期的な見直しと再分類**も分類プロセスの一部です。

### 「資産」はデータだけではない

分類・保護の対象となる**資産（Asset）**には、データのほかにハードウェア、ソフトウェア、さらには**人（People）**も含まれます。機密データを扱うサーバーや、重要な知識を持つキーパーソンも、組織が守るべき資産です。

### 確認問題

**問1.** 組織がデータ分類制度を導入する最も重要な（PRIMARY）目的はどれでしょう？

1. すべてのデータを最高レベルの暗号化で保護するため
2. 監査人にセキュリティ意識の高さを示すため
3. データの価値と影響に応じて保護コストを最適化するため
4. データオーナーの業務負荷を減らすため

<details><summary>答えと解説</summary>

正解: **3**

分類の第一の目的は、データの価値・漏えい時の影響に応じて保護レベルに濃淡をつけ、限られたコストを有効に使うことです。「すべてを最高レベルで保護」は分類の発想と正反対で、コストが破綻します。監査対応は副次的な効果にすぎず、オーナーの負荷はむしろ分類責任が加わる分増えます。PRIMARY（第一の）を問われたら「コストと保護のバランス」を思い出しましょう。

</details>

**問2.** 商用（Commercial）のデータ分類体系で、一般に最も高い機密レベルを表すのはどれでしょう？

1. Top Secret（トップシークレット）
2. Confidential / Proprietary（機密）
3. Secret（シークレット）
4. Sensitive（センシティブ）

<details><summary>答えと解説</summary>

正解: **2**

商用分類の最高レベルは一般に Confidential（または Proprietary）で、企業秘密やソースコードなどが該当します。Top Secret と Secret は政府（Government）分類の用語であり、商用体系には登場しません——ここが定番のひっかけです。Sensitive は商用分類の中位レベルで、社内限りの情報を指します。

</details>

**問3.** 政府分類で、漏えいすると国家安全保障に「重大な損害（serious damage）」を与えると定義されるレベルはどれでしょう？

1. Confidential
2. Top Secret
3. Unclassified
4. Secret

<details><summary>答えと解説</summary>

正解: **4**

政府分類の損害の定義は、Top Secret =「極めて重大な損害（exceptionally grave damage）」、Secret =「重大な損害（serious damage）」、Confidential =「損害（damage）」と段階づけられています。「serious」は Secret、と英語の対応で覚えるのが確実です。Unclassified は非機密で損害の定義がありません。

</details>

**問4.** ある企業で新しい顧客データベースを構築します。このデータの分類レベルを決定すべきなのは誰でしょう？

1. 日々の運用を行うシステム管理者
2. データオーナー（経営側の責任者）
3. セキュリティ監査人
4. データベースの開発ベンダー

<details><summary>答えと解説</summary>

正解: **2**

分類レベルの決定は、そのデータに対する最終責任を持つデータオーナーの役割です。システム管理者（カストディアン側）は決められた分類に従って保護作業を実施する立場で、分類を決める立場ではありません。監査人は独立性が必要なため意思決定には関与せず、外部ベンダーに分類を委ねるのは責任の放棄にあたります。「決めるのはオーナー、実施するのはカストディアン」が鉄則です。

</details>

**問5.** 製品の新機能の設計書は発表前まで Confidential に分類されていました。製品が正式発表され、機能の詳細が公式サイトに掲載されたあと、この設計書の扱いとして最も適切（BEST）なのはどれでしょう？

1. オーナーの承認のもと分類を見直し、適切なレベルへ格下げ（ダウングレード）する
2. 一度 Confidential にした以上、分類は永久に変更しない
3. ただちにすべての保護を解除して全社公開する
4. 監査指摘を避けるため、より高いレベルへ格上げする

<details><summary>答えと解説</summary>

正解: **1**

データの価値は時間とともに変化するため、定期的な見直しと再分類（格下げを含む）は分類プロセスの正常な一部です。ただし変更の判断・承認はデータオーナーが行います。「永久に変更しない」は過剰保護でコストの無駄、承認なしの即時全面公開はプロセス無視、価値が下がったのに格上げするのは分類の目的（コスト最適化）に反します。

</details>

## 2. データロール（役割と責任）

### 「誰の責任か」を問う試験

CISSP の D2 で最もよく出るのが、データに関わる**役割（Data Roles）**の区別です。シナリオを読んで「この作業は誰の責任か」を即答できるようにしましょう。

| 役割 | 誰か | 責任 |
|---|---|---|
| **データオーナー（Data Owner）** | 経営側の責任者 | 分類の決定、保護方針の承認、**最終責任** |
| **データカストディアン（Data Custodian）** | IT 部門など | バックアップ、アクセス権設定など**日々の保護作業** |
| **データスチュワード（Data Steward）** | 業務部門の担当者 | データの品質・意味・業務ルールの管理 |
| **ユーザー（User）** | 利用者全員 | ポリシーに従った適切な利用 |

💡 コツ: 「決める・責任を負う」のはオーナー、「手を動かして守る」のはカストディアン。シナリオに「バックアップ」「パーミッション設定」とあればカストディアン、「分類を決定」「方針を承認」とあればオーナーです。

### GDPR 文脈の役割（コントローラーとプロセッサー）

EU の **GDPR（一般データ保護規則）**では、別の役割名が使われます。

- **データコントローラー（Data Controller）**: 個人データの**処理の目的と手段を決定する**組織。例: 顧客データを集める事業会社そのもの
- **データプロセッサー（Data Processor）**: コントローラーの指示を受けて**委託されて処理する**組織。例: 給与計算の外部委託先、SaaS 事業者
- **データサブジェクト（Data Subject）**: データの本人（顧客・従業員など）

委託してもコントローラーの責任はなくなりません。「処理を外部に委託したから当社は無関係」は試験でも実務でも通用しない考え方です。

💡 コツ: Controller は「control（支配）する側」= 目的と手段を決める側、Processor は「process（処理）するだけ」の側、と英語から覚えると混同しません。

### 確認問題

**問1.** GDPR において、個人データの「処理の目的と手段」を決定する組織を指す用語はどれでしょう？

1. データプロセッサー（Data Processor）
2. データカストディアン（Data Custodian）
3. データコントローラー（Data Controller）
4. データサブジェクト（Data Subject）

<details><summary>答えと解説</summary>

正解: **3**

処理の目的と手段を決定するのはデータコントローラーです。プロセッサーはコントローラーの指示で処理を行う委託先、サブジェクトはデータの本人（個人）です。カストディアンは GDPR の用語ではなく、CISSP 一般のデータロール（日々の保護作業担当）なので、GDPR 文脈の問題に混ぜられたらひっかけと疑いましょう。

</details>

**問2.** データベースの日次バックアップの実行と、オーナーが承認したアクセス権限の設定作業を担当する役割はどれでしょう？

1. データカストディアン（Data Custodian）
2. データオーナー（Data Owner）
3. データサブジェクト（Data Subject）
4. 最高情報セキュリティ責任者（CISO）

<details><summary>答えと解説</summary>

正解: **1**

バックアップやパーミッション設定といった「手を動かす日々の保護作業」はデータカストディアン（通常は IT 部門）の責任です。オーナーは分類や方針を決定・承認する立場で、日々の作業は行いません。サブジェクトはデータの本人、CISO は組織全体のセキュリティ統括で、個別データの運用作業者ではありません。「作業=カストディアン、決定=オーナー」の対応が頻出です。

</details>

**問3.** ある小売企業が、顧客の購買データの分析を外部の SaaS 事業者に委託しました。GDPR の観点で、この SaaS 事業者の役割として最も適切（BEST）なのはどれでしょう？

1. データオーナー
2. データコントローラー
3. データサブジェクト
4. データプロセッサー

<details><summary>答えと解説</summary>

正解: **4**

委託を受けてコントローラー（小売企業）の指示どおりにデータを処理する SaaS 事業者はデータプロセッサーです。処理の目的と手段を決めているのはあくまで小売企業側なので、SaaS 事業者はコントローラーではありません。サブジェクトは購買データの本人である顧客です。なお、委託してもコントローラーの責任は残る、という点もあわせて問われやすいので覚えておきましょう。

</details>

**問4.** データオーナーの責任として最も適切（MOST appropriate）なのはどれでしょう？

1. ファイアウォールのルールを日々メンテナンスする
2. 自分が責任を持つデータの分類レベルを決定する
3. 全社のセキュリティ予算を承認する
4. データの品質とメタデータを日常的に管理する

<details><summary>答えと解説</summary>

正解: **2**

データオーナーの中核的な責任は、担当データの分類の決定と保護方針の承認です。ファイアウォールの日常メンテナンスはカストディアン（IT 部門）の作業、全社予算の承認は経営層・CISO レベルの話でデータ単位のオーナーの役割を超えています。データ品質やメタデータの日常管理はデータスチュワードの担当です。

</details>

**問5.** 業務部門に所属し、データの意味・品質・業務上の利用ルールを管理する役割はどれでしょう？

1. データカストディアン
2. データプロセッサー
3. データスチュワード（Data Steward）
4. システム管理者

<details><summary>答えと解説</summary>

正解: **3**

データの品質や意味（メタデータ）、業務ルールの管理はデータスチュワードの役割です。カストディアンが「技術的な保護作業」を担うのに対し、スチュワードは「業務的な中身の管理」を担う、という対比で覚えましょう。プロセッサーは GDPR 文脈の委託先、システム管理者はカストディアンに近い技術側の役割で、いずれも業務的な品質管理の担当ではありません。

</details>

## 3. データライフサイクルと資産管理

### データライフサイクルの6段階

データは生まれてから消えるまで、次の段階をたどります。各段階で守り方が変わるのがポイントです。

**収集（Collect）→ 保存（Store）→ 利用（Use）→ 共有（Share）→ アーカイブ（Archive）→ 廃棄（Destroy）**

| 段階 | 保護のポイント |
|---|---|
| 収集 | **データ最小化（Data Minimization）**: 必要最小限しか集めない |
| 保存 | 分類に応じた暗号化・アクセス制御 |
| 利用 | 最小権限、利用目的の制限 |
| 共有 | 契約（NDA・DPA）、転送時の暗号化 |
| アーカイブ | 保持期間の管理、長期保存媒体の劣化対策 |
| 廃棄 | 確実な消去（詳細は次章） |

💡 コツ: 「プライバシー保護に最も効果的な方法は？」と問われたら、答えはたいてい**データ最小化**です。持っていないデータは漏えいしようがない——これが最強の保護です。

### データ保持（Retention）——長く持つほどリスク

保持ポリシー（Retention Policy）は「何を・どれだけの期間・どう保存し・いつ消すか」を定めます。法規制が求める期間は守る必要がありますが、**必要以上に長く保持することはメリットではなくリスク**です。保存コストがかかるうえ、漏えい時の被害範囲が広がり、訴訟時の電子証拠開示（eDiscovery）の対象も増えます。「とりあえず全部残す」は試験では誤答の典型です。

### 資産管理（Asset Management）

守るべきものを知らなければ守れません。**資産インベントリ（Asset Inventory）**には、ハードウェアだけでなく、ソフトウェア（ライセンス管理を含む）、クラウド上のリソース、データなどの**無形資産**も含めます。

注意が必要なのが **EOL（End of Life: 販売終了）/ EOS（End of Support/Service: サポート終了）**を迎えた資産です。サポート終了後はセキュリティパッチが提供されず、脆弱性が放置されます。原則は計画的な移行・更改ですが、やむを得ず使い続ける場合はリスク評価のうえ、ネットワーク分離などの**補償コントロール（Compensating Control）**を講じます。

### 確認問題

**問1.** 個人データのプライバシーを保護する方法として最も効果的（MOST effective）なのはどれでしょう？

1. 収集したすべてのデータを強力に暗号化する
2. 業務に必要な最小限のデータしか収集しない（データ最小化）
3. すべてのデータを10年間保持して監査に備える
4. アクセスログを毎日レビューする

<details><summary>答えと解説</summary>

正解: **2**

最も効果的なのはデータ最小化（Data Minimization）です。そもそも持っていないデータは漏えいも悪用もされないため、収集段階で絞ることがあらゆる保護策に勝ります。暗号化やログレビューは有効ですが「持ってしまった後」の対策です。長期保持はむしろリスクを増やす行為で、プライバシー保護とは逆方向です。

</details>

**問2.** 法規制上は3年の保存義務しかない顧客取引データを、ある企業は「いつか役立つかもしれない」と無期限に保持しています。この方針の最大の問題点はどれでしょう？

1. データが古くなり分析精度が下がる
2. バックアップ時間が長くなる
3. ストレージベンダーとの契約違反になる
4. 漏えい時の被害範囲と訴訟時の eDiscovery 対象が拡大し、リスクとコストが増える

<details><summary>答えと解説</summary>

正解: **4**

必要以上の長期保持は、漏えい時に影響を受けるデータ量を増やし、訴訟時の電子証拠開示（eDiscovery）の対象と費用も膨らませます。保持は「法規制と業務上の必要期間だけ」が原則です。分析精度やバックアップ時間も影響としてはあり得ますが、セキュリティ試験で問われる「最大の問題」はリスクの拡大です。ベンダー契約違反は一般には生じません。

</details>

**問3.** データライフサイクルの段階を正しい順序で並べたものはどれでしょう？

1. 収集 → 保存 → 利用 → 共有 → アーカイブ → 廃棄
2. 収集 → 利用 → 保存 → 廃棄 → アーカイブ → 共有
3. 保存 → 収集 → 共有 → 利用 → 廃棄 → アーカイブ
4. 収集 → 共有 → 保存 → アーカイブ → 利用 → 廃棄

<details><summary>答えと解説</summary>

正解: **1**

正しい順序は、収集（Collect）→ 保存（Store）→ 利用（Use）→ 共有（Share）→ アーカイブ（Archive）→ 廃棄（Destroy）です。データはまず集められて保存され、使われ・共有されたのち、アクティブな利用が終わるとアーカイブされ、保持期間が満了したら確実に廃棄されます。廃棄が最後に来ない選択肢はすべて誤りです。

</details>

**問4.** 基幹システムが依存する OS が来月 EOS（サポート終了）を迎えますが、システム更改は1年後まで完了しません。この状況で最も適切（BEST）な対応はどれでしょう？

1. サポートが切れても実績ある OS なのでそのまま使い続ける
2. 基幹システムをただちに停止する
3. リスク評価を行い、ネットワーク分離などの補償コントロールを講じたうえで移行を計画どおり進める
4. EOS の事実を記録せず現場判断に委ねる

<details><summary>答えと解説</summary>

正解: **3**

EOS 後はパッチが提供されず脆弱性が放置されるため、やむを得ず使い続ける期間はリスク評価のうえ補償コントロール（Compensating Control）——ネットワーク分離や監視強化など——で露出を減らすのが正解です。「実績があるから大丈夫」はリスクの無視、基幹システムの即時停止は事業影響が過大で管理者の判断として不適切、記録せず放置はガバナンスの放棄です。

</details>

**問5.** 資産インベントリ（Asset Inventory）に含めるべき対象として最も適切なのはどれでしょう？

1. 物理サーバーとネットワーク機器のみ
2. ハードウェア・ソフトウェア（ライセンス含む）・クラウドリソース・データなどの無形資産すべて
3. 購入価格が一定額を超える資産のみ
4. データセンター内に設置された機器のみ

正解: **2**

「守るべきものを知らなければ守れない」が資産管理の原則で、インベントリにはハードウェアに加え、ソフトウェアとそのライセンス、クラウド上のリソース、データといった無形資産も含めます。物理機器だけ、高額資産だけ、データセンター内だけ、といった限定はいずれも把握漏れ＝保護漏れを生みます。クラウド時代は「社外にある自社資産」の把握が特に重要です。
