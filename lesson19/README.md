# 第19章 アクセス制御モデルと実装【D5】

アクセス制御は「誰に・何を・どこまで許すか」を決める、D5 の中核です。この章では DAC / MAC / RBAC / ABAC などのモデルの使い分け、最小権限 (least privilege) を現場で機能させる仕組み、そして攻撃者がアクセス制御をどう破ろうとするかを学びます。モデル名の暗記ではなく「このシナリオならどのモデルが BEST か」を即答できる状態がゴールです。

## 1. アクセス制御モデル（DAC・MAC・RBAC・ABAC）

### 6つのモデルを「誰がルールを決めるか」で整理する

アクセス制御モデルは名前の暗記ではなく、**ルールの決定者と粒度**で整理すると迷いません。

| モデル | ルールを決める人 | 特徴 | 典型例 |
|---|---|---|---|
| DAC (任意アクセス制御 / Discretionary) | **データのオーナー** | ACL で柔軟に設定できるが、統制は弱い | Windows のファイル共有 |
| MAC (強制アクセス制御 / Mandatory) | **システム（ポリシー）** | ラベルとクリアランスで強制。最も厳格で柔軟性が低い | 軍・政府の機密システム |
| RBAC (役割ベース / Role-Based) | 管理者が**役割**に割当 | 職務（ロール）に権限を束ねる。人事異動・大量ユーザーに強い | 経理ロール・人事ロール |
| ルールベース (Rule-Based) | 管理者が**全員一律のルール**を定義 | 個人ではなくルールが対象。例外なく適用 | ファイアウォールのフィルタ |
| ABAC (属性ベース / Attribute-Based) | 管理者が**属性の組合せ**を定義 | ユーザー・環境・リソースの属性で判定。最も細かい | 「営業部 かつ 社内NW かつ 平日」なら許可 |
| リスクベース (Risk-Based) | システムが**状況を評価** | リスクが高いときだけ追加認証や拒否 | 海外からのログインに MFA を要求 |

### MAC の補足

MAC はラベル（Top Secret など）とクリアランス（人の許可レベル）の照合に加えて、**知る必要性 (need to know)** も満たす必要があります。クリアランスが Top Secret でも、担当外のプロジェクト情報は見られません。区画化 (compartmentalization) と呼びます。

💡 コツ: 試験で「人事異動のたびに権限設定が大変」と来たら **RBAC**、「属性や環境条件で細かく」と来たら **ABAC**、「オーナーが自分の判断で共有」と来たら **DAC**、「ラベル」「クリアランス」という単語が見えたら **MAC** です。問題文のキーワードがほぼ答えを指しています。

### 確認問題

**問1.** ファイルの作成者がそのファイルの ACL を自分で編集し、同僚にアクセス権を付与できるシステムがあります。このアクセス制御モデルはどれですか？

1. MAC（強制アクセス制御）
2. RBAC（役割ベースアクセス制御）
3. DAC（任意アクセス制御）
4. ABAC（属性ベースアクセス制御）

<details><summary>答えと解説</summary>

正解: **3**

データの**オーナー（作成者）が自分の裁量（任意 = discretionary）で**アクセス権を決められるのが DAC です。MAC はシステムがラベルとクリアランスで強制するためオーナーに裁量はありません。RBAC は管理者が役割に権限を割り当てるもので、個々のオーナーは決められません。ABAC は属性の組み合わせで判定します。ひっかけ: 「ACL」という単語は DAC の典型的な実装手段です。

</details>

**問2.** 従業員 5,000 人の企業で、部署異動のたびにアクセス権の付け替え作業が膨大になっています。管理負荷を下げるために最も適切 (BEST) なアクセス制御モデルはどれですか？

1. RBAC を導入し、職務ごとのロールに権限を集約する
2. DAC を導入し、各データオーナーに権限管理を委任する
3. MAC を導入し、全データにラベルを付与する
4. ルールベースアクセス制御を導入し、全員一律のルールを定める

<details><summary>答えと解説</summary>

正解: **1**

大量のユーザーと頻繁な人事異動には RBAC が BEST です。異動時は「ロールの付け替え」だけで済み、個別権限の棚卸しが不要になります。DAC はオーナー任せで統制が効かず、むしろ管理が散らばります。MAC は軍事レベルの厳格さが必要な場合の選択で、商用の管理負荷軽減には過剰です。ルールベースは個人の職務差を表現できません。ひっかけ: 「管理負荷」「人事異動」というキーワードは RBAC のサインです。

</details>

**問3.** 「経理部の正社員が、社内ネットワークから、営業時間内にアクセスした場合のみ許可する」という条件でアクセスを制御したい場合、最も適切なモデルはどれですか？

1. DAC
2. MAC
3. RBAC
4. ABAC

<details><summary>答えと解説</summary>

正解: **4**

部署・雇用形態（ユーザー属性）、接続元（環境属性）、時間帯（環境属性）という**複数の属性の組み合わせ**で判定するのは ABAC です。RBAC は「経理部」というロールまでは表現できますが、接続元や時間帯などの環境条件は扱えません。DAC はオーナーの裁量、MAC はラベルとクリアランスによる制御です。ひっかけ: RBAC と迷わせる問題では「ロール以外の条件（場所・時間・デバイス）」が入っていたら ABAC を選びます。

</details>

**問4.** ファイアウォールが送信元 IP アドレスとポート番号に基づき、すべての通信に同じフィルタリング条件を適用しています。これはどのアクセス制御の例ですか？

1. ABAC
2. ルールベースアクセス制御
3. DAC
4. リスクベースアクセス制御

<details><summary>答えと解説</summary>

正解: **2**

**利用者が誰かに関係なく、全トラフィックに一律のルール**を適用するのがルールベースアクセス制御 (rule-based access control) で、ファイアウォールが典型例です。ABAC はユーザーやリソースの属性を組み合わせて個別に判定する点が異なります。DAC はオーナーの裁量による制御、リスクベースは状況のリスク評価に応じて要求を変える制御です。ひっかけ: ルールベースと ABAC の違いは「全員一律か、属性で個別判定か」です。

</details>

**問5.** 普段は ID とパスワードでログインできるが、深夜に国外の IP アドレスからアクセスすると追加の多要素認証を要求されるシステムがあります。この仕組みを最もよく表すものはどれですか？

1. MAC によるラベル制御
2. DAC によるオーナー裁量の制御
3. リスクベースアクセス制御
4. ルールベースアクセス制御

<details><summary>答えと解説</summary>

正解: **3**

アクセスの**状況（時間帯・場所・デバイスなど）からリスクを評価し、リスクが高いときだけ認証を強化（ステップアップ認証）**するのはリスクベースアクセス制御です。ゼロトラストの「常に検証」とも相性のよい考え方です。ルールベースは一律適用でリスク評価をしません。MAC・DAC は認証の強度を動的に変える仕組みではありません。ひっかけ: 「状況に応じて要求が変わる」という動的な表現があればリスクベースです。

</details>

## 2. 最小権限の実装（need to know・職務分掌・ACL）

### 最小権限と need to know は別物

どちらも「絞る」考え方ですが、試験では使い分けが問われます。

| 原則 | 絞る対象 | 例 |
|---|---|---|
| 最小権限 (least privilege) | **権限・操作**（できること） | 一般社員にサーバー再起動権限を与えない |
| 知る必要性 (need to know) | **情報へのアクセス**（見られること） | クリアランスがあっても担当外案件の資料は見られない |

あわせて、**職務分掌 (separation of duties)** は「1 つの重要な処理を 1 人で完結させない」仕組みです。発注者と承認者を分ける、開発者に本番デプロイ権限を与えない、などが典型で、不正と誤りの両方を防ぎます。

### 権限は放っておくと増える

長く勤めた社員ほど、異動のたびに古い権限が残って**権限集約 (privilege creep / aggregation)** が起きます。対策は定期的な**アクセスレビュー（権限棚卸し）**です。また、許可されていないものはすべて拒否する**暗黙の拒否 (implicit deny)** がアクセス制御の大前提です。

### ACL とケーパビリティテーブル

アクセス制御マトリクス（主体×客体の表）を**列（オブジェクト）側から見たものが ACL**、**行（主体）側から見たものがケーパビリティテーブル**です。「このファイルに誰がアクセスできるか」= ACL、「この人は何にアクセスできるか」= ケーパビリティ、と視点が逆になります。

そのほか、メニューだけ表示する**制約付きインターフェース (constrained interface)**、データの中身で判定する**コンテンツ依存制御**（例: 給与列だけ隠すビュー）、状況で判定する**コンテキスト依存制御**（例: 営業時間外は拒否）も実装手段です。

💡 コツ: 「権限の付与しすぎ」が題材なら最小権限、「情報の見せすぎ」なら need to know、「1 人で不正が完結してしまう」なら職務分掌が答えの軸になります。

### 確認問題

**問1.** 10 年間で 4 つの部署を異動した社員が、過去の部署の権限をすべて保持したままであることが判明しました。この状態を防ぐために最も効果的 (BEST) な管理策はどれですか？

1. パスワードの定期変更を義務付ける
2. 定期的なアクセスレビュー（権限の棚卸し）を実施する
3. すべての社員に MFA を導入する
4. 退職時のオフボーディング手順を強化する

<details><summary>答えと解説</summary>

正解: **2**

異動のたびに古い権限が残って膨らむ**権限集約（privilege creep / aggregation）**への対策は、定期的なアクセスレビューで不要権限を剥奪することです。パスワード変更や MFA は認証の強化であり、保有権限の過剰には効きません。オフボーディングは退職時の手続きで、在職中の異動には対応できません。ひっかけ: 「長年の異動で権限が溜まる」というシナリオは、ほぼアクセスレビュー（または RBAC 導入）が正解です。

</details>

**問2.** 「Top Secret のクリアランスを持つ職員でも、自分の担当プロジェクト以外の機密文書にはアクセスできない」という統制の根拠となる原則はどれですか？

1. 職務分掌 (separation of duties)
2. 最小権限 (least privilege)
3. 暗黙の拒否 (implicit deny)
4. 知る必要性 (need to know)

<details><summary>答えと解説</summary>

正解: **4**

クリアランス（資格レベル）を満たしていても、**業務上知る必要のない情報には触れさせない**のが need to know で、MAC の区画化 (compartmentalization) の根拠です。最小権限は「操作・権限」を絞る原則で、情報の閲覧範囲を絞る本問とは軸が違います。職務分掌は処理を複数人に分ける話、暗黙の拒否は「明示的に許可されないものは拒否」という実装の原則です。ひっかけ: 最小権限と need to know の違い（できること vs 見られること）は超頻出です。

</details>

**問3.** 経費精算システムで「申請した本人がその申請を承認できない」ように設計しました。この設計が直接の目的とするものはどれですか？

1. 1人の人間による不正や誤りが完結するのを防ぐ
2. ユーザーの操作ログを完全に記録する
3. 権限の集約（privilege creep）を防ぐ
4. パスワードの使い回しを防ぐ

<details><summary>答えと解説</summary>

正解: **1**

申請と承認を別人に分けるのは**職務分掌 (separation of duties)** で、目的は 1 人で不正（または重大ミス）を完結させないことです。共謀 (collusion) がない限り不正が成立しなくなります。ログ記録はアカウンタビリティの話で職務分掌そのものの目的ではありません。権限集約の防止はアクセスレビュー、パスワード使い回し対策は認証管理の領域です。ひっかけ: 「申請者≠承認者」「開発者に本番権限なし」は職務分掌の典型パターンとして覚えましょう。

</details>

**問4.** アクセス制御マトリクスにおいて、「特定のユーザーがアクセスできるオブジェクトの一覧」を主体（行）の視点でまとめたものを何と呼びますか？

1. ACL（アクセス制御リスト）
2. セキュリティラベル
3. ケーパビリティテーブル
4. 監査証跡

<details><summary>答えと解説</summary>

正解: **3**

マトリクスを**行（主体）側から見た「この人は何ができるか」の一覧がケーパビリティテーブル**です。逆に**列（オブジェクト）側から見た「このリソースに誰がアクセスできるか」が ACL** です。この行と列の対比は頻出です。セキュリティラベルは MAC で使う機密区分、監査証跡は事後確認のための記録で、マトリクスの見方とは関係ありません。ひっかけ: 「ユーザー起点なら Capability、リソース起点なら ACL」とセットで覚えます。

</details>

**問5.** ファイアウォールのルールをすべて確認しましたが、ある通信を許可するルールも拒否するルールも存在しません。セキュアに設計されたシステムでこの通信はどう扱われるべきですか？

1. 管理者に通知した上で許可される
2. 暗黙の拒否 (implicit deny) により遮断される
3. 過去の通信実績に基づいて判断される
4. ルールが追加されるまで一時的に許可される

<details><summary>答えと解説</summary>

正解: **2**

アクセス制御の大原則は**明示的に許可されていないものはすべて拒否する「暗黙の拒否 (implicit deny)」**です。デフォルト許可（ルールがなければ通す）は、想定外の通信をすべて通してしまうフェイルオープンな設計で、セキュア設計原則に反します。実績ベースや一時許可という動作は標準的なアクセス制御には存在しません。ひっかけ: 「デフォルトで拒否 (deny by default)」はゼロトラストやファイアウォール設計の問題でも繰り返し登場する考え方です。

</details>

## 3. アクセス制御への攻撃（パスワード攻撃・フィッシング・Kerberos攻撃）

### パスワード攻撃は「何を避けようとしているか」で見分ける

| 攻撃 | やり方 | ねらい・特徴 |
|---|---|---|
| 辞書攻撃 (dictionary attack) | よくある単語リストで試行 | 弱いパスワードを素早く破る |
| 総当たり攻撃 (brute force) | 全組み合わせを試行 | 時間はかかるが理論上必ず当たる |
| パスワードスプレー (password spraying) | **1つの弱いパスワードを多数のアカウントに試す** | **アカウントロックアウトを回避**する |
| クレデンシャルスタッフィング (credential stuffing) | **他サイトから漏えいした ID/パスワードの組を試す** | **パスワードの使い回し**を悪用する |

スプレーとスタッフィングの対比は超頻出です。スプレーは「横に薄く撒いてロックアウト検知を逃れる」、スタッフィングは「漏えい済みの組をそのまま流し込む」と覚えましょう。

また、ハッシュから元パスワードを逆引きする事前計算表が**レインボーテーブル**で、対策はハッシュ前にランダム値を混ぜる**ソルト (salt)** です。

### 人を狙う攻撃

- **フィッシング**: 不特定多数への偽メール
- **スピアフィッシング**: 特定の個人・組織を狙い撃ち
- **ホエーリング**: 経営層 (whale = 大物) を狙う
- **スミッシング** (SMS) / **ビッシング** (音声電話)

### 認証基盤そのものを狙う攻撃（概要）

- **Pass the Hash**: パスワードを解読せず、盗んだハッシュをそのまま認証に使う
- **Kerberoasting**: サービスチケットを取得してオフラインで解析し、サービスアカウントのパスワードを割り出す
- **ゴールデンチケット**: Kerberos の鍵（krbtgt）を奪い、任意のチケットを偽造する

💡 コツ: 対策を選ばせる問題では、単一の技術よりも **MFA + 監視 + 最小権限**のような多層の組み合わせ、あるいは「根本原因（使い回し・弱いパスワード）に効くもの」が BEST になりがちです。

### 確認問題

**問1.** 攻撃者が「Password2026!」という1つのパスワードを、社内の数千アカウントに対して時間をあけながら試行しています。この攻撃手法はどれですか？

1. クレデンシャルスタッフィング
2. 辞書攻撃
3. パスワードスプレー
4. レインボーテーブル攻撃

<details><summary>答えと解説</summary>

正解: **3**

**1 つ（少数）のパスワードを多数のアカウントに横展開して試す**のがパスワードスプレーです。1 アカウントあたりの失敗回数が少ないため、アカウントロックアウトによる検知を回避できるのが特徴です。クレデンシャルスタッフィングは他サイトから漏えいした ID とパスワードの「組」を使う点が異なります。辞書攻撃は 1 アカウントに多数の候補を試す攻撃、レインボーテーブルは盗んだハッシュを事前計算表で逆引きする手法です。ひっかけ: 「ロックアウトを回避」とあればスプレーです。

</details>

**問2.** 他社サービスから漏えいしたメールアドレスとパスワードの一覧を使い、自社サイトへのログインを試みる攻撃が急増しています。根本原因に対して最も効果的 (BEST) な対策はどれですか？

1. 多要素認証を導入し、パスワード単独でログインできないようにする
2. パスワードの最小文字数を 12 文字に引き上げる
3. アカウントロックアウトのしきい値を 3 回に下げる
4. すべての通信を TLS で暗号化する

<details><summary>答えと解説</summary>

正解: **1**

この攻撃はクレデンシャルスタッフィングで、**正しいパスワードの組**が使われるため、文字数強化やロックアウトでは防げません（正解を 1 回で当ててくるため失敗回数が増えない）。パスワードが合っていても追加要素がなければ入れない MFA が最も効果的です。TLS は盗聴対策であり、漏えい済み認証情報の悪用には無力です。ひっかけ: 「使い回し悪用」に対し複雑性ポリシーを選ばせる誤答肢が定番です。

</details>

**問3.** パスワードハッシュのデータベースが漏えいした場合に備え、レインボーテーブルによる解析を困難にする対策として最も適切なものはどれですか？

1. ハッシュを MD5 から SHA-1 に変更する
2. ハッシュ化の前にユーザーごとに異なるソルトを付加する
3. パスワードを可逆暗号で保存する
4. ハッシュ値を Base64 でエンコードして保存する

<details><summary>答えと解説</summary>

正解: **2**

レインボーテーブルは「よくあるパスワード→ハッシュ」の事前計算表です。**ユーザーごとに異なるソルト**を混ぜると、同じパスワードでも異なるハッシュになり、事前計算表が無効化されます。MD5 から SHA-1 への変更はどちらも既に脆弱なうえ、ソルトなしでは事前計算が依然有効です。可逆暗号での保存は鍵が漏れれば全滅するため不適切、Base64 は暗号化ではなく単なるエンコードです。ひっかけ: 「アルゴリズムを変える」だけの選択肢はソルトの代わりになりません。

</details>

**問4.** 攻撃者が CFO になりすました偽メールを CEO に送り、機密の財務情報を引き出そうとしました。この攻撃を最もよく表す用語はどれですか？

1. スミッシング
2. ビッシング
3. 一般的なフィッシング
4. ホエーリング

<details><summary>答えと解説</summary>

正解: **4**

CEO・CFO などの**経営幹部（大物 = whale）を標的にしたフィッシング**がホエーリングです。スピアフィッシングの一種ですが、標的が経営層である点が特徴です。スミッシングは SMS、ビッシングは音声電話 (voice) を使う手口で、本問はメールです。一般的なフィッシングは不特定多数が対象なので、特定の幹部を狙う本問には当てはまりません。ひっかけ: 「特定の個人」ならスピアフィッシング、「その中でも経営層」ならホエーリングと段階で覚えます。

</details>

**問5.** 攻撃者が侵害した端末からパスワードハッシュを窃取し、平文に復元しないままそのハッシュを使って別のサーバーへの認証に成功しました。この攻撃はどれですか？

1. Pass the Hash
2. Kerberoasting
3. ゴールデンチケット
4. 総当たり攻撃

<details><summary>答えと解説</summary>

正解: **1**

ハッシュを**解読せずにそのまま認証へ流用する**のが Pass the Hash です。NTLM 認証などハッシュ自体が認証子として機能する仕組みを悪用します。Kerberoasting はサービスチケットをオフライン解析してサービスアカウントのパスワードを割り出す攻撃、ゴールデンチケットは krbtgt の鍵を奪って Kerberos チケットを偽造する攻撃で、どちらも本問の「ハッシュをそのまま使う」描写とは異なります。総当たりは解読を試みる点で逆です。ひっかけ: 「復元しないまま使う」が Pass the Hash のキーフレーズです。

</details>
